# Agent OS 项目经验底稿：从传统 RAG 到 Agentic Search + OpenCode Runtime

> 用途：面试底稿，尽可能的提前穷尽面试官可能会问的一切，以免在面试时陷入被动。
> 结构：每节一张卡片，正文 + 表格 + 引用块。附录保留可深挖的技术细节。
> 待办：聚合分析样例当前是脱敏同构版本，面试前替换成真实客户案例。

---

## 30 秒版本

这个项目最早是政企场景的知识库 RAG。第一阶段先把事实性问答的命中率做上去，约 25%。后来用户问的不只是事实，还有业务流程、要中间判断的复杂问题、基于业务记录的聚合分析，于是补了固定 workflow、又试着自己写 agent runtime。再后来发现自己写 runtime 这件事跟模型生态赛跑划不来，迁到 OpenCode 这类通用 coding agent。最新架构收敛成 OpenCode Runtime + AGENTS.md + Skills：runtime 交给生态，客户交付的核心变成领域 harness，把检索路由、领域工具、结果契约、权限边界和验证逻辑沉淀到 AGENTS.md 与 skills 里。

被追问时想留三句话给面试官：

1. 知识形态决定检索范式。
2. runtime 这一层值得交给生态，客户交付的核心是 AGENTS.md + Skills 这套领域 harness。
3. 选 agent 的主干工具，看失败模式可不可判别，不看能力强不强。

---

## 一、背景与定位（Situation）

### 1.1 三类知识，三种性质

| 类型 | 典型 query | 难点本质 |
|---|---|---|
| 事实性 | 制度、定义、参数、规范 | 一次检索能答，召回和排序问题 |
| 程序性 | ① 业务流程怎么走、调什么工具<br>② 结构化数据上做过滤、聚合、排序 | 处理逻辑可显式定义，要多步执行 |
| 判断性 | 方案比选、异常诊断、复杂条件推理 | 「对」很难定义清楚，依据藏在专家的隐性经验里 |

程序性的两个子形态共享一个性质：查询逻辑可显式写出来。区别只在执行手段，一个偏工具编排，一个偏代码或 SQL。

### 1.2 项目的难处不在调 RAG

把单个 RAG 调得更准只是一个局部问题。这个项目要解的是先看清这条 query 属于哪一类，再选检索和执行路径。

### 1.3 面试要讲的主线

不是 BM25、reranker 这些手艺，而是这条架构演进路线：

> 传统 RAG → 固定 workflow → 自研 agent runtime → Agentic Search + OpenCode runtime

每一步切换都有触发条件和判断依据，下一章按这条线展开。

---

## 二、三阶段架构演进（Task + Action）

### 2.1 第一阶段：传统 RAG + 固定 workflow

那会儿模型的 agentic 能力还弱，LangChain、AutoGPT 离生产稳定差得远。设计思路就两条：事实性问题走传统 RAG，程序性问题走固定 workflow。把确定的部分写死，让模型只在语义层面做它擅长的事。

#### 决策一：召回是上限，先把召回做对再调 prompt

把单通道 dense 升级成混合召回。BM25 + dense 双路检索，RRF 融合，再用 reranker 精排。[详见附录 A.1、A.5]

配套三件事：

- 分块按语义边界切，块大小当成可调参数，不死守 512 token。[A.2]
- 向量相似度用 cosine 或显式做 L2 归一化，避免长文档系统性占优。[A.3]
- query 改写时保留原始 query 做锚，避免越改越偏。[A.6]

知识库问答命中率提升约 25%（简历可量化数字）。

#### 决策二：程序性知识不上动态 agent，先用固定 workflow 顶住

当时的真实场景是用户的遥感影像数据治理流程，已经配齐了原子化治理工具。做法是人先把任务节点、工具调用、约束条件编排好，模型在每个节点只做语义判别和参数提取，实现就是状态机。

模型的指令遵循和 agentic 能力跟不上的时候，单靠模型跑不下来整套流程。这个做法土，但合理。

#### 切到第二阶段的触发条件

workflow 死板，新增一类流程就要写一套编排。query 形态从「按固定流程走」变成「先看情况再决定下一步」之后，这套架构就不够用了。

---

### 2.2 第二阶段：手搓 agent runtime + Agentic Search

直接动机是让流程能动态走，让 agent 根据 query 和中间结果，自己决定下一步检索什么、调什么工具、要不要补 context。

模型调用走的是开源聚合网关（new-api 这类），工具调用协议适配不是主要矛盾。费时间的全在 runtime 这一层的三件事：context 窗口管理、状态管理、可观测性。

#### 坑一：context 窗口管理远比看起来复杂

context 里堆的不只是问题加检索结果，还有工具描述、中间结果、失败重试、压缩摘要、已执行/待执行动作。随之要解的问题：

- 工具一多，哪些描述必须留在 context、哪些可以外置
- 窗口快满，怎么压缩才不丢掉后续推理依赖的信息
- 压缩摘要把关键决策依据丢了，agent 会在错误前提上继续往下做

听起来像「做个 summary」就完了，做起来全是工程细节，且高度依赖模型的实际行为。

#### 坑二：状态管理得自己设计

原本显式写在状态机里的东西，现在要重新定义：

- 当前轮 agent 处在规划、执行、等结果、重试还是收敛输出
- 中间失败怎么恢复，哪些状态保留、哪些回滚
- 多步任务什么时候算这一轮结束、什么时候继续迭代

这些不明确，agent loop 看起来在跑，实际可能在围着一个不清晰的状态机打转。

#### 坑三：可观测性靠手动加日志，效率很低

排查问题只能手动埋日志，看每步 prompt、工具 IO、压缩结果、状态跳转。能调，但体验差，迭代慢。时间花在「系统怎么又这样了」，不在「业务效果怎么往上推」。

#### 这一阶段的认知

runtime 这一层容易把工程投入吸进去，且跟具体业务逻辑没什么关系。手搓 runtime 本质是用大量过程控制换确定性。问题已经从「模型够不够聪明」变成「这套 agent loop 在工程上托不托得住」。

#### 切到第三阶段的触发条件

两件事同时成立：Agentic Search 对复杂 query 有价值，自研 runtime 的投入产出比不行——尤其在模型能力和生态都在快速变化的时候。下一步不是放弃 Agentic，是放弃自己造 runtime 这个轮子。

---

### 2.3 第三阶段：基于 OpenCode 的 runtime + Agentic Search

第一次切换是问题类型变了，第二次切换是成本结构变了。Claude Code、OpenCode、Codex 这些通用 coding agent 成熟之后，runtime 这一层在收敛成可复用的标准能力。

#### 分工怎么变

| 层 | 关注点 | 当前分工 |
|---|---|---|
| 模型层 | 选哪个模型、哪个 provider | 按任务特征选 |
| 协议层 | 怎么调模型 API、怎么接工具 | 靠现成生态 |
| runtime 层 | agent loop / context / 文件 / 工具 / 子 agent / 权限 | 复用 OpenCode |
| 领域 harness 层 | 路由规则、领域 skill、工具封装、验证逻辑、权限边界 | 自己重点做 |

前两个阶段，runtime 的复杂度都是应用层在背。第三阶段把它交出去，重心挪到领域 harness 上。

这层可以压缩成两类资产：`AGENTS.md` 和 Skills。`AGENTS.md` 是总入口，写项目背景、路由原则、安全边界和何时加载哪些 skill；Skills 是领域能力包，不只是 prompt，而是可以包含 SOP、CLI、Python 脚本、SQL 模板、向量检索工具、workflow、验证规则和案例。换句话说，客户交付的重点不是改 OpenCode runtime，而是把客户的领域知识、工具和风险边界产品化成这两层。

这里的结果契约不只是输出格式。它还包括评估数据怎么构造、不同类型 query 用什么指标判断、失败后怎么回流成 skill，以及什么时候必须转人工。

#### OpenCode 对这个项目的四件价值

1. 一套稳的 agent loop。能执行、能看结果、能纠错，不是一次 API 调用吐完就结束。
2. Bash 当原子能力。原本要在 workflow 里特殊处理的事，直接让 agent 写脚本、跑脚本、看结果。
3. 文件系统当状态载体。文件是看得见的状态，agent 可以反复读、改、验证，适合做闭环。
4. Skill 渐进加载。把高成功率路径、领域 SOP、确定性工具和验证规则封装成 skill，每次不用从零试。

#### 第二阶段的三个坑解决得并不一样

context 管理，基本解决。OpenCode 把 context 拆成「工作 context + 外置文件状态」，bash 输出可以选择性回写，子 agent 跑完只回传摘要。配合 `experimental.session.compacting` hook 自定义压缩时哪些信息必须保留，第二阶段那个「压缩摘要把关键决策依据丢了」的具体坑就解决了。

状态管理分两块看：

| 谁负责 | 解决程度 |
|---|---|
| runtime 内：session 历史、消息流、todo、文件读写、permission | OpenCode 全管 |
| 工具侧：有副作用的工具失败了怎么回滚 | 任何 runtime 都不管，业内（MS Agent Framework、LangGraph）都是开放问题 |

工程上能给工具加的约束分两层。第一层是单工具至少做到幂等，最好同时可逆。幂等是底线——同一个调用重试多次结果一样，避免 agent 不知道上次有没有成功就盲目重试出脏数据；可逆是加分项——一次做完，失败能自动回到原样。第二层是跨多个工具的业务操作，给每一步配一个反操作，失败时按倒序撤销。工程上有成熟方案（saga 模式），但落到 agent 场景仍是开放问题。这两层都做不到的话，就用 `tool.execute.before` hook 在关键操作前拦下来人工审批或外部校验。这些都是领域 harness 的责任，runtime 帮不上忙。

可观测性，开箱够用，工业级靠生态：

| 需求 | 方案 |
|---|---|
| 看每步发生了什么 | `client.app.log()` 结构化日志，分级输出 |
| trace tree、token cost、prompt/response 检视、replay | 当前用 Arize Phoenix。OpenCode 没有原生 OTLP export，自写 plugin (`phoenix-otel.ts`) 把 session/tool 事件按 OpenTelemetry 协议导到本地 Phoenix server (OTLP gRPC 4317，UI 6006)，靠 `experimental.openTelemetry` 开关挂上去 |

什么时候会换：

- 团队整体接入了 Grafana 栈，想把 LLM trace 和系统指标放一处看 → 把 OTLP 同时导一份到 Tempo，Phoenix 仍然保留作为 LLM 视图。
- 开始做线上 prompt A/B 和系统化评测流水线 → 评估迁到 Langfuse，或 Phoenix + 单独的 prompt registry。
- 业务真上微服务化、要做跨服务根因分析 → 才考虑 Jaeger 或 Honeycomb 这类通用后端。

更准确的说法是：context 由 runtime 直接收掉，可观测性靠生态补齐，状态管理则把「runtime 该管的」和「领域 harness 该管的」明确切开。这个切分本身就是这一阶段的认知收获。

权限和 hooks 是这套架构进入客户生产流程时必须补上的治理面。低风险检索可以自动执行；只读 SQL 可以自动执行但记录 trace；批量治理、写库、删除图层、发布报告这类高风险 skill 必须先 dry-run，再通过 permission 或 `tool.execute.before` hook 做人工确认或参数校验。AGENTS.md 写原则，skill 写流程，permission 决定能不能做，hook 决定做到关键步骤时要不要停下来检查。

#### 生态层面的判断

Coding agent 是模型提供商当前主动适配的方向，工具调用格式、context 压缩策略、长 context 稳定性这些长尾问题由生态一起摊。自己写 runtime 就要跟模型迭代速度赛跑，站在通用 runtime 上则是让 runtime 跟着模型生态一起进步。

#### 项目重点的变化

不再是堆 workflow，也不再是打磨自研 runtime。三件事变成主线：

1. 看 query 属于哪种知识形态
2. 为这类 query 选对检索和执行路径
3. 把「怎么做」和「怎么验证」沉淀进 AGENTS.md、skills、permissions 和 hooks

放到面试里讲，这一阶段的价值不在系统做出来了，在于知道哪些东西该自己做、哪些该站在生态上复用。OpenCode 负责通用 runtime，应用团队负责领域 harness。

## 三、当前架构深度展开（Result）

### 3.1 路由原则：知识形态决定检索范式

三阶段走完之后，路由判断收敛成一张表：

| 知识类型 | 典型 query | 当前主路径 | 为什么 |
|---|---|---|---|
| 事实性 | 制度、定义、参数、规范 | 混合 RAG | 召回和排序问题 |
| 程序性 - 业务流程 | 某类业务流程怎么走 | 固定 workflow 或浅层 Agentic | 路径已知，保留确定性骨架 |
| 程序性 - 结构化分析 | 时间过滤、分组聚合、排序对比 | 代码 / SQL 执行 + 汇总 | 逻辑明确，走计算不走检索 |
| 判断性 | 方案比选、异常诊断、要中间判断 | Agentic Search | 标准在过程中逐步逼近 |

这张表把「要不要上 Agentic」从一个抽象讨论变成了明确的路由规则。系统不会所有 query 都往 Agentic 推，也不会都塞进 RAG。怎么算成熟？知道什么时候该保住确定性，什么时候该把控制权交给 agent。

这张表也决定了评估方式。事实性问题看证据召回和引用是否准确；程序性问题看流程选择、参数提取和 SQL / 脚本结果能否复算；判断性问题看证据链是否完整、工具路由是否合理、信息不足时是否转人工。

### 3.2 Agentic Search 处理的两类活

Agentic Search 当前主要处理两类场景：结构化分析（程序性）和判断性问题。两者都要多步执行，区别在前者逻辑明确，后者标准模糊。

#### 类型一：结构化分析——别把算账做成找相似

脱敏样例。系统里有任务执行记录表，用户会问：

1. 「找出所有最后一次成功执行使用了某类治理策略的任务，按策略归类。」
2. 「最近一周主要在处理什么类型的任务？」
3. 「哪类任务执行次数最多且一次通过率最低？」

看着是问答，骨子里是 group by、时间过滤、排序、多指标联合比较。问题不是「找相似文本」，是「在数据上做计算」。把这种数据切块灌进向量库再让 RAG 去答，最多召回几段「看起来相关」的片段，给不出精确统计。跟分块、reranker、prompt 怎么调都没关系。

合理路径：agent 识别这是结构化分析，读入全量或子集数据，动态生成 Python / SQL / shell 脚本做精确统计，再基于统计输出自然语言总结。

这里有一个面试加分点：context 装得下的时候，RAG 可能是负优化。能直接对原始数据做精确分析的场景，RAG 把数据切碎，把问题降级成「相似片段拼接」，精度天然差。

#### 类型二：判断性问题——LLM 是检索规划器，不是生成器

GIS 客户常问的「某省地理要素更新方面的变化信息有哪些」，面试里可以先翻译成通用问题：某个地区的道路、建筑、河流、边界等地图对象，在一段时间内发生了哪些新增、删除、属性变化或位置变化。这个问题通常要同时查规范文档、变更记录表、治理任务日志和历史案例，所以评估也不能只看最终回答是否流畅，而要看关键证据是否覆盖、统计结果是否可复算、结论是否都有来源。

异常诊断这种问题不是检索一次就答：

1. 检索相关规则和历史案例
2. 根据中间结果判断当前更像哪种异常
3. 补检索缺的那部分证据
4. 收成答案或下一步建议

LLM 的角色变了：决定搜什么、搜几次、用什么工具、结果够不够回答。这一类问题的天花板不在工程，在能不能把领域专家的隐性经验显式化下来。

### 3.3 工具选择的底层逻辑：失败模式决定 agent 友好度

到了 Agentic Search 阶段，工具的价值不只是能不能查到，还要看查不到的时候 agent 知不知道自己没查到。

| 工具 | 失败模式 | agent 友好度 |
|---|---|---|
| grep / ripgrep | 返回 0 行，明确无结果 | 高 |
| SQL | 语法报错或返回空表，明确 | 高 |
| 向量检索 | 永远返回 top-k，哪怕全不相关 | 低 |
| 直接读文件 | 装得下就准，装不下静默退化 | 中 |

选 agent 的主干工具，看的不是能力强不强，是失败模式可不可判别。

这也是为什么 coding agent 的搜索主干往往是 grep。grep 没结果，agent 立刻知道要换关键词、换范围、换工具；向量检索就算没找到答案，也会返回一堆「看起来像结果」的东西，agent 就不知道自己没找到。

业务场景同理。结构化分析用 SQL 和脚本比向量检索合适，不是因为它们更聪明，是因为结果边界更清楚。

### 3.4 工作方式从过程确定性转到结果确定性

迁到 OpenCode 之后，主要精力不再放在「怎么把 agent loop 写稳」，挪到了两件靠近业务价值的事：

1. 把「结果对」的标准定下来
2. 把高成功率的路径沉淀成 skill 和确定性工具

|  | 自研 runtime 阶段 | OpenCode 阶段 |
|---|---|---|
| 本能反应 | 把每一步都规定死 | 不强规定每一步走哪条路 |
| 稳定性来自 | 过程控制 | 把最终产物长什么样定清楚 |
| 给 agent 留什么 | 强约束流程 | 自己看结果、自己改的验证手段 |

这也是 OpenCode 的文件系统和 Bash 能力为什么重要：文件是看得见的状态，脚本是可验证的动作，agent loop 才能闭环。[详见附录 B.1]

### 3.5 用 skill 收敛模型路径差异

迁到 OpenCode 之后有个很直观的观察：同一个复杂 query，换不同模型跑，最终答案差不多，但中间路径差很多。

常见的差异：

- 有的模型先写代码做精确统计再总结，有的读完数据就开始自然语言推理
- 有的对单 agent 能搞定的任务过度派发子 agent
- 有的会自作主张改统计口径，比如把「最近一周」理解成自然周或滚动 7 天

不加约束的话，这种路径差异在生产环境就变成输出口径不一致。

skill 在当前架构里干的就是这件事：不是给 agent 多塞几句 prompt，而是把高成功率路径沉淀成可复用的领域能力包，把模型默认的路径偏好往一处收。一个 skill 可以包含操作说明、CLI、脚本、SQL 模板、向量检索入口、workflow、验证规则和案例。

当前已经识别出三条值得封装的 skill 规则：

1. 结构化数据分析必须先做精确统计再总结，不允许 agent 看一眼数据就下结论。
2. 单文件且 context 装得下的时候，不要为了并行而并行，避免无意义派发子 agent，把 token 成本和整合复杂度抬上去。
3. 输出口径必须固定。时间范围怎么算、分类标签用哪一套、统计口径怎么定义，写进 skill 或契约层，不让模型临场决定。

抽象一层，skill 把「每次重新试错」变成「复用已经验证过的成功路径」。这既是路径一致性问题，也是结果确定性问题。[详见附录 B.2]

skill 的来源不是预先拍脑袋写规则，而是从线上失败 case、专家评审和回归评测里沉淀。每次发现 agent 漏查数据源、改错统计口径、该停不停，都要把这类失败变成新的评测样本或 skill 约束。

### 3.6 多 agent 编排：task tool 和手工 spawn 的取舍

> 高级话题，被追问时展开。

OpenCode 体系里子 agent 编排两种方式。task tool 是同 session 内主 agent 派发子 agent；手工 spawn 是在 OpenCode 外面自己写编排器，起多个独立 session。

| 场景 | 推荐模式 |
|---|---|
| 单任务内能拆 2-3 个足够重的子任务 | task tool |
| 跨模型对比或大规模批量跑任务 | 手工 spawn |
| 需要细粒度控制超时、重试、并发 | 手工 spawn |
| 单文件或小范围任务 | 不并行，主 agent 自己做 |

当前项目里大多数聚合分析 query 属于最后一种，一个主 agent 直接读数据、写脚本、跑验证、汇总结果就够了。这种场景更需要明确的 skill 约束，防止模型为了显得更 agentic 而过度并行。

## 四、结果与复盘（Result + Learning）

### 4.1 可讲结果

| 层 | 内容 |
|---|---|
| 量化结果 | 传统 RAG 阶段用混合检索 + RRF + reranker，知识库问答命中率提升约 25% |
| 能力边界扩展 | 从只处理事实性问答，到覆盖程序性查询（业务流程 + 结构化分析），到覆盖判断性问题 |
| 评估闭环 | 复杂 GIS 问题从「agent 能跑」变成「可评估、可回归、可持续改进」 |
| 交付形态收敛 | 从交付自研 runtime，收敛为交付 AGENTS.md + Skills + 权限 / hooks 的领域 harness |
| 架构判断力成熟 | 从倾向自己造轮子，到知道哪一层该交出去、哪一层自己守 |

第三阶段补上的关键不是更多 workflow，而是领域 harness 和评估闭环。沿用前面的知识分类定义评估方式：事实性问题看证据召回和引用是否准确；程序性问题看流程选择、参数提取和计算结果能否复算；判断性问题看证据链是否完整、工具路由是否合理、信息不足时是否转人工。线上失败的 case 会回流成新的评测样本和 skill 规则，模型、检索策略或 skill 变更前先跑回归，避免靠主观体感判断效果。对高风险 skill，再通过 permission 和 hooks 做 dry-run、人工确认和参数校验。

面试官问「这个项目难在哪」，建议讲第三层。前两层很多团队都有，第三层更能体现对 agent 系统边界的认知。

### 4.2 留下的 6 个判断

1. 召回是上限。事实性问答先把召回做对，再谈排序和生成。
2. 知识形态决定检索范式。事实性、程序性、判断性三类不该用同一套方法硬打；程序性内部还要再分流程编排和结构化分析。
3. 模型能力不够时，固定 workflow 是保留确定性的合理手段，谈不上落后。
4. 自研 runtime 的成本不在功能开发，在 context 工程、状态管理、可观测性。
5. runtime 这一层值得交给生态。应用层精力放在 AGENTS.md、skills、权限 / hooks 和业务结果定义上。
6. 选 agent 的主干工具，看失败模式可不可判别，不看能力强不强。

### 4.3 一句话版本

> 项目走过三步：把 RAG 调准；给不同类型的 query 选对范式；划清自研和复用 runtime 的边界。最新形态是 OpenCode Runtime + AGENTS.md + Skills，难点从 runtime 转移到领域 harness 和结果契约。

## 附录 A：传统 RAG 调优技术速查

这一部分不是正文主线，而是被深挖时拿来展开的“技术弹药”。正文讲到事实性问答的优化时，可以按需引用。

### A.1 Hybrid Recall + RRF：为什么先做 BM25 + dense

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：Dense 单通道在专有名词、产品编号、错误码这类 query 上天然会塌，必须补一路稀疏检索。BM25 + dense 做 hybrid，是 ROI 最高的一步。

**为什么**：embedding 模型会把精确 token 泛化成语义类别，字面精度丢失。BM25 在精确 token 匹配上是天然强项，两路刚好互补。

**为什么用 RRF 融合**：BM25 分数和 cosine 分数量纲不可比，直接做归一化加权不稳。RRF 用 rank 不用 score，绕开量纲问题，简单但稳定。

**面试一句话**：在 RAG 里，hybrid 不是锦上添花，而是 dense retrieval 结构性弱点的补丁。

### A.2 Chunking：为什么把 chunk size 当变量调

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：chunk size 不应固化成 512 token 这种教程默认值，而应该按 query 类型和语义边界调。

**为什么**：事实性问题适合短 chunk，信号纯；主题性问题适合长 chunk，需要更多 context。固定 token 切分还容易把完整语义单元截断。

**实际策略**：按标题、段落、列表、代码块等语义边界切；默认值更倾向 200-300 token；长文档场景上 hierarchical retrieval。

**面试一句话**：512 token 是教程默认值，不是最优值。chunking 应该是变量，不是常数。

### A.3 向量相似度：为什么默认选 cosine

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：cosine similarity 默认比 dot product 更稳，因为它消除了向量长度对分数的系统性影响。

**为什么**：语料同时包含短 FAQ 和长手册时，长文档 embedding 范数天然更大，dot product 会偏向长文档。cosine 或显式做 L2 归一化可以消除这个偏差。

**面试一句话**：dot product 的问题不是偶发误差，而是分布偏置，所以值得在上线前主动校验。

### A.4 HNSW：为什么 `ef_search` 值得调高

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：在 LLM pipeline 里，HNSW 的 `ef_search` 往往可以放心调高，因为检索延迟不是整体瓶颈。

**为什么**：检索阶段多花几毫秒到几十毫秒，后面 reranker 和 LLM 本来就是更大的延迟头。对用户体感几乎无差，但能换来更高召回。

**面试一句话**：HNSW 的 `ef_search` 是典型的“用一点点延迟换稳定召回”的单边收益参数。

### A.5 Reranker：为什么说它是放大器，不是召回器

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：reranker 的作用是在候选池里做精排，前提是候选池里已经有相关文档。第一阶段没捞回来，第二阶段救不回来。

**为什么**：两阶段排序的上限由召回质量决定。很多团队喜欢先调 reranker，是优先级倒了。

**实践原则**：召回阶段先做多通道和合理的 top-k；reranker 至少做一次领域评测，不要直接套用通用网页搜索上的默认模型。

**面试一句话**：reranker 只能把相关文档排前面，不能把没召回的文档凭空变出来。

### A.6 Query Rewriting：为什么要保留原始 query

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：query rewriting 的价值是补 vocabulary gap，但必须保留原始 query 做 fallback。

**为什么**：LLM 改写的核心风险是 query drift。一旦改写偏了，整个检索会越走越偏。最稳妥的方法是原始 query 和改写 query 同时检索，再合并去重。

**面试一句话**：LLM query rewriting 很强，但它继承了传统 relevance feedback 的老问题，不能把原始 query 扔掉。

### A.7 如果面试官往 IR 深挖，可以主动抛的 3 句

1. **“RRF 的核心不是公式有多复杂，而是它用 rank 绕开了多路分数量纲不可比的问题。”**
2. **“chunking 真正该问的是 query 形态，不是教程里写了 256 还是 512。”**
3. **“RAG 的大部分核心技术，在 IR 里其实早就有对应经验，真正的新东西是把这套能力压缩到了普通 Python 开发者也能快速搭起来的程度。”**

## 附录 B：基于 OpenCode 做 runtime 的工程细节

这部分是正文里"为什么迁移到 OpenCode"和"工作方式变化"两段的工程展开。面试官如果继续往"怎么真正接进系统"里问，可以从这里抽素材。正文已经覆盖了四层结构、四个核心能力、task tool 与手工 spawn 的取舍，附录不再重复，只补两块正文放不下的内容：生产级接入细节，以及契约层应该怎么定义。

### B.1 把 OpenCode 真接进系统时，几个细节不能忽略

1. **文件响应模式比管道模式稳。** 把输入和输出都显式落文件，agent 的心智模型更稳定，也便于审计和重试。
2. **工作目录要设计清楚。** 这类 runtime 往往对可访问路径有明确边界，临时文件、prompt 文件、输出文件最好都放在项目工作目录下。
3. **stdout 要有兜底。** 即使已经要求 agent 把结果写入文件，也要准备从 stdout 提取结构化输出的 fallback。
4. **并发能力不要想当然。** 一个 runtime 能不能稳定吃多并发，除了自己这层，还取决于底层模型 provider 的 rate limit。
5. **权限边界是工程问题，不是 prompt 问题。** 能限制的工具尽量限制，必要时配合 sandbox 和 allowed tools。

这些细节平时看起来琐碎，但真正决定了"能 demo"还是"能生产"。

### B.2 结果确定性：契约层应该怎么定义

迁移到 OpenCode 之后，应用层最应该投入的不是再去规定 agent 每一步怎么做，而是把结果契约写清楚。最少要明确四件事：什么叫做完、什么叫做对、怎么验证它做对了、验证失败后怎么办。

放到当前项目里，契约层至少应该包含：输出 schema 或固定结构；时间范围、分类体系、统计口径等显式定义；对关键结果的验证脚本或可复算逻辑；何时重试、何时人工接管的规则。

也正因为如此，skill 不是孤立存在的。它和契约层是一体两面：契约层定义"什么是对的"，skill 定义"多数情况下怎么更容易做到对"。

### B.3 领域 harness：AGENTS.md + Skills + 权限 / hooks

最新架构可以压缩成一句：OpenCode Runtime 承接通用 agent 能力，AGENTS.md 做总路由，Skills 承载领域方法、工具和验证。客户交付的核心不是改 runtime，而是为客户写好这套领域 harness。

这里的 skill 不是普通 prompt 模板，而是可复用的领域能力包。它可以包含操作说明、CLI、Python 脚本、SQL 模板、向量检索入口、workflow、验证规则和案例。比如 GIS 数据治理里，一个「地理要素更新分析」skill 可以规定先查规范文档，再查变更记录表，再跑 SQL 统计，最后用验证脚本检查答案里的数字是否都来自可复算结果。

权限和 hooks 负责治理高风险动作。低风险检索自动允许；只读 SQL 自动允许但记录 trace；批量治理、写库、删除图层、发布报告必须先 dry-run，再由 permission 要求人工确认，或由 `tool.execute.before` hook 检查参数和影响范围。这样 AGENTS.md 定原则，skill 定流程，工具负责执行，permission 和 hook 守住生产边界。
