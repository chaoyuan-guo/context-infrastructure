# GeoAgent 项目面试准备底稿

## 开场介绍：90 秒版本

这个项目面向政企客户。客户的制度文档、业务数据、流程系统和工具入口分散在不同系统里，很多业务问题从提出到处理完成，需要在文档检索、数据分析、专家判断和流程执行之间来回切换。项目要解决的是分散入口带来的效率问题，具体表现为处理链路长、人工拼接成本高。

所以这个项目的定位是企业智能体：把这些分散能力收敛到一个自然语言入口里，再根据问题类型选择合适的处理路径，帮助客户用自然语言完成高效的信息获取和受控任务执行。

我把用户问题分成四类：能查到的、能算出来的、需要综合判断的、需要执行的。比如规章制度和规范定义走文档 RAG；治理任务次数、通过率、失败原因分布走 SQL 或脚本；地理要素变化分析需要综合规范文档、变更记录、治理日志和专家经验；数据治理流程和报告生成则属于受控任务执行。

技术上我把它拆成两层。底层复用 OpenCode 这类成熟 agent runtime，负责 agent loop、工具执行、文件状态和权限控制。上层自己建设领域 harness，也就是 AGENTS.md + Skills，把客户的领域知识、业务流程、工具入口和风险边界沉淀下来。

评估上也拆成两层。第一层看结果是否正确，比如证据是否能支撑回答，SQL / 脚本结果是否可复算，任务是否完成。第二层看 agent 行为是否可靠，比如路由是否合理，证据不足时是否追问或拒答，高风险动作是否经过模拟执行、审批和审计。

## 追问地图

开场之后不用按顺序背。面试官往哪个方向问，就跳到对应分组。

---

### 1. 定位与价值

#### 项目边界：和知识库 RAG、BI、工作流系统分别怎么分工？哪些场景应该交给传统系统或转人工？

**对方可能在关心**：你是否理解 agent 的边界，以及传统系统各自适合解决什么问题。

**先回应**：RAG、BI、工作流分别适合文档问答、固定指标和标准流程；agent 更适合跨文档、数据和工具的开放任务，尤其是中间需要判断、探索或动态选择路径的场景。

**如果继续聊**：知识库 RAG 适合回答制度、规范、定义这类文档证据问题；BI 适合稳定指标和固定报表；工作流系统适合标准化流程流转。Agent 的价值在于把这些能力编排起来，处理那些路径无法提前完全固化的问题。

**边界提醒**：高频、稳定、低歧义的指标查询优先做成 BI 或固定接口；规则已经完全固定的审批流优先走工作流；缺少数据来源、业务规则或可验证依据的问题，应该追问、拒答或转人工。

#### 业务价值：没有更多通用量化指标时，怎么证明这个项目有价值？

**对方可能在关心**：没有收入、DAU 这类通用指标时，你是否能把项目带来的业务变化讲清楚。

**先回应**：我会从工作方式变化讲价值：原来分散在文档、数据、专家和流程里的工作，现在能被收敛成一条可追溯的任务处理链路。

**如果继续聊**：过去用户要分别找制度文档、查数据库、问 GIS 专家，再手工整理报告；现在 agent 能在同一次任务里给出证据、SQL / 脚本结果、限制条件和下一步动作建议。对客户来说，价值体现在减少跨系统切换和人工拼接，让结论有依据、数字可复算、动作可审计。

**边界提醒**：25% 可以在被问到 RAG 效果时作为补充，口径限定在传统 RAG 的内部事实性问答集，来自 hybrid recall、RRF 和 reranker。这个指标用于说明 RAG 基础能力；OpenCode / Agentic Search 阶段需要单独评估。

### 2. 架构分层

#### Runtime 取舍：为什么复用 OpenCode 做 agent runtime？

**对方可能在关心**：你们是在套一个现成工具，还是清楚哪些能力应该复用、哪些能力必须自己做。

**先回应**：我把 OpenCode 当成通用 agent runtime。它解决 agent loop、工具执行、文件状态、权限控制和 hook 这些底层问题，我们把主要精力放到客户侧领域 harness 和业务工具接入上。

**如果继续聊**：自研 runtime 的成本很高，政企客户项目的差异点通常在领域知识、业务工具和治理规则。OpenCode 已经提供工具调用、权限配置、插件 hook、上下文和交互式执行体验。项目里更关键的是把制度文档、业务数据、GIS 工具、SQL 查询、报告模板、审批规则和审计 trace 接进去，让 agent 能在客户真实环境里工作。

**边界提醒**：复用 runtime 只是起点。OpenCode 提供运行底座，客户场景里的知识组织、工具封装、权限规则、trace 字段、评测集和失败处理仍然要单独建设。

#### Skills 设计：Skill 具体长什么样？怎么判断一个 skill 质量高不高？

**对方可能在关心**：领域能力怎么沉淀，复杂任务执行时是否每次都靠模型自由发挥。

**先回应**：Skill 是一类任务的执行手册和质量约束。它会写清触发条件、输入要求、步骤依赖、可并行和需串行的环节、工具入口、输出结构、校验规则和失败处理。

**如果继续聊**：比如 GIS 变化分析 skill 会先要求确认地区、时间范围、对象类型、数据版本和输出目标。边界确认后，规范口径、数据结构、历史案例可以并行查；候选变化和空间计算依赖数据版本、字段和判定口径，要等这些输入明确后再执行；最后按同一批对象把规范、记录、计算结果和日志解释对齐。

**边界提醒**：我判断一个 skill 好不好，会看它能否约束执行过程。比如缺少输入时是否会追问，工具调用和输出 schema 是否稳定，关键证据和参数是否会进入 trace，遇到失败 case 时，能否定位到应该修订触发条件、校验规则还是降级路径。

#### 架构复用：如果换一个政企客户，GeoAgent 怎么迁移？

**对方可能在关心**：这个项目是否形成了可复制的方法论，还是只针对一个客户定制了一次。

**先回应**：我会把可复用部分分成两类：一类是技术底座，另一类是交付方法。真正需要重建的是客户自己的领域内容和业务边界。

**如果继续聊**：技术底座包括 OpenCode runtime、permission / hook 模式、trace 与审计结构、skill 文件格式。交付方法包括任务分类、skill 设计方法、评测集构造和失败 case 复盘流程。换客户时要重新建设领域术语、数据 schema、工具连接器、业务流程、权限规则和核心 skills。

**边界提醒**：迁移时最容易低估的是业务边界重建。两个客户都做 GIS，也可能在数据版本、审批链路、异常口径和风险动作上差异很大，所以要重新做领域访谈、样例收集和回归集。

### 3. 路由与编排

#### 任务分类：为什么把问题分成查得到、算出来、判断出来、任务执行？边界模糊时怎么处理？

**对方可能在关心**：四类任务的依据是否清楚，以及复杂问题落到多个类别时系统怎么处理。

**先回应**：这个分类来自用户意图和答案生成方式，主要用来决定后面的处理路径和验收方式。边界模糊时，agent 会先做低风险探索，关键约束仍然缺失时再追问或拒答。

**如果继续聊**：查得到的问题靠检索，算出来的问题靠计算，判断出来的问题靠多源证据和专家规则，任务执行会改变业务状态。边界模糊时，agent 先查 AGENTS.md、Skills INDEX、数据目录和历史样例，找出最可能的执行路径；能形成可验证计划时，就按计划推进并写出关键假设。

**边界提醒**：探索只用于缩小不确定性。关键意图、统计口径、权限或数据源仍然缺失时，需要用户澄清；涉及写库、发布、删除等副作用时，进入审批或拒绝执行。

#### 任务路由：模型怎么判断该走 RAG、SQL、Agentic Search 还是任务执行？路由错了怎么办？

**对方可能在关心**：路由依据是否清楚，以及路由错误后是否有反馈机制。

**先回应**：路由由 AGENTS.md + Skills INDEX 驱动，INDEX 暴露每个 skill 的适用场景、输入要求、工具入口、输出格式和风险等级。

**如果继续聊**：AGENTS.md 放全局原则和安全边界，例如制度类结论必须带来源，统计数字必须来自 SQL / 脚本，证据不足需要追问，写库、删除、发布必须先模拟执行再审批。路由结果会进入 trace，包括加载了哪个 skill、调用了什么工具、拿到了哪些证据、在哪一步失败。

**边界提醒**：路由错误会沉淀成失败 case，用来修正 skill 描述、补充反例，必要时加入回归集，避免同类问题反复走错路径。

#### 复杂编排：需要综合多源证据时，agent 怎么把不同证据串起来？

**对方可能在关心**：你说的"综合判断"是否有真实场景，以及 agent 怎么把文档、数据、空间计算工具、日志和专家经验组合成可验证结论。

**先回应**：我会用 GIS 地理要素变化分析举例。它需要同时理解规范定义、查询变更事实、调用空间计算工具、参考治理日志和专家口径，最后把这些结果串成一条证据链。

**如果继续聊**：比如用户问某地区地理要素有哪些变化，可以先把它翻译成更通用的问题：道路、建筑、河流、边界等地图对象，在一段时间内有哪些新增、删除、属性变化或位置变化。规范文档定义什么算变化，变更记录提供候选事实，空间计算工具负责判断位置变化、范围叠加、距离关系和面积变化，治理日志解释处理过程和质量校验结果，专家经验处理口径差异和例外情况。

**边界提醒**：最后输出要按结论挂证据：每个变化分类对应规范依据、数据来源、空间计算结果、统计结果和限制条件。空间计算的参数和版本要留痕，缺少证据或工具结果不可信时，要标注不确定性或拒答。

#### Multi-subagent：什么情况下用多个 subagent？成本、冲突和结果整合怎么处理？

**对方可能在关心**：multi-subagent 在真实业务场景里怎么落地，任务依赖关系和并行边界怎么处理。

**先回应**：GIS 变化分析适合用主 agent 编排多个 subagent。它带有明确依赖关系：主 agent 先按 skill 确认任务边界，再在条件满足后局部并行，最后做证据对齐和结论判断。

**如果继续聊**：GIS 变化分析 skill 会先规定整体 workflow。主 agent 先确认地区、时间范围、要素类型、数据版本和输出目标。边界确认后，可以并行查规范口径、数据结构和历史案例；候选变化和空间计算任务依赖数据版本、图层字段和判定口径，要等这些输入明确后再执行；空间计算或候选变化出来后，再并行查对应治理日志和异常案例。最后主 agent 按同一批地理要素对齐规范、记录、空间计算结果和日志解释，检查这些证据是否能共同支撑结论。

重叠控制在这里体现为对齐锚点。不同 subagent 负责不同证据源或计算任务，但输出都围绕同一地区、同一时间窗口、同一数据版本、同一批要素和同一套结构。主 agent 由此可以发现冲突：记录里有变化但空间计算没有支持，空间计算发现变化但变更记录没有登记，治理日志显示任务失败但结果被当成有效结论。

**边界提醒**：multi-subagent 是编排策略，有明确触发条件（子任务互相独立、每个任务需要 5 次以上的工具调用、并行后的效率能够显著优于串行）。结构化统计通常不需要拆，单 agent 生成 SQL / 脚本、执行并复核结果更可靠。任务边界没确认、子任务太小、结果无法按同一批对象交叉验证时，并行会增加噪声。

### 4. 领域执行能力

#### 文档检索：关键词检索、向量检索、hybrid recall、reranker 怎么取舍？什么叫证据召回和原文核验？

**对方可能在关心**：你是否理解 RAG 的失败模式，以及是否会把相关片段误当成可靠答案。

**先回应**：精确术语、编号、条款号优先关键词检索；口语化、同义表达多的问题优先向量检索；高风险结论前必须 hybrid，并回到原始文档核验。

**如果继续聊**：快速探索时可以先走单路检索。形成高风险结论前，要结合关键词和向量召回，再用 reranker 排序。原文核验要看前后文、适用范围、版本时间和例外条件，确认材料能直接支撑结论。

**边界提醒**：证据召回只是找到可能相关的材料，原文核验才是确认这段材料是否支撑结论。向量检索会返回 top-k，但 top-k 只是候选材料。

#### 结构化分析：SQL / 脚本怎么生成、执行、校验？如何防止模型改错统计口径？

**对方可能在关心**：统计类问题是否会被误路由到 RAG，以及模型生成 SQL 时怎么控制口径。

**先回应**：只要问题要求过滤、分组、聚合、排序或精确数字，就应该路由到 SQL / 脚本。进入结构化分析后，先把统计口径显式化，数字只允许来自运行结果。

**如果继续聊**：路由时会先判断用户要的是解释性材料还是计算结果。问"某制度怎么规定"可以走 RAG；问"某类治理任务有多少次、通过率是多少、失败原因怎么分布"就要走结构化分析。执行时先确定数据源、时间范围、过滤条件、分组字段、空值处理、去重规则和输出粒度。然后生成 SQL 或脚本，运行结果表，再基于结果做自然语言总结。口径、SQL / 脚本和结果要一起展示，方便复核。

**边界提醒**：用户口径和已有字段对不上时，先追问或标注假设。把结构化数据切块放进向量库，容易召回看起来相关的片段，却难以生成可重复计算的数字。

### 5. 质量评估与持续改进

#### 评估落地：评测集怎么构造？Agentic 阶段怎么做回归？

**对方可能在关心**：agent 的质量是否有工程评估方法，还是主要靠主观体验判断。

**先回应**：Agentic 阶段我会分两层评估：一层看结果是否正确，另一层看过程是否可靠。评测集来自专家标注、典型业务问题和线上失败 case。

**如果继续聊**：文档问答看证据召回、引用和原文支撑；结构化分析看统计口径、数据范围和结果；复杂判断看证据链是否完整；任务执行看路径、参数、工具结果和审批记录。统计类问题要保留口径、数据范围、SQL / 脚本和运行结果，让同一个问题在同一数据版本上能重新跑出同一组数字。

**边界提醒**：Agentic 回归要覆盖中间行为，包括路由、加载的 skill、工具调用、证据覆盖、参数留痕和高风险动作审批。政企场景里，路径合规和结果正确都要纳入通过标准。

#### 持续改进：trace、memory、skill、回归集之间是什么关系？

**对方可能在关心**：系统会不会随着使用变好，以及这种变好是否可控。

**先回应**：trace 和失败 case 是改进原料，memory、skill、回归集是不同沉淀位置。真正写入系统前需要人工审核。

**如果继续聊**：trace 会记录 query、路由结果、加载的 skill、工具调用、证据来源、最终答案和人工修正。稳定的客户术语、别名和口径可以写入 memory；稳定流程和异常处理可以进入 skill；典型失败进入回归集；涉及高风险动作的失败会进入 permission / hook 规则复查。

**边界提醒**：Memory 是运行时知识，skill 是执行方法，eval 是质量门。三者可以共享 trace 和失败 case，但职责不同，更新节奏也不同。

### 6. 风险治理与失败处理

#### Permission / Hook：高风险动作怎么管？审计记录怎么留？

**对方可能在关心**：安全边界是否落在执行层，以及出问题后能否追溯。

**先回应**：我会把高风险动作放到执行层治理。检索和只读查询可以自动执行，写库、删除、发布、批量更新这类动作要经过模拟执行、参数校验、人工审批和审计留痕。

**如果继续聊**：permission 和 hook 可以在工具真正执行前拦截请求，检查动作类型、目标对象、影响范围和参数格式。低风险动作直接放行，中高风险动作要求模拟执行或人工确认；涉及生产删除、越权访问、敏感字段明文导出、绕过审批执行变更这类硬边界的请求，直接拒绝。审计记录按 run_id 留痕，包括用户问题、加载的 skill、工具调用参数、证据版本、SQL / 脚本、模拟执行结果、审批记录和最终输出。

**边界提醒**：敏感字段要脱敏，工具结果可以存摘要或 hash。审计的目标是解释一次任务为什么这么做，并在事故复盘时回放关键路径。

#### 失败处理：工具失败、证据不足、数据缺失、结论缺少依据分别怎么处理？

**对方可能在关心**：系统失败时是否有可判别、可恢复、可拒答的机制。

**先回应**：我会先把失败分流：执行失败、证据不足、数据不可用、结论缺少依据。每一类都有不同处理路径。

**如果继续聊**：工具调用失败时，记录错误类型、参数和返回码；幂等读操作可以自动重试，写操作进入人工确认。证据不足时，说明缺了哪类证据，要求用户补充范围或明确拒答。数据缺失时，区分"确实没有记录""没有权限访问""字段或表不存在"。结论生成时必须绑定证据、SQL / 脚本结果或工具返回，依据不足就进入澄清或拒答流程。

**边界提醒**：失败处理的目标是让系统停在正确位置：能恢复的恢复，缺证据的追问，高风险的审批，依据不足的拒答。
