# ColaOS Agent QA 面试 Playbook

## 定位

## 核心主线

我不是传统测试候选人，也不是只会做 Agent demo 的研发。我更匹配的是 Agent 行为质量体系：定义什么样的 Agent 行为算靠谱、自然、符合设计意图，并把模糊体验问题转成质量标准、可复现场景、问题归因和回归闭环。

## 30 秒版本

我有 8 年研发和质量工程经验，之前在百度负责搜索架构质量和稳定性治理，后来在创业公司主导 Agentic AI 产品研发和交付。

我觉得自己匹配 Agent QA 的原因是，两段经历刚好能拼起来：百度经历让我熟悉线上质量治理、问题召回和反馈闭环；Agent 项目让我理解非确定性输出、上下文、工具调用、记忆和行为边界。

对我来说，Agent QA 不是点功能找 bug，而是判断 Agent 在当前上下文里的行为是否合理、自然、符合设计意图，并把这种判断沉淀成可复现、可归因、可回归的质量体系。

## 高频问题答法

### 1. 为什么从 Agent 研发看 Agent QA？

我不是想从研发退到测试，而是觉得 Agent QA 这个问题本身变重要了。Agent 从 demo 到可用系统，瓶颈不只是能不能跑起来，而是怎么定义好、怎么验证好、怎么持续变好。

尤其是 ColaOS 这种有记忆、人格和主动行为的 Agent，很多问题不是功能错，而是行为在当前上下文里不自然、不克制、不符合用户预期。这个岗位正好在 Agent 研发、产品体验和质量工程的交叉点上。

### 2. Agent QA 和传统 QA 的区别是什么？

传统 QA 更多面对确定性系统，核心是给定输入下输出是否符合预期。Agent QA 面对的是非确定性行为系统，核心是这个行为在当前上下文里是否合理，是否符合设计意图，是否能被用户信任。

差异主要在四点：输入包含历史、记忆和上下文；输出是一段行为，不只是一个结果；标准是连续质量谱，不是简单 pass/fail；归因可能来自 prompt、模型、记忆、工具、工程或产品设计。

### 3. 没有标准答案时怎么判断好坏？

先把“没有标准答案”拆成可判断维度。比如 ColaOS 可以看上下文理解、记忆引用、人格一致性、主动行为恰当性、情绪识别、边界感、是否知道停下来。

这和 `02_podinsight` 里处理观点型内容类似。观点没有唯一答案，但可以拆成主张、证据、边界条件和反例验证。Agent 行为也可以用类似方式拆出质量结构。

### 4. 如果你觉得“这里不对但说不清”，你会怎么处理？

我会先保留这个直觉，但不会停在直觉。

下一步是记录具体上下文：用户前面说了什么，Agent 记住了什么，它做了什么，哪里让我觉得不对。然后做对比：更合理的行为应该是什么。最后归类到主动时机、语气、人设、记忆、情绪、安全边界等维度，写成 case 进入场景库或回归集。

### 5. 怎么评估记忆一致性？

记忆一致性不只是记得准，还包括什么时候该用、用到什么程度、什么时候该更新或遗忘。

我会重点看：事实记忆是否准确，偏好记忆是否过度泛化，临时情绪是否被写成长期偏好，过时记忆是否还在影响行为，多个记忆冲突时是否能澄清。这里可以自然连接 `03_memory_architecture_interview_notes.md`。

### 6. 怎么评估人格稳定性？

人格稳定性不是每句话都一样，而是在不同场景下保持一致的价值取向、语气边界和关系距离。

我会定义几个不该漂移的维度：亲密度边界、表达风格、主动程度、对负面情绪的处理方式、对敏感问题的克制。然后用场景矩阵测普通聊天、压力状态、用户拒绝、长期未交互、记忆冲突和敏感话题。

### 7. 怎么评估主动行为是否恰当？

主动行为的关键不是越多越智能，而是触发时机、上下文依据和可打断性。

我会看四个问题：它为什么主动，是基于明确事件还是模型猜测；主动内容是否真的有帮助；用户拒绝后是否收敛；敏感场景下是否先确认再行动。没有边界的主动，很容易从贴心变成打扰。

### 8. 怎么区分 prompt、模型、工程和设计问题？

先复现问题，再看它是否稳定、是否跨模型存在、是否和上下文或记忆状态相关。

如果规则缺失时才错，更多是 prompt 或行为规范问题。如果日志显示记忆检索、状态更新或工具返回异常，是工程问题。如果 Agent 严格执行了规则但用户仍然感觉不对，可能是产品设计问题。若明确规则下仍反复失败，才更像模型能力边界。

### 9. 早期团队数据少，怎么搭 eval？

不用一开始就做重平台，但要从第一天建立轻量闭环。

先从人工 case 库开始：每次内部使用或小范围用户反馈里出现高价值问题，就记录上下文、预期行为、实际行为、归因和修复方式。按记忆、人格、主动、情绪、安全等维度归类，每周挑核心 case 回归。case 稳定后，再逐步加自动化 judge、日志指标和线上行为指标。

### 10. 怎么避免 QA 变成主观挑刺？

让每个主观判断尽量带上场景、对比和归因。

“我不喜欢这个回答”价值有限。“用户刚表达拒绝后，Agent 仍然继续追问，违反了拒绝后收敛的行为标准”就可以讨论、复现和修复。主观感受是入口，不是交付物。交付物应该是场景、标准、问题分类、优先级和回归 case。

## 可主动抛出的观点

### Agent QA 的核心资产不是测试用例，而是质量语言

测试用例只是把已经形成的判断编码下来。Agent 产品早期更关键的是建立团队共享的质量语言：什么叫记忆一致，什么叫人格漂移，什么叫主动越界，什么叫情绪误判。没有这套语言，讨论会停在“我觉得怪”和“我觉得还好”。

### Agent 质量要同时看结果和行为

普通问答系统经常只看答案是否正确。Agent 产品还要看它为什么这样回答，是否该回答，是否该追问，是否该主动，是否该拒绝。尤其是有记忆和人格的 Agent，过程本身会影响用户信任。

### 人格 Agent 的主要风险不是不够聪明，而是不知道边界

用户未必要求一个伴侣型 Agent 每次都给最聪明的答案，但会非常敏感于越界、误解、过度亲密、记忆错误和情绪处理不当。这里的质量标准要保护用户信任，而不是只优化回答丰富度。

## 反向面试问题

### 判断岗位是不是质量体系岗

- 这个岗位会参与产品设计阶段的质量标准讨论吗，还是主要在开发完成后验收？
- 这个角色的核心产出是什么：bug 数量，还是评测维度、场景矩阵、质量标准和回归机制？
- 如果 QA 发现问题根因在 prompt、memory、模型选择或产品设计上，是否有推动对应改动的空间？

### 判断团队有没有 Agent 质量意识

- 你们现在如何定义 Agent 的行为质量？比如记忆一致性、人格稳定性、主动行为恰当性。
- 现在是否有 trace、日志、用户反馈和失败 case 库？一次体验问题通常如何从发现进入修复和回归？
- 对于非确定性输出，你们更倾向人工 review、自动化 judge、线上行为指标，还是几种方式结合？

### 判断产品方向和边界

- ColaOS 希望用户把 Agent 当成什么关系：助手、伙伴、陪伴者，还是个人操作系统？
- 当前最大质量风险是什么：不够聪明、不够自然、记忆不稳定、主动行为不成熟，还是安全和隐私边界？
- 端上 Agent 在隐私、记忆和主动行为上会有很多边界问题。哪些行为是绝对禁止的？

### 判断个人发展空间

- 如果这个角色做得好，未来更接近质量负责人、Agent 产品负责人，还是测试团队负责人？
- 这个岗位在团队里的决策接口是什么？会和产品、模型、工程一起定义行为标准吗？

## 风险判断

### 1. QA title 可能对应测试执行岗

如果对方只谈 bug 数量、覆盖率、提测流程，不谈标准定义、trace、case、回归和产品设计参与，这个岗位对我的长期价值有限。

### 2. Taste 没有机制会变成主观争论

我感兴趣的是定义问题和定义好，但组织里需要 case、标准、评审和决策权来承载。没有机制，taste 会变成“谁声音大谁有理”。

### 3. ToC 伴侣型 Agent 和我过去经验不同

我的强项更偏工程质量、系统稳定性、政企 Agent 和知识工程。ColaOS 如果更偏 ToC 陪伴，需要更细腻的用户情绪、关系感和日常使用体感。面试里要承认差异，强调迁移能力，不要假装天然懂陪伴产品。

### 4. 早期团队可能低估验证成本

AI 降低的是生成成本，不等于降低验证成本。人格、记忆和主动行为的质量验证可能比普通功能更难。如果团队觉得“多测测就行”，要谨慎。

### 5. 不能只被岗位概念吸引

关键判断只有一个：这个岗位是否让我成为定义 Agent 行为质量的人，还是让我成为高频体验产品并提交问题的人。前者值得认真争取，后者要谨慎。

## 面试收束表达

我对这个岗位感兴趣，不是因为它叫 QA，而是因为 Agent QA 这个问题本身变重要了。

Cola 这种有记忆、人格和主动行为的 Agent，质量标准不能只靠传统功能测试，也不能只靠主观体验。它需要有人把“这个行为像不像靠谱伙伴”拆成具体维度，持续积累场景、trace、失败 case 和回归机制。

我的优势是两边都有经验：百度经历让我做过大规模系统质量治理，知道质量闭环怎么落地；现在的 Agent 项目让我理解上下文、工具、记忆、权限和行为可靠性。两个经验合在一起，我觉得可以比较好地承担这个角色。
