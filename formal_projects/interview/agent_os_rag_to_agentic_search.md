# Agent OS 项目经验底稿：从传统 RAG 到 Agentic Search + OpenCode Runtime

> 用途：面试时讲 Agent OS 项目经验的底稿。
> 讲述方式：正文按 STAR-L 结构组织；附录保留 RAG 和 OpenCode 的技术细节，方便被深挖时展开。
> 当前状态：聚合分析类 query 先用一个脱敏同构样例说明，面试前可替换成真实客户案例。

---

## 30 秒版本

这个项目最初是面向政企场景的知识库 RAG。早期先把事实性问答的召回做好，用混合检索、RRF 和 reranker 把命中率拉了大约 25%。后来发现客户问的不只是事实，还会问业务流程、要中间判断的复杂问题、基于业务记录的聚合分析。为了补程序性知识，先做了固定的 workflow 和状态机编排；为了让流程能动态走，又试着自己封装 agent loop，在 context 管理、状态管理、可观测性这三件事上耗了很多时间。最后迁到 OpenCode 这类通用 coding agent runtime，把 runtime 这一层交出去，主线收敛到检索路由、结果契约和 skill 沉淀，Agentic Search 的架构才稳下来。

这条线最后留下三句判断。

1. 知识形态决定检索范式。
2. runtime 这一层值得交给生态，应用层应该把精力放到契约层。
3. 选 agent 的主干工具，关键不在能力强不强，而在失败时 agent 知不知道自己失败了。

---

## 一、背景与定位（Situation）

Agent OS 要应付的场景比较杂，表面上用户都在"提问"，进到系统里其实是三类不太一样的活。

1. 事实性问答，比如制度、定义、参数、规范。一次检索基本能答。
2. 程序性查询，处理逻辑明确但要多步执行。这一类里又分两种子形态：一种是业务流程类，比如某个流程怎么走、下一步该调什么工具；另一种是结构化数据分析，比如从任务记录、台账、提交记录里做时间过滤、分组聚合、排序对比。它们共同的特点是查询逻辑可以被显式定义出来，区别只是执行手段一个偏工具编排、一个偏代码或 SQL。
3. 判断性问题，比如方案比选、异常诊断、要中间判断的复杂问答。这类问题最难，难在完整的"对"很难定义清楚，很多关键依据藏在专家的隐性经验里，不容易显式收集。

项目里难的不是把单个 RAG 调得更准，而是先看清楚这条 query 属于哪一类，再决定走哪种检索和执行的路径。

放到面试里讲，这个项目最值得说的也不是"会用混合检索"，而是从传统 RAG，到固定 workflow，到自研 agent runtime，再到 Agentic Search + OpenCode runtime 这条演进路线，以及每次切架构时的触发条件和判断依据。

## 二、三阶段架构演进（Task + Action）

### 2.1 第一阶段：传统 RAG + 固定 workflow 编排

最早的目标比较朴素，先把知识问答做起来。当时模型的 agentic 能力还比较弱，成熟的 agent 框架也基本没有，LangChain、AutoGPT 看着热闹，离生产级稳定差得远。这个阶段的设计思路就两条。

1. 事实性的问题先交给传统 RAG。
2. 程序性的问题先交给固定 workflow。

理由很直接：当时的模型不适合扛动态编排，硬让它自己决定全流程，跑起来不稳。与其让模型自由发挥，不如把确定的部分写死，模型只在语义层面做它擅长的事。

这个阶段有两个关键决策。

**决策 1：事实性问答先把召回做对，再去调 prompt。**

这条线最核心的判断就一句话：召回是上限。具体做法是把单通道的稠密检索升级成混合召回，BM25 + dense 两路召回，再用 RRF 融合，最后把候选交给 reranker 精排。[详见附录 A.1、A.5]

配套还做了三件事：分块不再死守教程默认值，按语义边界切，块大小当成可调参数[详见附录 A.2]；向量相似度用 cosine 或者显式做 L2 归一化，避免长文档系统性占优[详见附录 A.3]；query 改写时一定保留原始 query 做锚，避免越改越偏[详见附录 A.6]。

这条线的直接产出，就是简历里那条可以量化的数字：**知识库问答命中率提升约 25%。**

**决策 2：程序性知识不上动态 agent，先用固定 workflow 顶住。**

当时面对的一类真实场景是这样：用户有一套遥感影像的数据治理流程，已经配好了各种原子化的治理工具。要让这套流程稳定跑下来，靠的不是让模型自己想办法，而是人先把任务节点、工具调用和约束条件编排好。模型在每个节点上只做两件事：语义判别、参数提取。

这套 workflow 的实现就是写状态机。土归土，但放在当时是合理的：目标定义得再清楚，模型的指令遵循和 agentic 能力跟不上，单靠模型也跑不下来整套流程。

到这一步，系统已经能覆盖事实性问题和一部分程序性问题。但问题也很快暴露：workflow 死板，新增一类流程就要新写一套编排；它适合路径已知的任务，遇到中间要动态判断、动态补检索、动态选工具的场景就不行。一旦 query 形态从"按固定流程走"变成"先看情况再决定下一步"，这套架构就开始失效。这就是切到第二阶段的触发条件：问题类型已经超出了单轮检索 + 固定流程能覆盖的范围。

### 2.2 第二阶段：手搓 agent runtime + Agentic Search

走到第二阶段的直接动机，是想让流程能动态走。不再满足于人提前编排好，而是希望 agent 能根据 query 和中间结果，自己决定下一步去检索什么、调什么工具、要不要补 context、要不要换路径。这一步本质上就是从固定 workflow 走向 Agentic Search。

为了做到这一步，当时尝试过自己在模型调用层之上封装一套 agent loop。模型调用走的是开源的聚合网关（new-api 这类项目），所以工具调用的协议适配不是主要矛盾；真正费时间的是 runtime 这一层那些看起来不起眼、做起来极脏的工程问题。最大的三件事是：context 窗口管理、状态管理、可观测性。

**坑 1：context 窗口管理远比看起来复杂。**

agent 一旦能动态编排，context 里堆的就不只是用户问题加几段检索结果，还会塞进工具描述、前几轮的中间结果、失败重试信息、压缩摘要、已执行动作、待执行动作。麻烦也就来了：工具多了，哪些描述必须留在 context、哪些可以外置；窗口快满了，怎么压缩才不丢掉后续推理依赖的信息；压缩摘要要是把关键决策依据抹掉，后面 agent 会在错误前提上继续往下推。这事听起来像"做个 summary 就完了"，做起来全是工程细节，而且高度依赖模型的实际行为。

**坑 2：状态管理得自己设计。**

从固定 workflow 切到 agent loop 之后，原本显式写在状态机里的东西都要重新定义：当前轮的 agent 处在规划中、执行中、等结果、需要重试还是可以收敛输出；中间失败了怎么恢复，哪些状态保留、哪些状态回滚；多步任务里什么时候算这一轮结束、什么时候继续迭代。这些东西不明确，agent loop 看起来在跑，实际可能只是围着一个不清晰的状态机打转。

**坑 3：可观测性主要靠手动加日志，效率很低。**

自研 runtime 的时候，排查问题往往只能靠手动加日志，看每一步的 prompt、工具的输入输出、压缩结果、状态跳转。能调，但体验很差，迭代慢。很多时候时间花在"系统怎么又这样了"，而不是"业务效果怎么往上推"。

**这一阶段最重要的认知**

不是 agentic 多酷，而是 runtime 这一层最容易把工程投入吸进去，而且它跟具体业务逻辑没什么关系。自己手搓 runtime，本质上还是用大量过程控制去换确定性。context 怎么压、状态怎么转、失败怎么恢复、日志怎么埋，这些都不是业务，但会消耗掉大量时间。问题已经不是"模型够不够聪明"，而是"这套 agent loop 在工程上托不托得住"。

这一步同时验证了两件事。一，Agentic Search 对复杂 query 是有价值的，不是概念噱头。二，自研 runtime 投入产出比不行，尤其在模型能力和生态都在快速变化的时候。于是第二次切架构来了：不是放弃 Agentic，而是放弃自己造 runtime 这个轮子。

### 2.3 第三阶段：基于 OpenCode 的 runtime + Agentic Search

第三阶段的逻辑跟前一次切换不一样。第一次切换是因为问题类型变了，第二次切换是因为成本结构变了。

随着 Claude Code、OpenCode、Codex 这类通用 coding agent 成熟，行业里出现一个挺清楚的趋势：runtime 这一层正在收成一个可以复用的标准能力。

最关键的转变不是换了一个工具，而是分工变了。模型层管选哪个模型、哪个 provider；协议层管怎么调模型 API、怎么接工具；runtime 层管 agent loop、context 管理、工具调用、文件系统、子 agent、权限边界；契约层管什么叫做对、怎么验证、什么时候重试、什么时候换人来接。

前两个阶段，runtime 这一层的复杂度其实是应用层在背。第三阶段的核心决策，是把 runtime 这一层更多交给 OpenCode 这类通用 runtime，重心挪到契约层和领域能力沉淀上。

**为什么最后选 OpenCode 这条路**

OpenCode 对这个项目最大的价值不在某个单点功能，而是它把几件原本要自己做的脏活一起接过去了。

1. 一套稳的 agent loop。Agent 能执行、能看到结果、能纠错，而不是一次 API 调用吐完就结束。
2. Bash 当原子能力。原本要在 workflow 里特殊处理的事情，现在直接让 agent 写脚本、跑脚本、看结果。
3. 文件系统当状态载体。文件是看得见的状态，agent 可以反复读、改、验证，天然适合做闭环。
4. Skill 渐进加载。可以把高成功率的路径、领域 SOP、确定性的工具封装成 skill，不用每个 session 都从零试。

这几件加在一起，相当于帮系统把 context 工程和 runtime 这一层的复杂度消化掉了。第三阶段带来的不是多了几个工具，而是整体工程复杂度下来了，Agentic Search 才开始稳定可用。

**但要诚实讲，第二阶段的三个坑并没有被同等程度地解决。**

按照实际落地后的体感，三件事的解决程度差别很大。

1. **context 管理：基本解决。** OpenCode 把 context 拆成"工作 context + 外置文件状态"，bash 输出可以选择性回写，子 agent 跑完只回传摘要。再配合 `experimental.session.compacting` hook 自定义压缩时哪些信息必须保留，第二阶段那个"压缩摘要把关键决策依据抹掉"的具体坑就被堵住了。
2. **状态管理：runtime 内的 session 状态解决了，工具侧的失败回滚是开放问题，必须靠工具自己的设计来兜底。** session 历史、消息流、todo、文件读写、permission 状态，OpenCode 都管。但 agent 调一个有副作用的工具失败了怎么回滚，任何 runtime 都不管，业内（Microsoft Agent Framework、LangGraph 都一样）都是开放问题。落到工程上，能给工具加的约束有两层：第一层是单工具内部要么可逆要么幂等——可逆是说一次做完，失败自动回到原样；幂等是说同一个调用重试多次结果一样，避免 agent 不知道上次有没有成功就盲目重试出脏数据。第二层是跨多个工具的业务操作要给每一步配一个反操作，失败时按倒序撤销，工程上有成熟方案（saga 模式），但落到 agent 场景属于开放问题，业内还在探索。如果做不到这两层，最稳妥的兜底是用 `tool.execute.before` hook 在关键操作前拦下来人工审批或外部系统校验。要强调的是这些都是工具层和契约层的责任，runtime 帮不上忙。
3. **可观测性：开箱够用，工业级靠生态。** OpenCode 自带结构化日志（`client.app.log()` 分级输出），看每步发生了什么够用，但没有 LangSmith 那种 trace tree、token cost、replay 的成品。需要的话靠 plugin 补：`opencode-otel` 把 session/message/tool call 导成 OpenTelemetry，能接 Jaeger / Tempo / Honeycomb 任意 OTLP 后端；`opencode-plugin-langfuse` 直接接 Langfuse，体验最接近 LangSmith。官方在跟进 native OTLP export，issue 编号 14697。

也就是说，第三阶段更准确的说法不是"三个坑都解决了"，而是 context 这条线 runtime 直接收掉，可观测性靠生态补齐，状态管理则是把"runtime 该管的"和"工具/契约层该管的"明确切开。这个切分本身就是阶段三最重要的认知收获。

到了这一步，项目重点不再是堆 workflow，也不再是打磨自己的 runtime，而是收成三件事：先看 query 属于哪种知识形态；为这类 query 选对检索和执行路径；把结果对不对的标准写清楚，再用 skill 和验证逻辑把它固定下来。

放到面试里讲，第三阶段是这个项目的承重点。它体现的不只是一个系统做出来了，更重要的是知道哪些东西该自己做、哪些东西该站在生态上复用。

## 三、当前架构深度展开（Result）

### 3.1 路由原则：知识形态决定检索范式

走完三阶段以后，整个系统最重要的路由判断收成了一张表。

| 知识类型 | 典型 query | 当前主路径 | 为什么 |
|---|---|---|---|
| 事实性 | 制度、定义、参数、规范 | 混合 RAG | 这是召回和排序的问题 |
| 程序性 - 业务流程 | 某类业务流程怎么走 | 固定 workflow 或浅层 Agentic | 路径已知，适合保留确定性骨架 |
| 程序性 - 结构化分析 | 时间过滤、分组聚合、排序对比 | 代码 / SQL 执行 + 汇总 | 逻辑明确，但要走计算而不是检索 |
| 判断性 | 方案比选、异常诊断、要中间判断 | Agentic Search | 要多步检索 + 中间判断，正确标准本身需要在过程中逐步逼近 |

这张表的意义在于，把"要不要上 Agentic"从抽象讨论变成了明确的路由规则。系统不会所有 query 都往 Agentic 推，也不会所有 query 都塞进 RAG。成熟的标志是：知道什么时候该保住确定性，什么时候该把控制权交给 agent。

### 3.2 Agentic Search 的具体形态

当前架构里，Agentic Search 主要处理两类场景：程序性里的结构化分析子型，以及判断性问题。两者都需要多步执行，区别在于前者逻辑明确、后者标准模糊。

先说前一类。用一个脱敏的同构例子。系统里有一份任务执行记录表，用户会问类似下面这些问题。

1. "找出所有最后一次成功执行使用了某类治理策略的任务，并按策略归类。"
2. "最近一周主要在处理什么类型的任务？"
3. "哪类任务执行次数最多且一次通过率最低？"

这类 query 看着是问答，骨子里是 group by、时间过滤、排序、多指标联合比较。如果把这种数据切块灌进向量库再让 RAG 去答，最多召回一些"看起来相关"的片段，没法给出精确的统计结果。这跟调分块、调 reranker、调 prompt 没关系，因为问题本身不是"找相似文本"，而是"在数据上做计算"。

正确的路径是：agent 先识别这不是普通问答而是结构化分析；读入全量数据或相关子集；动态生成 Python / SQL / shell 脚本做精确统计；再基于统计结果输出自然语言总结。

这里有一个反常识但面试里很加分的点：context 窗口装得下的时候，RAG 反而可能是负优化。因为这时本可以直接对原始数据做精确分析，RAG 却把数据切碎，把问题降级成"相似片段拼接"，精度天然更差。

判断性问题走的是同一套 Agentic Search 框架，但难度更高，因为正确标准本身就要在过程里逐步逼近。比如一个异常诊断，不会是检索一次就答，而是先检索相关规则和历史案例；根据中间结果判断当前更像哪种异常；再去补检索缺的那部分证据；最后收成答案或下一步建议。这时候 LLM 不再是生成器，而是检索规划器，要决定搜什么、搜几次、每次用什么工具、结果够不够回答问题。这一类问题的天花板不在工程，而在能不能把领域专家的隐性经验显式化下来。

### 3.3 工具选择的底层逻辑：失败模式决定 agent 友好度

走到 Agentic Search 阶段，工具的价值不只是"能不能查到"，还要看"查不到的时候 agent 知不知道自己没查到"。

| 工具 | 失败模式 | 对 agent 友好度 |
|---|---|---|
| grep / ripgrep | 返回 0 行，明确无结果 | 高 |
| SQL | 语法报错或返回空表，明确 | 高 |
| 向量检索 | 永远返回 top-k，哪怕全不相关 | 低 |
| 直接读文件 | 装得下就准，装不下会静默退化 | 中 |

这张表背后的判断是：选 agent 的主干工具，关键不在能力强不强，而在失败模式可不可判别。

这也是为什么 coding agent 的搜索主干往往是 grep 而不是向量检索。grep 没结果，agent 立刻知道要换关键词、换范围、换工具；向量检索就算没找到答案，也会返回一堆"看起来像结果"的东西，agent 反而不知道自己其实没找到。

这条判断放到业务场景同样成立。结构化分析类问题用 SQL 和脚本比用向量检索更合适，不是因为它们更"聪明"，而是因为结果边界更清楚。

### 3.4 OpenCode 作为 runtime 带来的工作方式变化

迁到 OpenCode 之后，架构上一个核心变化是：开始更明确地分清楚"什么是 runtime 管的、什么是应用层管的"。

| 层 | 关注点 | 当前分工 |
|---|---|---|
| 模型层 | 选哪个模型、推理强度多少 | 按任务特征选模型 |
| 协议层 | 怎么调模型和工具 | 尽量靠现成生态 |
| runtime 层 | agent loop、context、文件、工具、子 agent | 主要复用 OpenCode |
| 契约层 | 什么叫结果对、怎么验证 | 重点自己做 |

迁完之后，主要精力不再放在"怎么把 agent loop 写稳"，而是放在两件更靠近业务价值的事情上：把"结果对"这件事的标准定下来；把高成功率的路径沉淀成 skill 和确定性工具。

这背后对应一种工作方式的变化：从更看重过程确定性，转向更看重结果确定性。以前自己写 runtime 的时候，本能反应是把每一步怎么做都规定死，靠过程控制换稳定。迁到 OpenCode 之后，更合理的方式变成不强规定每一步走哪条路，但把最终产物长什么样定清楚，再给 agent 留下能自己看结果、自己改的验证手段。

这也是为什么 OpenCode 的文件系统和 Bash 能力很关键。文件是看得见的状态，脚本是可验证的动作，agent loop 才能真正闭环。[详见附录 B.1]

### 3.5 用 skill 收敛模型路径差异

进入 OpenCode 阶段后有一个挺直观的观察：同一个复杂 query，换不同的模型去跑，最终答案可能差不多，但中间路径差很多。

常见的差异：有的模型先写代码做精确统计再总结；有的模型读完数据直接开始自然语言推理；有的模型对一个本来单 agent 能搞定的任务过度派发子 agent；有的模型会自作主张改统计口径，比如把"最近一周"理解成自然周或滚动 7 天。

没有约束的话，这种路径差异在生产环境里就会变成输出口径不一致。

这就是 skill 在当前架构里的角色：不是给 agent 多塞几句 prompt，而是把高成功率的路径沉淀成可复用的工作文档和确定性工具，把模型默认的路径偏好往一处收。

当前已经识别出三条特别值得封装的 skill 规则。

1. 结构化数据分析类 query 必须先做精确统计再总结，不允许 agent 看一眼数据就下结论。
2. 单文件而且 context 窗口装得下的时候，不要为了并行而并行，避免无意义地派发子 agent，把 token 成本和整合复杂度抬上去。
3. 输出口径必须固定下来。时间范围怎么算、分类标签用哪一套、统计口径怎么定义，都写进 skill 或契约层，不让模型临场决定。

往上抽象一层，skill 解决的问题是把"每次都重新试错"变成"复用已经验证过的成功路径"。这既是模型路径一致性的问题，也是结果确定性的问题。[详见附录 B.2]

### 3.6 多 agent 编排：task tool 和手工 spawn 的取舍

这部分算高级话题，面试官如果继续往下挖可以展开。

OpenCode 体系里子 agent 编排大致两种方式。task tool 是在同一个 session 内让主 agent 派发子 agent；手工 spawn 是在 OpenCode 外面自己写编排器，起多个独立 session 去跑。

选哪个不是看谁更高级，而是看任务长什么样。

| 场景 | 推荐模式 |
|---|---|
| 单任务内能拆 2-3 个足够重的子任务 | task tool |
| 跨模型对比或大规模批量跑任务 | 手工 spawn |
| 需要细粒度控制超时、重试、并发 | 手工 spawn |
| 单文件或小范围任务 | 不并行，主 agent 自己做 |

当前这条项目线里，大多数聚合分析类 query 都属于最后一种：一个主 agent 直接读数据、写脚本、跑验证、汇总结果就够了。这种场景更需要的是明确的 skill 约束，防止模型为了显得更 agentic 而过度并行。

## 四、结果与复盘（Result + Learning）

### 4.1 可讲结果

这个项目对外能稳定讲的东西分三层。

1. 量化结果。传统 RAG 阶段用混合检索、RRF 和 reranker，把知识库问答命中率拉了大约 25%。
2. 能力边界扩展。系统从只能处理事实性问答，逐步覆盖到程序性查询（包括业务流程编排和结构化数据分析），以及要中间判断的判断性问题。
3. 架构判断力上的成熟。从倾向自己造轮子，到知道哪一层该交出去、哪一层是自己要守的。这条线上最能迁移的能力就是这个。

如果面试官更关心"这个项目难在哪"，建议讲第三层。前两层不少团队都能做出一部分，第三层才更体现对 agent 系统工程边界的理解。

### 4.2 这条项目线最后留下的 6 个判断

1. 召回是上限。事实性问答先把召回做对，再谈排序和生成。
2. 知识形态决定检索范式。事实性、程序性、判断性三类，不该用同一套方法硬打；程序性内部还要再分流程编排和结构化分析。
3. 固定 workflow 不是落后，而是模型能力不够时保留确定性的合理手段。
4. 自研 runtime 的成本不在功能开发，而在 context 工程、状态管理和可观测性。
5. runtime 这一层值得交出去。应用层应该把更多精力放在契约层、skill 和业务结果定义上。
6. 选 agent 的主干工具，关键不在能力强不强，而在失败模式可不可判别。

如果要把这条项目线压成一句最像"面试答案"的话，可以这么说。

> 这个项目让我从"怎么把 RAG 调得更准"，走到"怎么给不同类型的 query 选对范式"，再走到"什么该自己做、什么该复用成熟 runtime"。分水岭不在模型层，而在 runtime 层和契约层。

## 附录 A：传统 RAG 调优技术速查

这一部分不是正文主线，而是被深挖时拿来展开的“技术弹药”。正文讲到事实性问答的优化时，可以按需引用。

### A.1 Hybrid Recall + RRF：为什么先做 BM25 + dense

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：Dense 单通道在专有名词、产品编号、错误码这类 query 上天然会塌，必须补一路稀疏检索。BM25 + dense 做 hybrid，是 ROI 最高的一步。

**为什么**：embedding 模型会把精确 token 泛化成语义类别，字面精度丢失。BM25 在精确 token 匹配上是天然强项，两路刚好互补。

**为什么用 RRF 融合**：BM25 分数和 cosine 分数量纲不可比，直接做归一化加权不稳。RRF 用 rank 不用 score，绕开量纲问题，简单但稳定。

**面试一句话**：在 RAG 里，hybrid 不是锦上添花，而是 dense retrieval 结构性弱点的补丁。

### A.2 Chunking：为什么把 chunk size 当变量调

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：chunk size 不应固化成 512 token 这种教程默认值，而应该按 query 类型和语义边界调。

**为什么**：事实性问题适合短 chunk，信号纯；主题性问题适合长 chunk，需要更多 context。固定 token 切分还容易把完整语义单元截断。

**实际策略**：按标题、段落、列表、代码块等语义边界切；默认值更倾向 200-300 token；长文档场景上 hierarchical retrieval。

**面试一句话**：512 token 是教程默认值，不是最优值。chunking 应该是变量，不是常数。

### A.3 向量相似度：为什么默认选 cosine

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：cosine similarity 默认比 dot product 更稳，因为它消除了向量长度对分数的系统性影响。

**为什么**：语料同时包含短 FAQ 和长手册时，长文档 embedding 范数天然更大，dot product 会偏向长文档。cosine 或显式做 L2 归一化可以消除这个偏差。

**面试一句话**：dot product 的问题不是偶发误差，而是分布偏置，所以值得在上线前主动校验。

### A.4 HNSW：为什么 `ef_search` 值得调高

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：在 LLM pipeline 里，HNSW 的 `ef_search` 往往可以放心调高，因为检索延迟不是整体瓶颈。

**为什么**：检索阶段多花几毫秒到几十毫秒，后面 reranker 和 LLM 本来就是更大的延迟头。对用户体感几乎无差，但能换来更高召回。

**面试一句话**：HNSW 的 `ef_search` 是典型的“用一点点延迟换稳定召回”的单边收益参数。

### A.5 Reranker：为什么说它是放大器，不是召回器

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：reranker 的作用是在候选池里做精排，前提是候选池里已经有相关文档。第一阶段没捞回来，第二阶段救不回来。

**为什么**：两阶段排序的上限由召回质量决定。很多团队喜欢先调 reranker，是优先级倒了。

**实践原则**：召回阶段先做多通道和合理的 top-k；reranker 至少做一次领域评测，不要直接套用通用网页搜索上的默认模型。

**面试一句话**：reranker 只能把相关文档排前面，不能把没召回的文档凭空变出来。

### A.6 Query Rewriting：为什么要保留原始 query

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：query rewriting 的价值是补 vocabulary gap，但必须保留原始 query 做 fallback。

**为什么**：LLM 改写的核心风险是 query drift。一旦改写偏了，整个检索会越走越偏。最稳妥的方法是原始 query 和改写 query 同时检索，再合并去重。

**面试一句话**：LLM query rewriting 很强，但它继承了传统 relevance feedback 的老问题，不能把原始 query 扔掉。

### A.7 如果面试官往 IR 深挖，可以主动抛的 3 句

1. **“RRF 的核心不是公式有多复杂，而是它用 rank 绕开了多路分数量纲不可比的问题。”**
2. **“chunking 真正该问的是 query 形态，不是教程里写了 256 还是 512。”**
3. **“RAG 的大部分核心技术，在 IR 里其实早就有对应经验，真正的新东西是把这套能力压缩到了普通 Python 开发者也能快速搭起来的程度。”**

## 附录 B：基于 OpenCode 做 runtime 的工程细节

这部分是正文里"为什么迁移到 OpenCode"和"工作方式变化"两段的工程展开。面试官如果继续往"怎么真正接进系统"里问，可以从这里抽素材。正文已经覆盖了四层结构、四个核心能力、task tool 与手工 spawn 的取舍，附录不再重复，只补两块正文放不下的内容：生产级接入细节，以及契约层应该怎么定义。

### B.1 把 OpenCode 真接进系统时，几个细节不能忽略

1. **文件响应模式比管道模式稳。** 把输入和输出都显式落文件，agent 的心智模型更稳定，也便于审计和重试。
2. **工作目录要设计清楚。** 这类 runtime 往往对可访问路径有明确边界，临时文件、prompt 文件、输出文件最好都放在项目工作目录下。
3. **stdout 要有兜底。** 即使已经要求 agent 把结果写入文件，也要准备从 stdout 提取结构化输出的 fallback。
4. **并发能力不要想当然。** 一个 runtime 能不能稳定吃多并发，除了自己这层，还取决于底层模型 provider 的 rate limit。
5. **权限边界是工程问题，不是 prompt 问题。** 能限制的工具尽量限制，必要时配合 sandbox 和 allowed tools。

这些细节平时看起来琐碎，但真正决定了"能 demo"还是"能生产"。

### B.2 结果确定性：契约层应该怎么定义

迁移到 OpenCode 之后，应用层最应该投入的不是再去规定 agent 每一步怎么做，而是把结果契约写清楚。最少要明确四件事：什么叫做完、什么叫做对、怎么验证它做对了、验证失败后怎么办。

放到当前项目里，契约层至少应该包含：输出 schema 或固定结构；时间范围、分类体系、统计口径等显式定义；对关键结果的验证脚本或可复算逻辑；何时重试、何时人工接管的规则。

也正因为如此，skill 不是孤立存在的。它和契约层是一体两面：契约层定义"什么是对的"，skill 定义"多数情况下怎么更容易做到对"。
