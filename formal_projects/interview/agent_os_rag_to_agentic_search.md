# Agent OS 项目经验底稿：从传统 RAG 到 Agentic Search + OpenCode Runtime

> 用途：面试底稿，便于临场翻阅与被追问时定位细节。
> 结构：卡片式组织，每张卡片含一个判断 + 关键支撑。附录保留可深挖的技术细节。
> 待办：聚合分析样例当前是脱敏同构版本，面试前替换成真实客户案例。

---

## 30 秒版本

**项目主线**：政企场景知识库 RAG → 程序性问题逼出固定 workflow → 复杂判断逼出自研 agent runtime → 工程复杂度逼出迁移 OpenCode。

**演进结果**：把 runtime 这一层交给生态，主线收敛到检索路由、结果契约、skill 沉淀，Agentic Search 才稳下来。

**三句留底的判断**：

1. **知识形态决定检索范式**。
2. **runtime 值得交给生态**，应用层精力放到契约层。
3. **选 agent 主干工具，看失败模式可不可判别**，不看能力强不强。

---

## 一、背景与定位（Situation）

### 1.1 系统要应付的不是一种"提问"，是三类活

| 类型 | 典型 query | 难点本质 |
|---|---|---|
| **事实性** | 制度、定义、参数、规范 | 一次检索能答，本质是召回和排序问题 |
| **程序性** | ① 业务流程怎么走、调什么工具<br>② 结构化数据上做过滤/聚合/排序 | 处理逻辑可显式定义，但要多步执行 |
| **判断性** | 方案比选、异常诊断、复杂条件推理 | "对"很难定义清楚，关键依据藏在专家的隐性经验里 |

> 程序性的两个子形态共享同一性质：查询逻辑可显式写出来。区别只是执行手段——一个偏工具编排，一个偏代码或 SQL。

### 1.2 项目真正难的地方

不是把单个 RAG 调得更准，而是**先看清这条 query 属于哪一类，再选检索和执行的路径**。

### 1.3 面试讲的重点

不是"会用混合检索"，而是这条演进路线本身：**传统 RAG → 固定 workflow → 自研 agent runtime → Agentic Search + OpenCode runtime**，以及每次切架构的触发条件和判断依据。

---

## 二、三阶段架构演进（Task + Action）

### 2.1 第一阶段：传统 RAG + 固定 workflow

**背景**：模型 agentic 能力弱，没有成熟 agent 框架，LangChain / AutoGPT 离生产级稳定差得远。

**设计思路**：把确定的部分写死，模型只在语义层面做擅长的事。事实性问题走传统 RAG，程序性问题走固定 workflow。

#### 决策一：召回是上限，先做对召回再调 prompt

**核心动作**：单通道 dense 升级成混合召回。BM25 + dense 双路检索 → RRF 融合 → reranker 精排。[详见附录 A.1、A.5]

**配套三件事**：

- **分块按语义边界切**，块大小当成可调参数，不死守 512 token。[A.2]
- **向量相似度用 cosine 或显式 L2 归一化**，避免长文档系统性占优。[A.3]
- **query 改写保留原始 query 做锚**，避免越改越偏。[A.6]

**直接产出**：知识库问答命中率提升约 25%（简历可量化数字）。

#### 决策二：程序性知识不上动态 agent，先用固定 workflow 顶住

**真实场景**：用户的遥感影像数据治理流程，已配齐原子化治理工具。

**做法**：人先把任务节点、工具调用、约束条件编排好，模型在每个节点只做语义判别 + 参数提取。实现就是状态机。

**为什么这样合理**：模型指令遵循和 agentic 能力跟不上，单靠模型跑不下来整套流程。土，但合理。

#### 切到第二阶段的触发条件

workflow 死板，新增流程就要新写编排。一旦 query 形态从"按固定流程走"变成"先看情况再决定下一步"，这套架构就失效。

---

### 2.2 第二阶段：手搓 agent runtime + Agentic Search

**直接动机**：让流程能动态走。agent 根据 query 和中间结果，自己决定下一步检索什么、调什么工具、要不要补 context。

**协议层不是矛盾**：模型调用走开源聚合网关（new-api 这类），工具调用协议适配不是主要问题。

**真正吞时间的是 runtime 三件事**：context 窗口管理、状态管理、可观测性。

#### 坑一：context 窗口管理远比看起来复杂

context 里堆的不只是问题加检索结果，还有：工具描述、中间结果、失败重试、压缩摘要、已执行/待执行动作。

随之的问题：

- 工具一多，哪些描述必须留、哪些可以外置
- 窗口快满，怎么压缩才不丢推理依赖的信息
- 压缩摘要抹掉关键决策依据 → agent 在错误前提上继续推

> 听起来像"做个 summary"，做起来全是工程细节，且高度依赖模型实际行为。

#### 坑二：状态管理得自己设计

原本显式写在状态机里的东西，全要重新定义：

- 当前轮 agent 处在规划/执行/等结果/重试/收敛输出
- 中间失败怎么恢复，哪些状态保留、哪些回滚
- 多步任务什么时候算这一轮结束、什么时候继续迭代

> 这些不明确，agent loop 看起来在跑，实际可能只是围着不清晰的状态机打转。

#### 坑三：可观测性主要靠手动加日志，效率很低

排查问题只能手动埋日志看每步 prompt、工具 IO、压缩结果、状态跳转。能调，但体验差，迭代慢。

> 时间花在"系统怎么又这样了"，不是"业务效果怎么往上推"。

#### 这一阶段最重要的认知

**runtime 这一层最容易把工程投入吸进去，且跟具体业务逻辑没关系。** 自己手搓 runtime，本质是用大量过程控制换确定性。问题不再是"模型够不够聪明"，而是"这套 agent loop 在工程上托不托得住"。

#### 切到第三阶段的触发条件

两件事同时成立：Agentic Search 对复杂 query 确实有价值，但自研 runtime 的投入产出比不行——尤其在模型能力和生态都在快速变化的时候。

> 不是放弃 Agentic，而是放弃自己造 runtime 这个轮子。

---

### 2.3 第三阶段：基于 OpenCode 的 runtime + Agentic Search

**触发逻辑**：第一次切换是问题类型变了，第二次切换是成本结构变了。Claude Code、OpenCode、Codex 等通用 coding agent 成熟，runtime 正在收成可复用的标准能力。

#### 关键转变：分工变了

| 层 | 关注点 | 当前分工 |
|---|---|---|
| 模型层 | 选哪个模型、哪个 provider | 按任务特征选 |
| 协议层 | 怎么调模型 API、怎么接工具 | 靠现成生态 |
| runtime 层 | agent loop / context / 文件 / 工具 / 子 agent / 权限 | 复用 OpenCode |
| 契约层 | 什么叫做对、怎么验证、何时重试、何时人接 | 自己重点做 |

> 前两个阶段，runtime 的复杂度其实是应用层在背。第三阶段把它交出去，重心挪到契约层和领域能力沉淀。

#### OpenCode 的四件价值，正好对应自研痛点

1. **稳的 agent loop**：能执行、能看结果、能纠错，不是一次 API 调用吐完就完事。
2. **Bash 当原子能力**：原本要在 workflow 里特殊处理的事，直接让 agent 写脚本、跑脚本、看结果。
3. **文件系统当状态载体**：文件是看得见的状态，agent 可以反复读、改、验证，天然适合闭环。
4. **Skill 渐进加载**：高成功率路径、领域 SOP、确定性工具封装成 skill，不用每次从零试。

#### 但要诚实讲：第二阶段三个坑没被同等程度解决

**context 管理：基本解决。** runtime 把 context 拆成"工作 context + 外置文件状态"，bash 输出可选择性回写，子 agent 跑完只回传摘要。配合 `experimental.session.compacting` hook 自定义压缩逻辑，"压缩抹掉关键决策依据"那个具体坑被堵住。

**状态管理：runtime 内的 session 状态解决了，工具侧失败回滚必须靠工具自己设计来兜底。**

| 谁负责 | 解决程度 |
|---|---|
| **runtime 内**：session 历史、消息流、todo、文件读写、permission | OpenCode 全管 |
| **工具侧**：有副作用工具失败了怎么回滚 | 任何 runtime 都不管，业内（MS Agent Framework、LangGraph）都是开放问题 |

工程上能给工具加的约束有两层：

- **第一层（单工具）**：至少幂等，最好同时可逆。**幂等是底线**——同一调用重试多次结果一样，避免 agent 不知道上次成没成就盲目重试出脏数据；**可逆是加分项**——一次做完，失败自动回到原样。两者不冲突，能叠加。
- **第二层（跨工具）**：每步配反操作，失败按倒序撤销。工程上有成熟方案（**saga 模式**），但落到 agent 场景仍是开放问题。
- **兜底**：做不到上面两层，用 `tool.execute.before` hook 在关键操作前拦下来人工审批或外部校验。

> 强调：这些都是工具层和契约层的责任，runtime 帮不上忙。

**可观测性：开箱够用，工业级靠生态。**

| 需求 | 方案 |
|---|---|
| 看每步发生了什么 | `client.app.log()` 结构化日志，分级输出 |
| trace tree / token cost / replay | `opencode-otel` 导成 OpenTelemetry，接 Jaeger / Tempo / Honeycomb |
| 类 LangSmith 体验 | `opencode-plugin-langfuse` 直接接 Langfuse |
| 官方 native 支持 | issue #14697 在跟进 OTLP export |

#### 第三阶段更准确的说法

不是"三个坑都解决了"，而是 **context 由 runtime 直接收掉，可观测性靠生态补齐，状态管理则把 "runtime 该管的" 和 "工具/契约层该管的" 明确切开**。这个切分本身就是这一阶段最重要的认知收获。

#### 还有一个生态层面的判断

coding agent 是模型提供商当前主动适配的方向，工具调用格式、context 压缩策略、长 context 稳定性这些长尾问题，整个生态一起摊。**自己写 runtime = 跟模型迭代速度赛跑；站在通用 runtime 上 = 让 runtime 跟着模型生态一起进步。**

#### 项目重点的变化

不再是堆 workflow，也不再是打磨自研 runtime，收成三件事：

1. 看 query 属于哪种知识形态
2. 为这类 query 选对检索和执行路径
3. 把"对"的标准写清楚，用 skill 和验证逻辑固定下来

> 第三阶段是项目的承重点。体现的不是系统做出来了，而是知道哪些东西该自己做、哪些该站在生态上复用。

## 三、当前架构深度展开（Result）

### 3.1 路由原则：知识形态决定检索范式

走完三阶段，整个系统最重要的路由判断收成一张表。

| 知识类型 | 典型 query | 当前主路径 | 为什么 |
|---|---|---|---|
| 事实性 | 制度、定义、参数、规范 | 混合 RAG | 召回和排序问题 |
| 程序性 - 业务流程 | 某类业务流程怎么走 | 固定 workflow 或浅层 Agentic | 路径已知，保留确定性骨架 |
| 程序性 - 结构化分析 | 时间过滤、分组聚合、排序对比 | 代码 / SQL 执行 + 汇总 | 逻辑明确，但要走计算不是检索 |
| 判断性 | 方案比选、异常诊断、要中间判断 | Agentic Search | 标准本身需要在过程中逐步逼近 |

**核心意义**：把"要不要上 Agentic"从抽象讨论变成明确的路由规则。

> 成熟的标志：知道什么时候该保住确定性，什么时候该把控制权交给 agent。

### 3.2 Agentic Search 的两类活：逻辑明确的算账，与标准模糊的诊断

Agentic Search 当前主要处理两类场景：**结构化分析**（程序性）和**判断性问题**。都要多步执行，区别在前者逻辑明确，后者标准模糊。

#### 类型一：结构化分析——别把"算账"做成"找相似"

**脱敏样例**：系统里有任务执行记录表，用户会问：

1. "找出所有最后一次成功执行使用了某类治理策略的任务，按策略归类。"
2. "最近一周主要在处理什么类型的任务？"
3. "哪类任务执行次数最多且一次通过率最低？"

看着是问答，骨子里是 group by、时间过滤、排序、多指标联合比较。

**为什么 RAG 在这里是错路径**：问题本身不是"找相似文本"，而是"在数据上做计算"。切块灌向量库再检索，最多召回几段"看起来相关"的片段，给不出精确统计。跟分块、reranker、prompt 怎么调都没关系。

**正确路径**：agent 识别这是结构化分析 → 读全量或子集数据 → 动态生成 Python / SQL / shell 脚本做精确统计 → 基于统计输出自然语言总结。

**反常识但加分的点**：context 装得下时，**RAG 反而是负优化**。能直接对原始数据做精确分析的场景，RAG 把数据切碎，把问题降级成"相似片段拼接"，精度天然更差。

#### 类型二：判断性问题——LLM 是检索规划器，不是生成器

异常诊断这种问题不是检索一次就答：

1. 检索相关规则和历史案例
2. 根据中间结果判断当前更像哪种异常
3. 补检索缺的那部分证据
4. 收成答案或下一步建议

LLM 的角色变了：**决定搜什么、搜几次、用什么工具、结果够不够回答**。

**天花板不在工程，在能不能把领域专家的隐性经验显式化下来。**

### 3.3 工具选择的底层逻辑：失败模式决定 agent 友好度

到 Agentic Search 阶段，工具的价值不只是"能不能查到"，还要看"**查不到的时候 agent 知不知道自己没查到**"。

| 工具 | 失败模式 | agent 友好度 |
|---|---|---|
| grep / ripgrep | 返回 0 行，明确无结果 | 高 |
| SQL | 语法报错或返回空表，明确 | 高 |
| 向量检索 | 永远返回 top-k，哪怕全不相关 | 低 |
| 直接读文件 | 装得下就准，装不下静默退化 | 中 |

**核心判断**：选 agent 主干工具，关键不在能力强不强，而在**失败模式可不可判别**。

**为什么 coding agent 的搜索主干往往是 grep**：grep 没结果，agent 立刻知道要换关键词、换范围、换工具；向量检索就算没找到，也会返回一堆"看起来像结果"的东西，agent 反而不知道自己没找到。

> 业务场景同样成立：结构化分析用 SQL 和脚本比向量检索合适，不是更"聪明"，而是结果边界更清楚。

### 3.4 工作方式变化：从过程确定性转到结果确定性

**精力转移点**：从"怎么把 agent loop 写稳"，挪到两件靠近业务价值的事——

1. 把"结果对"的标准定下来
2. 把高成功率路径沉淀成 skill 和确定性工具

**思维方式变化**：

| | 自研 runtime 阶段 | OpenCode 阶段 |
|---|---|---|
| 本能反应 | 把每一步都规定死 | 不强规定每一步走哪条路 |
| 稳定性来源 | 过程控制换稳定 | 把最终产物长什么样定清楚 |
| 给 agent 留什么 | 强约束流程 | 自己看结果、自己改的验证手段 |

> 这就是为什么 OpenCode 的文件系统和 Bash 能力很关键：**文件是看得见的状态，脚本是可验证的动作，agent loop 才能真正闭环**。[详见附录 B.1]

### 3.5 用 skill 收敛模型路径差异

**观察**：同一个复杂 query，换不同模型跑，最终答案差不多，**中间路径差很多**。

**典型路径差异**：

- 有的模型先写代码做精确统计再总结，有的读完数据就开始自然语言推理
- 有的对单 agent 能搞定的任务过度派发子 agent
- 有的会自作主张改统计口径（"最近一周"理解成自然周或滚动 7 天）

**没约束的后果**：生产环境输出口径不一致。

**skill 在当前架构里的角色**：不是给 agent 多塞几句 prompt，而是把高成功率路径沉淀成可复用的工作文档和确定性工具，**把模型默认的路径偏好往一处收**。

#### 当前已识别的三条 skill 规则

1. **结构化数据分析必须先做精确统计再总结**，不允许 agent 看一眼数据就下结论。
2. **单文件且 context 装得下时，不要为了并行而并行**，避免无意义派发子 agent，把 token 成本和整合复杂度抬上去。
3. **输出口径必须固定**。时间范围、分类标签、统计口径都写进 skill 或契约层，不让模型临场决定。

> 抽象一层：skill 把"每次重新试错"变成"复用已经验证过的成功路径"。既是路径一致性问题，也是结果确定性问题。[详见附录 B.2]

### 3.6 多 agent 编排：task tool 和手工 spawn 的取舍

> 高级话题，被追问时展开。

OpenCode 体系里子 agent 编排两种方式：**task tool**（同 session 内主 agent 派发子 agent）；**手工 spawn**（OpenCode 外面自己写编排器，起多个独立 session）。

| 场景 | 推荐模式 |
|---|---|
| 单任务内能拆 2-3 个足够重的子任务 | task tool |
| 跨模型对比或大规模批量跑任务 | 手工 spawn |
| 需要细粒度控制超时、重试、并发 | 手工 spawn |
| 单文件或小范围任务 | 不并行，主 agent 自己做 |

**当前项目里的实际情况**：大多数聚合分析 query 属于最后一种——一个主 agent 直接读数据、写脚本、跑验证、汇总结果就够了。这种场景更需要明确的 skill 约束，**防止模型为了显得更 agentic 而过度并行**。

## 四、结果与复盘（Result + Learning）

### 4.1 可讲结果（三层）

| 层 | 内容 |
|---|---|
| **量化结果** | 传统 RAG 阶段用混合检索 + RRF + reranker，知识库问答命中率提升约 25% |
| **能力边界扩展** | 从只处理事实性问答 → 覆盖程序性查询（业务流程 + 结构化分析）→ 覆盖判断性问题 |
| **架构判断力成熟** | 从倾向自己造轮子，到知道哪一层该交出去、哪一层自己守 |

> 面试官关心"这个项目难在哪" → 讲第三层。前两层不少团队都能做出一部分，**第三层才体现对 agent 系统工程边界的理解**。

### 4.2 留下的 6 个判断

1. **召回是上限**。事实性问答先把召回做对，再谈排序和生成。
2. **知识形态决定检索范式**。事实性、程序性、判断性三类不该用同一套方法硬打；程序性内部还要再分流程编排和结构化分析。
3. **固定 workflow 不是落后**，是模型能力不够时保留确定性的合理手段。
4. **自研 runtime 的成本不在功能开发**，在 context 工程、状态管理、可观测性。
5. **runtime 这一层值得交出去**。应用层精力应放在契约层、skill、业务结果定义上。
6. **选 agent 主干工具，看失败模式可不可判别**，不看能力强不强。

### 4.3 一句话压缩

> 这个项目让我从"怎么把 RAG 调得更准"，走到"怎么给不同类型的 query 选对范式"，再走到"什么该自己做、什么该复用成熟 runtime"。**分水岭不在模型层，而在 runtime 层和契约层**。

## 附录 A：传统 RAG 调优技术速查

这一部分不是正文主线，而是被深挖时拿来展开的“技术弹药”。正文讲到事实性问答的优化时，可以按需引用。

### A.1 Hybrid Recall + RRF：为什么先做 BM25 + dense

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：Dense 单通道在专有名词、产品编号、错误码这类 query 上天然会塌，必须补一路稀疏检索。BM25 + dense 做 hybrid，是 ROI 最高的一步。

**为什么**：embedding 模型会把精确 token 泛化成语义类别，字面精度丢失。BM25 在精确 token 匹配上是天然强项，两路刚好互补。

**为什么用 RRF 融合**：BM25 分数和 cosine 分数量纲不可比，直接做归一化加权不稳。RRF 用 rank 不用 score，绕开量纲问题，简单但稳定。

**面试一句话**：在 RAG 里，hybrid 不是锦上添花，而是 dense retrieval 结构性弱点的补丁。

### A.2 Chunking：为什么把 chunk size 当变量调

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：chunk size 不应固化成 512 token 这种教程默认值，而应该按 query 类型和语义边界调。

**为什么**：事实性问题适合短 chunk，信号纯；主题性问题适合长 chunk，需要更多 context。固定 token 切分还容易把完整语义单元截断。

**实际策略**：按标题、段落、列表、代码块等语义边界切；默认值更倾向 200-300 token；长文档场景上 hierarchical retrieval。

**面试一句话**：512 token 是教程默认值，不是最优值。chunking 应该是变量，不是常数。

### A.3 向量相似度：为什么默认选 cosine

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：cosine similarity 默认比 dot product 更稳，因为它消除了向量长度对分数的系统性影响。

**为什么**：语料同时包含短 FAQ 和长手册时，长文档 embedding 范数天然更大，dot product 会偏向长文档。cosine 或显式做 L2 归一化可以消除这个偏差。

**面试一句话**：dot product 的问题不是偶发误差，而是分布偏置，所以值得在上线前主动校验。

### A.4 HNSW：为什么 `ef_search` 值得调高

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：在 LLM pipeline 里，HNSW 的 `ef_search` 往往可以放心调高，因为检索延迟不是整体瓶颈。

**为什么**：检索阶段多花几毫秒到几十毫秒，后面 reranker 和 LLM 本来就是更大的延迟头。对用户体感几乎无差，但能换来更高召回。

**面试一句话**：HNSW 的 `ef_search` 是典型的“用一点点延迟换稳定召回”的单边收益参数。

### A.5 Reranker：为什么说它是放大器，不是召回器

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：reranker 的作用是在候选池里做精排，前提是候选池里已经有相关文档。第一阶段没捞回来，第二阶段救不回来。

**为什么**：两阶段排序的上限由召回质量决定。很多团队喜欢先调 reranker，是优先级倒了。

**实践原则**：召回阶段先做多通道和合理的 top-k；reranker 至少做一次领域评测，不要直接套用通用网页搜索上的默认模型。

**面试一句话**：reranker 只能把相关文档排前面，不能把没召回的文档凭空变出来。

### A.6 Query Rewriting：为什么要保留原始 query

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：query rewriting 的价值是补 vocabulary gap，但必须保留原始 query 做 fallback。

**为什么**：LLM 改写的核心风险是 query drift。一旦改写偏了，整个检索会越走越偏。最稳妥的方法是原始 query 和改写 query 同时检索，再合并去重。

**面试一句话**：LLM query rewriting 很强，但它继承了传统 relevance feedback 的老问题，不能把原始 query 扔掉。

### A.7 如果面试官往 IR 深挖，可以主动抛的 3 句

1. **“RRF 的核心不是公式有多复杂，而是它用 rank 绕开了多路分数量纲不可比的问题。”**
2. **“chunking 真正该问的是 query 形态，不是教程里写了 256 还是 512。”**
3. **“RAG 的大部分核心技术，在 IR 里其实早就有对应经验，真正的新东西是把这套能力压缩到了普通 Python 开发者也能快速搭起来的程度。”**

## 附录 B：基于 OpenCode 做 runtime 的工程细节

这部分是正文里"为什么迁移到 OpenCode"和"工作方式变化"两段的工程展开。面试官如果继续往"怎么真正接进系统"里问，可以从这里抽素材。正文已经覆盖了四层结构、四个核心能力、task tool 与手工 spawn 的取舍，附录不再重复，只补两块正文放不下的内容：生产级接入细节，以及契约层应该怎么定义。

### B.1 把 OpenCode 真接进系统时，几个细节不能忽略

1. **文件响应模式比管道模式稳。** 把输入和输出都显式落文件，agent 的心智模型更稳定，也便于审计和重试。
2. **工作目录要设计清楚。** 这类 runtime 往往对可访问路径有明确边界，临时文件、prompt 文件、输出文件最好都放在项目工作目录下。
3. **stdout 要有兜底。** 即使已经要求 agent 把结果写入文件，也要准备从 stdout 提取结构化输出的 fallback。
4. **并发能力不要想当然。** 一个 runtime 能不能稳定吃多并发，除了自己这层，还取决于底层模型 provider 的 rate limit。
5. **权限边界是工程问题，不是 prompt 问题。** 能限制的工具尽量限制，必要时配合 sandbox 和 allowed tools。

这些细节平时看起来琐碎，但真正决定了"能 demo"还是"能生产"。

### B.2 结果确定性：契约层应该怎么定义

迁移到 OpenCode 之后，应用层最应该投入的不是再去规定 agent 每一步怎么做，而是把结果契约写清楚。最少要明确四件事：什么叫做完、什么叫做对、怎么验证它做对了、验证失败后怎么办。

放到当前项目里，契约层至少应该包含：输出 schema 或固定结构；时间范围、分类体系、统计口径等显式定义；对关键结果的验证脚本或可复算逻辑；何时重试、何时人工接管的规则。

也正因为如此，skill 不是孤立存在的。它和契约层是一体两面：契约层定义"什么是对的"，skill 定义"多数情况下怎么更容易做到对"。
