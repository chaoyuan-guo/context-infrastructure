# Agent OS 项目经验底稿：从传统 RAG 到 Agentic Search + OpenCode Runtime

> 用途：面试时讲 Agent OS 项目经验的底稿。主线按项目演进组织，不按 IR 教材章节平铺。
> 讲述方式：正文按 STAR-L 结构组织；附录保留 RAG 和 OpenCode 的技术细节，方便被深挖时展开。
> 当前状态：聚合分析类 query 先用一个脱敏同构样例说明，面试前可替换成真实客户案例。

---

## 30 秒版本

这个项目一开始是一个面向政企场景的知识库 RAG。早期先把事实性问答的召回做好，用 hybrid search、RRF 和 reranker 把命中率提升了约 25%。但很快发现，客户并不只问事实性问题，还会问业务流程、需要中间判断的复杂问题，以及基于业务记录的聚合分析。早期为了补程序性知识，做过固定 workflow 和自己写的状态机编排；再往后为了提升动态编排能力，尝试过自己封装 agent loop，但很快撞到上下文管理、状态管理和可观测性的工程复杂度。最终迁移到 OpenCode 这类通用 coding agent runtime，把运行时层外包出去，自己重点做检索路由、结果契约和 skill 沉淀，整个 Agentic Search 架构才逐渐成熟稳定下来。

---

## 一、背景与定位（Situation）

Agent OS 服务的不是单一类型的问答，而是混合型知识与业务操作场景。表面上看，用户都在“提问”；落到系统里，本质上其实混着四类不同任务：

1. **事实性知识问答**：例如制度、定义、参数、规范。
2. **程序性知识查询**：例如某个业务流程该怎么走、下一步该调用什么工具。
3. **判断性问题**：例如方案比选、异常诊断、需要中间判断的复杂问答。
4. **结构化数据分析**：例如从任务记录、台账、提交记录里做时间过滤、分组聚合、排序对比。

这个项目里真正难的地方，不是把一个 RAG 调得更准，而是先判断：**当前这个 query 到底属于哪一类，应该走哪种检索和执行范式。**

所以这条项目线最后沉淀出的核心判断不是“某个模型更强”，而是两句话：

1. **知识形态决定检索范式。**
2. **运行时层决定 agent 能不能稳定交付。**

从面试表达上看，这个项目最值得讲的不是“我会 hybrid search”，而是：从传统 RAG、固定 workflow、自研 agent runtime，一路演进到 Agentic Search + OpenCode runtime，背后每次架构切换的触发条件和判断依据是什么。

## 二、三阶段架构演进（Task + Action）

### 2.1 第一阶段：传统 RAG + 固定 workflow 编排

最早期的目标比较朴素：先把知识问答做起来。当时模型的 agentic 能力还不强，成熟的 agent 框架基本没有。LangChain、AutoGPT 这一类东西看着很热闹，但离生产级稳定还差得很远。这个阶段的设计思路很务实：

1. **事实性问题先交给传统 RAG。**
2. **程序性问题先交给固定 workflow。**

这背后的判断是，当时的模型还不适合做强动态编排，强行让模型自己决定全流程，稳定性很差。与其让模型“自由发挥”，不如把确定性的部分先写死，让模型只在语义层面承担它擅长的职责。

这个阶段有两个关键决策。

**决策 1：事实性问答先把召回做对，不先调 prompt。**

在事实性知识问答这条线上，最核心的判断是：**召回是上限。** 具体做法是把单通道 dense retrieval 升级成 hybrid recall，用 BM25 + dense 双通道召回，再用 RRF 融合，最后把 top-k 候选交给 reranker 做精排。[详见附录 A.1、A.5]

配套还做了三件事：

1. chunking 不再固定成某个教程默认值，而是按语义边界切，并把 chunk size 当成可调变量。[详见附录 A.2]
2. 向量相似度确认用 cosine 或显式做 L2 归一化，避免长文档系统性占优。[详见附录 A.3]
3. query rewriting 保留原始 query 做锚，避免 query drift。[详见附录 A.6]

这条线的直接结果，就是简历里那条可以量化的产出：**知识库问答命中率提升约 25%。**

**决策 2：程序性知识不用强上动态 agent，先用固定 workflow 顶住。**

当时面对的一类真实场景，是用户有一套遥感影像数据治理流程，已经配置好了各种原子化治理工具。要想把这套流程稳定跑下来，核心靠的不是让模型自己“想办法”，而是靠人把任务节点、工具调用和约束条件先编排好。模型在各个节点上只承担两类工作：

1. 做语义判别。
2. 做参数提取。

这套 workflow 的实现方式本质上是自己写的状态机。这样做很土，但在当时是合理的：目标定义得再清楚，如果模型的指令遵循和 agentic 能力不够强，单靠模型也很难把整套流程稳定跑下来。

**这一阶段的结果与边界**

到这里，系统已经能覆盖两类问题：

1. 事实性问题，用 RAG 解决。
2. 一部分程序性问题，用状态机 workflow 解决。

但局限也很快暴露出来了：

1. workflow 很死板，新增一类流程就要新增一套编排。
2. 它适合“路径已知”的任务，不适合中间要动态判断、动态补检索、动态选工具的问题。
3. 一旦 query 的形态从“按固定流程走”变成“先看情况再决定下一步”，这套架构就开始失效。

这就是第一阶段到第二阶段的触发条件：**不是 RAG 做得不够好，而是问题类型已经超出了单轮检索和固定流程的边界。**

### 2.2 第二阶段：手搓 agent runtime + Agentic Search

进入第二阶段的直接动机，是想提升系统的动态编排能力。说白了，就是不再满足于“流程由人提前编排好”，而是希望 agent 能根据 query 和中间结果，自己决定下一步去检索什么、调用什么工具、要不要补上下文、要不要改路径。

这一步本质上就是从固定 workflow 走向 Agentic Search。

为了做到这一点，当时尝试过自己在模型调用层上方封装 agent loop。模型调用层用了聚合网关，所以工具调用协议适配不是主要矛盾；真正开始吞时间的，是运行时层那堆看起来不起眼、做起来极脏的工程问题。

**最大的三个坑是：**

1. **上下文窗口管理。**
2. **状态管理。**
3. **可观测性。**

**坑 1：上下文窗口管理比看上去复杂得多。**

一旦 agent 能动态编排，context 不再只是“用户问题 + 若干检索片段”，而会开始堆很多东西：工具描述、前几轮中间结果、失败重试信息、压缩摘要、已执行动作、待执行动作。问题很快就来了：

1. 工具多的时候，哪些描述必须保留在 context 里，哪些可以外置。
2. 窗口快满的时候，怎么压缩才不丢掉后续推理真正依赖的信息。
3. 压缩过的摘要如果把关键决策依据抹掉了，后面的 agent 会在错误前提上继续推理。

这类问题说起来像“做个 summary”就完了，真做起来全是工程细节，而且高度依赖模型的实际行为。

**坑 2：状态管理必须自己设计。**

从固定 workflow 切到 agent loop 后，很多原本显式写在状态机里的东西都要重新定义：

1. 当前轮 agent 到底处于“规划中”“执行中”“等待结果”“需要重试”还是“可收敛输出”。
2. 中间失败后怎么恢复，哪些状态要保留，哪些状态要回滚。
3. 多步任务里，什么时候可以认为某一轮已经结束，什么时候该继续迭代。

如果这些东西不明确，agent loop 看起来像在跑，实际上可能只是“围着一个不清晰的状态机打转”。

**坑 3：可观测性主要靠自己补日志，效率很低。**

自研 runtime 时，排查问题往往只能靠自己加日志，看每一步 prompt、工具输入输出、压缩结果、状态跳转。这样做当然能调，但体验很差，迭代效率也低。很多时候精力都花在“系统为什么又这样了”，而不是“业务效果怎么提升”。

**这一阶段最大的学习**

这一阶段最重要的认知，不是“agentic 很酷”，而是：**运行时层是系统里最容易吞噬工程投入的一层，而且它跟具体业务逻辑关系并不大。**

这条判断后来越来越清楚：自己手搓 runtime，本质上还是在用大量过程控制换取确定性。上下文怎么压、状态怎么轮转、失败怎么恢复、日志怎么埋，这些东西都不是业务本身，却会消耗掉大量时间。换句话说，问题已经不再是“模型够不够聪明”，而是“这套 agent loop 能不能被工程上稳稳托住”。

**这一阶段的结果与边界**

这一步验证了两件事：

1. Agentic Search 对复杂 query 是真的有价值，不是概念噱头。
2. 自研 runtime 的投入产出比不理想，尤其是在模型能力和生态快速变化的背景下。

于是第二次架构切换来了：**不是放弃 Agentic，而是放弃自己造 runtime 的轮子。**

### 2.3 第三阶段：基于 OpenCode 的 runtime + Agentic Search

第三阶段的判断，跟第一阶段到第二阶段不同。第一阶段切到第二阶段，是因为问题类型变了；第二阶段切到第三阶段，是因为成本结构变了。

随着 Claude Code、OpenCode、Codex 这类通用 coding agent 成熟，行业里开始出现一个很清晰的趋势：**运行时层正在收敛成一个可复用的标准能力。**

这一步最关键的转变，不是“我们换了一个工具”，而是分工变了：

1. **模型层**：选什么模型、什么 provider。
2. **协议层**：怎么调模型 API、怎么接工具。
3. **运行时层**：agent loop、上下文管理、工具调用、文件系统、子 agent、权限边界。
4. **契约层**：什么叫结果正确、怎么验证、何时重试、何时人工接管。

前两个阶段里，团队其实在自己背运行时层的大部分复杂度。第三阶段的核心决策，是把运行时层更多交给 OpenCode 这类通用 runtime，自己把重心转到契约层和领域能力沉淀上。[详见附录 B.1]

**为什么最终选择走 OpenCode 这条路**

OpenCode 对这个项目最大的价值，不是某个单点功能，而是它把几件原本需要自己做的脏活一起吸收掉了：

1. **稳健的 agent loop。** agent 能执行、观测、纠错，而不是一次 API 调用吐完就结束。
2. **Bash 的原子能力。** 很多原本要在 workflow 里特殊处理的事情，现在直接让 agent 写脚本、跑脚本、看结果就行。
3. **文件系统作为状态载体。** 文件是可见状态，agent 可以反复读取、修改、验证，天然适合做闭环。
4. **skill 的渐进式加载。** 可以把高成功率路径、领域 SOP、确定性工具封装成 skill，不需要每个 session 从零试错。

这些能力加在一起，本质上是在帮系统吸收上下文工程和运行时层的复杂度。也正因为如此，第三阶段真正带来的不是“多了几个工具”，而是**整体工程复杂度下降了，Agentic Search 才开始变得稳定可用。**

**这一阶段的结果**

到了这里，项目的重点不再是继续堆 workflow，也不再是继续打磨自研 runtime，而是收敛成三件事：

1. 先判断 query 属于哪种知识形态。
2. 为这种 query 选对检索和执行路径。
3. 把结果正确性的标准写清楚，并通过 skill 和验证逻辑固化下来。

从面试表达上看，第三阶段是这个项目真正的承重点。因为它体现的不只是一个系统做出来了，而是：**知道哪些东西该自己做，哪些东西应该站在生态上复用。**

## 三、当前架构深度展开（Result）

### 3.1 路由原则：知识形态决定检索范式

走到第三阶段后，整个系统最重要的 routing 判断被收敛成了一张表：

| 知识类型 | 典型 query | 当前主路径 | 为什么 |
|---|---|---|---|
| 事实性 | 制度、定义、参数、规范 | Hybrid RAG | 本质是召回和排序问题 |
| 程序性 | 某类业务流程怎么走 | 固定 workflow 或浅层 Agentic | 稳定 SOP 适合保留确定性骨架 |
| 判断性 | 方案比选、异常诊断、条件筛选 | Agentic Search | 需要多步检索和中间判断 |
| 结构化数据分析 | 时间过滤、分组聚合、排序对比 | 代码 / SQL 执行 + 汇总 | 本质是计算问题，不是检索问题 |

这张表的意义在于，它把“要不要上 Agentic”从抽象讨论变成了明确的 routing 规则。

系统不是所有 query 都往 Agentic 上推，也不是所有 query 都塞进 RAG。真正成熟的点，在于知道什么时候该保持确定性，什么时候该把控制权更多交给 agent。

### 3.2 Agentic Search 的具体形态

当前这套架构里，Agentic Search 主要处理两类场景：

1. **需要中间判断的复杂问题。**
2. **结构化数据分析类 query。**

先看第二类。用一个脱敏同构样例说明：系统里有一份任务执行记录表，用户会问：

1. “找出所有最后一次成功执行使用了某类治理策略的任务，并按策略归类。”
2. “最近一周主要在处理什么类型的任务？”
3. “哪类任务执行次数最多且一次通过率最低？”

这类 query 看起来也是问答，实际上本质上是：

1. group by
2. 时间过滤
3. 排序
4. 多指标联合比较

如果把这类数据直接 chunk 后灌进向量库，再让 RAG 去答，系统最多只能召回一些“看起来相关”的片段，没法给出精确统计结果。**这不是调 chunking、调 reranker、调 prompt 能解决的问题，因为问题本身不是“找相似文本”，而是“对数据做计算”。**

这种场景下，正确路径应该是：

1. agent 先识别这不是普通问答，而是结构化分析。
2. 读入全量数据或相关子集。
3. 动态生成 Python / SQL / shell 脚本做精确统计。
4. 基于统计结果再输出自然语言总结。

这里有一个很反直觉、但面试里很加分的判断：**当上下文窗口装得下时，RAG 反而可能是负优化。**

因为这时问题本来可以直接对原始数据做精确分析，RAG 却会先把数据切碎，再把问题降级成“相似片段拼接”，精度天然更差。

对第一类判断性问题也是同理。比如一个异常诊断问题，往往不是“检索一次就答”，而是：

1. 先检索相关规则和历史案例。
2. 根据中间结果判断当前更像哪种异常。
3. 再去补检索缺的那部分证据。
4. 最后收敛成答案或下一步建议。

这时 LLM 不再只是生成器，而是检索规划器。它负责决定搜什么、搜几次、每次用什么工具、结果是否足够回答问题。

### 3.3 为什么 OpenCode 适合作为 runtime

这个项目迁移到 OpenCode 之后，架构上的一个核心变化，是开始更明确地区分“什么是 runtime 负责的，什么是应用层负责的”。

从四层结构看：

| 层 | 关注点 | 当前分工 |
|---|---|---|
| 模型层 | 选哪个模型、推理强度如何 | 按任务特征选模型 |
| 协议层 | 如何调用模型与工具 | 尽量通过现成生态解决 |
| 运行时层 | agent loop、上下文、文件、工具、子 agent | 主要复用 OpenCode |
| 契约层 | 什么叫结果正确、怎么验证 | 重点自己做 |

迁移之后，团队不再把主要精力放在“如何把 agent loop 写稳”，而是放到两件更靠近业务价值的事情上：

1. **定义结果正确性的标准。**
2. **把高成功率路径沉淀成 skill 和确定性工具。**

这背后其实对应的是一种工作方式变化：从更强调“过程确定性”，逐渐转向更强调“结果确定性”。

以前自研 runtime 时，本能是把每一步怎么做都规定死，希望通过过程控制换稳定性。迁移到 OpenCode 后，更合理的方式变成了：

1. 不强规定 agent 每一步怎么走。
2. 更明确地规定最终产物应该长什么样。
3. 提供验证手段，让 agent 能自己观测结果、自己修正。

这也是为什么 OpenCode 的文件系统和 Bash 能力很关键。文件是可见状态，脚本是可验证动作，agent loop 才能真正闭环。[详见附录 B.2、B.4]

### 3.4 工具选择的底层逻辑：失败模式决定 agent 友好度

走到 Agentic Search 阶段后，工具的价值不再只是“能不能查到”，还要看“查不到时 agent 是否知道自己没查到”。

| 工具 | 失败模式 | 对 agent 友好度 |
|---|---|---|
| grep / ripgrep | 返回 0 行，明确无结果 | 高 |
| SQL | 语法报错或返回空表，明确 | 高 |
| 向量检索 | 往往永远返回 top-k，哪怕全不相关 | 低 |
| 直接读文件 | 装得下就准，装不下会静默退化 | 中 |

这张表背后的判断很重要：**agent 主干工具不一定选能力最强的，而是选失败模式最可判别的。**

这也是为什么在 coding agent 场景里，搜索主干往往是 grep 而不是向量检索。grep 失败了，agent 立刻知道要换关键词、换范围、换工具；向量检索即使失败，也经常会返回一堆“看起来像结果”的东西，agent 反而不知道自己其实没找到答案。

这条判断放到业务场景也一样成立。对于结构化分析类问题，SQL 和脚本比向量检索更适合作为主干工具，不是因为它们更“智能”，而是因为它们的结果边界更清晰。

### 3.5 用 skill 收敛模型路径差异

进入 OpenCode runtime 阶段后，一个非常真实的观察是：**同一个复杂 query，换不同模型去跑，最终答案可能差不多，但中间路径差异很大。**

常见差异包括：

1. 有的模型会先写代码做精确统计，再输出总结。
2. 有的模型会直接读完数据后开始自然语言推理。
3. 有的模型会对一个本来单 agent 就能完成的任务过度派发子 agent。
4. 有的模型会自己改动统计口径，比如把“最近一周”理解成自然周或滚动 7 天。

如果没有约束，这种路径差异在生产环境里会直接变成输出口径不一致。

这就是 skill 在当前架构里的角色：**不是给 agent 多塞一点 prompt，而是把高成功率路径沉淀成可复用的工作文档和确定性工具，把模型默认的路径偏好收敛起来。**

当前已经识别出三条特别值得封装的 skill 规则：

1. **结构化数据分析类 query 必须先做精确统计再总结。** 禁止 agent 看一眼数据就直接下结论。
2. **单文件且上下文窗口装得下时，不要为了并行而并行。** 避免无意义地派发子 agent，增加 token 成本和整合复杂度。
3. **输出口径必须固化。** 时间范围怎么算、分类标签用哪套标准、统计口径怎么定义，都应该写进 skill 或契约层，而不是让模型临场决定。

从更高层看，skill 真正解决的问题，是把“每次都重新试错”变成“复用已经验证过的成功路径”。这既是模型路径一致性问题，也是结果确定性问题。[详见附录 B.5]

### 3.6 多 agent 编排：task tool 和手工 spawn 的取舍

这部分是高级话题，面试官如果继续往下挖可以展开。

在 OpenCode 体系里，子 agent 编排大致有两种方式：

1. **task tool。** 在同一个 session 内让主 agent 派发子 agent。
2. **手工 spawn。** 在 OpenCode 外层自己写 orchestrator，起多个独立 session 去跑。

两者的选择标准不是“哪个更高级”，而是看任务形态：

| 场景 | 推荐模式 |
|---|---|
| 单任务内拆 2-3 个足够重的子任务 | task tool |
| 跨模型对比或大规模批量跑任务 | 手工 spawn |
| 需要细粒度控制超时、重试、并发 | 手工 spawn |
| 单文件或小范围任务 | 不并行，主 agent 直接做 |

当前这条项目线里，大多数聚合分析类 query 其实都属于最后一种：一个主 agent 直接读数据、写脚本、跑验证、汇总结果就够了。这里反而更需要的是明确的 skill 约束，防止模型“为了看起来更 agentic 而过度并行”。

## 四、结果与复盘（Result + Learning）

### 4.1 可讲结果

这个项目可以对外稳定讲的结果，建议分成三层：

1. **第一层是量化结果。** 传统 RAG 阶段通过 hybrid recall、RRF 和 reranker，知识库问答命中率提升约 25%。
2. **第二层是能力边界扩展。** 系统从只能处理事实性问答，逐步扩展到程序性问题、需要中间判断的问题，以及结构化数据分析类 query。
3. **第三层是工程复杂度收敛。** 从自己背 runtime 层的大量细节，切换到站在 OpenCode 这类通用 agent runtime 上复用成熟能力，把精力集中到契约层和 skill 沉淀上。

如果面试官更关心“这个项目真正难在哪”，建议强调第三层。因为前两层很多团队都能做到一部分，第三层才真正体现出对 agent 系统工程边界的理解。

### 4.2 这条项目线最终沉淀出的 6 个判断

1. **召回是上限。** 事实性问答先把召回做对，再谈排序和生成。
2. **知识形态决定检索范式。** 事实性、程序性、判断性、结构化分析，不该用同一套方法硬打。
3. **固定 workflow 不是落后，而是在模型能力不够时保留确定性的合理手段。**
4. **自研 runtime 的真正成本不在功能开发，而在上下文工程、状态管理和可观测性。**
5. **运行时层值得外包。** 自己应该把更多精力放在契约层、skill 和业务结果定义上。
6. **skill 的价值不是“多写几句 prompt”，而是收敛模型路径差异，提升结果稳定性。**

如果把这条项目线压缩成一句最像“面试答案”的表述，可以这么说：

> 这个项目让我从“怎么把 RAG 调得更准”，逐步走到“怎么给不同类型的 query 选对范式”，最后再走到“什么该自己做，什么该复用成熟 runtime”。真正的分水岭不在模型层，而在运行时层和契约层。

## 附录 A：传统 RAG 调优技术速查

这一部分不是正文主线，而是被深挖时拿来展开的“技术弹药”。正文讲到事实性问答的优化时，可以按需引用。

### A.1 Hybrid Recall + RRF：为什么先做 BM25 + dense

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：Dense 单通道在专有名词、产品编号、错误码这类 query 上天然会塌，必须补一路稀疏检索。BM25 + dense 做 hybrid，是 ROI 最高的一步。

**为什么**：embedding 模型会把精确 token 泛化成语义类别，字面精度丢失。BM25 在精确 token 匹配上是天然强项，两路刚好互补。

**为什么用 RRF 融合**：BM25 分数和 cosine 分数量纲不可比，直接做归一化加权不稳。RRF 用 rank 不用 score，绕开量纲问题，简单但稳定。

**面试一句话**：在 RAG 里，hybrid 不是锦上添花，而是 dense retrieval 结构性弱点的补丁。

### A.2 Chunking：为什么把 chunk size 当变量调

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：chunk size 不应固化成 512 token 这种教程默认值，而应该按 query 类型和语义边界调。

**为什么**：事实性问题适合短 chunk，信号纯；主题性问题适合长 chunk，需要更多上下文。固定 token 切分还容易把完整语义单元截断。

**实际策略**：按标题、段落、列表、代码块等语义边界切；默认值更倾向 200-300 token；长文档场景上 hierarchical retrieval。

**面试一句话**：512 token 是教程默认值，不是最优值。chunking 应该是变量，不是常数。

### A.3 向量相似度：为什么默认选 cosine

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：cosine similarity 默认比 dot product 更稳，因为它消除了向量长度对分数的系统性影响。

**为什么**：语料同时包含短 FAQ 和长手册时，长文档 embedding 范数天然更大，dot product 会偏向长文档。cosine 或显式做 L2 归一化可以消除这个偏差。

**面试一句话**：dot product 的问题不是偶发误差，而是分布偏置，所以值得在上线前主动校验。

### A.4 HNSW：为什么 `ef_search` 值得调高

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：在 LLM pipeline 里，HNSW 的 `ef_search` 往往可以放心调高，因为检索延迟不是整体瓶颈。

**为什么**：检索阶段多花几毫秒到几十毫秒，后面 reranker 和 LLM 本来就是更大的延迟头。对用户体感几乎无差，但能换来更高召回。

**面试一句话**：HNSW 的 `ef_search` 是典型的“用一点点延迟换稳定召回”的单边收益参数。

### A.5 Reranker：为什么说它是放大器，不是召回器

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：reranker 的作用是在候选池里做精排，前提是候选池里已经有相关文档。第一阶段没捞回来，第二阶段救不回来。

**为什么**：两阶段排序的上限由召回质量决定。很多团队喜欢先调 reranker，是优先级倒了。

**实践原则**：召回阶段先做多通道和合理的 top-k；reranker 至少做一次领域评测，不要直接套用通用网页搜索上的默认模型。

**面试一句话**：reranker 只能把相关文档排前面，不能把没召回的文档凭空变出来。

### A.6 Query Rewriting：为什么要保留原始 query

**正文对应位置**：2.1 第一阶段的“决策 1”。

**结论**：query rewriting 的价值是补 vocabulary gap，但必须保留原始 query 做 fallback。

**为什么**：LLM 改写的核心风险是 query drift。一旦改写偏了，整个检索会越走越偏。最稳妥的方法是原始 query 和改写 query 同时检索，再合并去重。

**面试一句话**：LLM query rewriting 很强，但它继承了传统 relevance feedback 的老问题，不能把原始 query 扔掉。

### A.7 如果面试官往 IR 深挖，可以主动抛的 3 句

1. **“RRF 的核心不是公式有多复杂，而是它用 rank 绕开了多路分数量纲不可比的问题。”**
2. **“chunking 真正该问的是 query 形态，不是教程里写了 256 还是 512。”**
3. **“RAG 的大部分核心技术，在 IR 里其实早就有对应经验，真正的新东西是把这套能力压缩到了普通 Python 开发者也能快速搭起来的程度。”**

## 附录 B：基于 OpenCode 做 runtime 的工程细节

这部分是正文里“为什么迁移到 OpenCode”那段的工程展开。面试官如果继续往“怎么真正接进系统”里问，可以从这里抽素材。

### B.1 四层结构：为什么说运行时层值得外包

把 agent 系统拆开看，大致有四层：

1. **模型层**：选模型和推理强度。
2. **协议层**：怎么调用模型 API、怎么接工具。
3. **运行时层**：agent loop、上下文管理、工具调用、文件系统、并发、权限。
4. **契约层**：什么算成功、怎么验证、何时重试、何时人工接管。

大多数团队最容易低估的是第三层。因为它看上去不显眼，但会吞掉最多的工程时间，而且很多问题跟业务本身无关，属于每个团队都在重复造的轮子。

迁移到 OpenCode 的核心价值，不是“又多了一个 AI 工具”，而是把第三层里大量通用能力复用掉，把精力转回第四层。

### B.2 OpenCode 真正提供的不是一个壳，而是一套 runtime 假设

OpenCode 在这个项目里最重要的四个能力是：

1. **可执行、可观测、可纠错的 agent loop。**
2. **以文件系统作为状态载体。**
3. **以 Bash 和脚本作为原子动作。**
4. **以 skill 作为渐进式加载的先验。**

这四个能力组合起来，带来的不是“更炫”，而是：

1. agent 可以真正看到自己上一步做了什么。
2. agent 可以调用验证脚本判断结果是否达标。
3. agent 可以在不中断任务的情况下继续修正。
4. 应用层不再需要自己维护一套脆弱的闭环。

如果要一句话解释为什么这类 coding agent runtime 会比“自己调 API + 自己补 workflow”更稳，可以说：**因为它们把执行、观测、纠错的闭环做成了默认能力。**

### B.3 task tool 和手工 spawn 的差别

**task tool** 适合单任务内的子任务拆分：

1. 主 agent 负责规划。
2. 子 agent 在隔离上下文中执行。
3. 主 agent 收回结果再整合。

它的优点是简单，状态由 runtime 管；缺点是外层对并发、超时、模型混搭的控制更弱。

**手工 spawn** 适合更强控制需求：

1. 外层 orchestrator 自己起多个独立 session。
2. 可以给不同 session 指定不同模型。
3. 可以细粒度控制超时、重试、并发和结果回收。

它的优点是可控，缺点是又会把一部分 runtime 复杂度重新拿回来。

所以这两种方式不是替代关系，而是分场景使用。项目里真正最常见的情况，往往是第三种：**根本不需要并行，单 agent 直接做完。**

### B.4 如果要把 OpenCode 真接进系统，几个细节不能忽略

1. **文件响应模式比管道模式稳。** 把输入和输出都显式落文件，agent 的心智模型更稳定，也便于审计和重试。
2. **工作目录要设计清楚。** 这类 runtime 往往对可访问路径有明确边界，临时文件、prompt 文件、输出文件最好都放在项目工作目录下。
3. **stdout 要有兜底。** 即使已经要求 agent 把结果写入文件，也要准备“从 stdout 提取结构化输出”的 fallback。
4. **并发能力不要想当然。** 一个 runtime 能不能稳定吃多并发，除了自己这层，还取决于底层模型 provider 的 rate limit。
5. **权限边界是工程问题，不是 prompt 问题。** 能限制的工具尽量限制，必要时配合 sandbox 和 allowed tools。

这些细节平时看起来琐碎，但真正决定了“能 demo”还是“能生产”。

### B.5 结果确定性：契约层应该怎么定义

迁移到 OpenCode 之后，应用层最应该投入的不是再去规定 agent 每一步怎么做，而是把结果契约写清楚。最少要明确四件事：

1. **什么叫做完。**
2. **什么叫做对。**
3. **怎么验证它做对了。**
4. **验证失败后怎么办。**

放到当前项目里，契约层至少应该包含：

1. 输出 schema 或固定结构。
2. 时间范围、分类体系、统计口径等显式定义。
3. 对关键结果的验证脚本或可复算逻辑。
4. 何时重试、何时人工接管的规则。

也正因为如此，skill 不是孤立存在的。它和契约层是一体两面：契约层定义“什么是对的”，skill 定义“多数情况下怎么更容易做到对”。
