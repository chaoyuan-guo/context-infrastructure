# Agent OS 项目面试作战脚本

## 开场介绍：90 秒版本

这个项目面向政企客户。客户的制度文档、业务数据、流程系统和工具入口分散在不同系统里，很多业务问题从提出到处理完成，需要在文档检索、数据分析、专家判断和流程执行之间来回切换。项目要解决的是分散入口带来的效率问题，具体表现为处理链路长、人工拼接成本高。

所以这个项目的定位是企业智能体：把这些分散能力收敛到一个自然语言入口里，再根据问题类型选择合适的处理路径，帮助客户用自然语言完成高效的信息获取和受控任务执行。

我把用户问题分成四类：能查到的、能算出来的、需要综合判断的、需要执行的。比如规章制度和规范定义走文档 RAG；治理任务次数、通过率、失败原因分布走 SQL 或脚本；地理要素变化分析需要综合规范文档、变更记录、治理日志和专家经验；数据治理流程和报告生成则属于受控任务执行。

技术上我把它拆成两层。底层复用 OpenCode 这类成熟 agent runtime，负责 agent loop、工具执行、文件状态和权限控制。上层自己建设领域 harness，也就是 AGENTS.md + Skills，把客户的领域知识、业务流程、工具入口和风险边界沉淀下来。

评估上也拆成两层。第一层看结果是否正确，比如证据是否能支撑回答，SQL / 脚本结果是否可复算，任务是否完成。第二层看 agent 行为是否可靠，比如路由是否合理，证据不足时是否追问或拒答，高风险动作是否经过 dry-run、审批和审计。

## 开场后的常见追问

### 1. 项目边界：和知识库 RAG、BI、工作流系统分别怎么分工？哪些场景不适合交给 agent？

知识库 RAG 适合回答制度、规范、定义这类文档证据问题；BI 适合稳定指标和固定报表；工作流系统适合标准化流程流转。Agent 更适合跨文档、数据和工具的开放任务，尤其是中间需要判断、探索或动态选择路径的场景。

高频、稳定、低歧义的指标查询优先做成 BI 或固定接口；规则已经完全固定的审批流优先走工作流；缺少数据来源、缺少业务规则、结论无法验证的问题，不适合直接交给 agent 硬做。高风险写操作可以由 agent 发起，但必须进入审批和审计链路。

### 2. 任务分类：为什么把问题分成查得到、算出来、判断出来、任务执行？边界模糊时怎么处理？

这个分类来自用户意图和答案生成方式，本质上是路由提示和评估基准。查得到的问题靠检索，算出来的问题靠计算，判断出来的问题靠多源证据和专家规则，任务执行则会改变业务状态。

边界模糊时，agent 先查 AGENTS.md、Skills INDEX、数据目录和历史样例，做低风险只读探索，找出最可能的执行路径。能形成可验证计划时，就按计划推进并把关键假设写出来；关键意图、统计口径、权限或数据源仍然缺失时，就要求用户澄清。涉及写库、发布、删除等副作用时，进入审批或拒绝执行。我的判断是，企业 agent 应该保留主动探索能力，但探索的作用是缩小不确定性，需求确认仍然要由用户、权限系统或业务规则完成。

### 3. 评估落地：评测集怎么构造？可复算是什么意思？Agentic 阶段怎么做回归？

评测集主要来自专家标注、历史工单、典型业务问题和线上失败 case。文档问答看证据召回和引用，结构化分析看统计口径和结果，复杂判断看证据链，任务执行看路径、参数和工具结果。

“可复算”指统计口径、数据范围、SQL / 脚本和运行结果都留下来，让同一个问题在同一数据版本上能重新跑出同一组数字。Agentic 阶段的回归不只比最终答案，还会检查路由、加载的 skill、工具调用、证据覆盖和高风险动作审批是否符合预期。

### 4. 任务路由：模型怎么判断该走 RAG、SQL、Agentic Search 还是任务执行？路由错了怎么办？

路由由 AGENTS.md + Skills INDEX 驱动。AGENTS.md 放全局原则和安全边界，例如制度类结论必须带来源，统计数字必须来自 SQL / 脚本，证据不足需要追问，写库、删除、发布必须 dry-run + 审批。Skills INDEX 列出每个 skill 的适用场景、输入要求、工具入口、输出格式和风险等级。

路由结果会进入 trace，包括加载了哪个 skill、调用了什么工具、拿到了哪些证据、在哪一步失败。路由错了以后，用失败 case 修正 skill 描述、补充反例，必要时加入回归集，防止同类问题反复走错路径。

### 5. 文档检索：关键词检索、向量检索、hybrid recall、reranker 怎么取舍？什么叫证据召回和原文核验？

快速探索时可以先走单路检索。精确术语、编号、条款号优先关键词检索；口语化、同义表达多的问题优先向量检索。形成高风险结论前必须做 hybrid，并回到原始文档核验前后文、适用范围、版本时间和例外条件。

证据召回是找到可能相关的材料，原文核验是确认这段材料能不能支撑结论。两者的目标不同，前者解决“找没找到”，后者解决“能不能这么说”。

### 6. 结构化分析：SQL / 脚本怎么生成、执行、校验？如何防止模型改错统计口径？

统计类问题的本质是过滤、分组、聚合和排序，答案应该来自结构化计算。把结构化数据切块放进向量库，容易召回看起来相关的片段，却难以生成可重复计算的数字。

执行时先把统计口径显式化：数据源、时间范围、过滤条件、分组字段、空值处理、去重规则和输出粒度。然后生成 SQL 或脚本，运行结果表，再基于结果做自然语言总结。防止模型改错口径的办法是把口径、SQL / 脚本和结果一起展示，数字只允许来自运行结果；如果用户口径和已有字段对不上，先追问或标注假设。

### 7. GIS 变化分析：怎么把规范、变更记录、治理日志和专家经验串起来？

先把问题翻译成通用任务：某地区的道路、建筑、河流、边界等地图对象，在一段时间内有哪些新增、删除、属性变化或位置变化。

规范文档负责定义什么算变化、哪些字段需要关注；变更记录负责提供具体事实，比如哪个对象在哪个时间发生了什么变化；治理日志负责解释处理过程、失败原因和质量校验结果；专家经验负责处理口径差异、例外情况和业务解释。最后输出时按结论挂证据：每个变化分类对应数据来源、统计结果和限制条件。

### 8. Skills 设计：Skill 具体长什么样？怎么判断一个 skill 质量高不高？

Skill 是领域能力包，里面写清适用场景、输入要求、执行步骤、工具入口、输出结构、校验规则和失败处理。比如 GIS 变化分析 skill 会规定先查规范，再查变更记录，再看治理日志，数字必须来自 SQL 或脚本结果。

AGENTS.md 放全局原则，比如所有高风险结论必须带来源，所有写操作必须审批；Skill 放具体任务方法，比如某类 GIS 变化分析要查哪些表、跑哪些脚本、输出哪些字段。一个高质量 skill 要满足几个条件：触发条件清楚，缺少输入时知道追问，工具调用路径明确，输出格式稳定，校验规则可执行，失败时有降级路径，并且能用回归 case 测出来。

### 9. Runtime 取舍：OpenCode 解决了哪些通用问题，客户侧仍然要自己做什么？

OpenCode 解决的是通用 agent runtime 问题，包括 agent loop、context 管理、文件状态、工具执行、权限配置、插件 hook 和交互式执行体验。这部分自己从零做，成本主要花在通用工程能力上，业务沉淀反而慢。

客户交付里仍然要自己做领域 harness：AGENTS.md、Skills、业务工具封装、只读 SQL / GIS 查询入口、报告模板、trace 结构、审计记录、评测集和失败 case 回流。换句话说，OpenCode 提供通用运行底座，项目价值主要沉淀在客户领域能力和治理规则里。

### 10. Permission / Hook：高风险动作怎么管？审计记录怎么留？

prompt 约束属于软约束，适合告诉模型应该怎么做。permission 和 hook 是执行层约束，能在工具真正执行前拦截、校验参数、要求 dry-run、触发人工审批，或者直接拒绝高风险动作。

审计记录按 `run_id` 留痕：用户问题、识别出的意图、加载的 skill、工具调用参数、SQL / 脚本、证据文档路径和版本、dry-run 结果、审批人、审批时间、最终输出和生成物编号。敏感字段要脱敏，工具结果可以存摘要或 hash。审计的目标是能解释一次任务为什么这么做，并能在事故复盘时回放关键路径。

### 11. Multi-subagent：什么情况下用多个 subagent？成本、冲突和结果整合怎么处理？

适合用在任务足够复杂、证据源可以并行拆开、且需要交叉验证的场景。比如 GIS 变化分析可以让不同 subagent 分别查规范、变更记录和历史案例，主 agent 汇总一致性。结构化统计默认单 agent 跑 SQL / 脚本、验证数字，成本更低，结果也更容易控制。

### 12. 自我进化：trace、memory、skill、回归集之间是什么关系？

系统会积累真实运行 trace 和失败 case，包括 query、路由结果、加载的 skill、工具调用、证据来源、最终答案和人工修正。稳定的客户术语写入 memory，稳定流程写回 skill，典型失败进入回归集。改进路径由审核控制：系统自动发现候选改进，人确认后再沉淀到 memory、skill、eval 或 permission / hook。

### 13. 失败处理：工具调用失败、证据不足、数据缺失、模型硬答分别怎么处理？

工具调用失败时，记录错误类型、参数和返回码；只对幂等的读操作自动重试，写操作进入人工确认。证据不足时，输出缺了哪类证据，要求用户补充范围或明确拒答。数据缺失时，区分“确实没有记录”“没有权限访问”“字段或表不存在”，这三种情况对应不同处理方式。模型硬答时，用输出 schema 和证据校验拦住：结论必须绑定证据、SQL / 脚本结果或工具返回，缺少依据的结论进入澄清或拒答流程。

### 14. 业务价值：没有更多通用量化指标时，怎么证明这个项目有价值？

这类回答要克制。25% 是明确量化指标，口径限定在传统 RAG 的事实性问答命中率提升，来自 hybrid recall、RRF 和 reranker。Agentic 阶段如果没有完整量化评估，回答里保持边界，重点讲可验证变化。

更有说服力的讲法是用可验证变化替代虚构数字：过去用户要分别找制度文档、查数据库、问 GIS 专家，再手工整理报告；现在 agent 能在同一次任务里给出证据、SQL / 脚本结果、限制条件和下一步动作建议。这里强调的是交付形态变化：从单点问答，变成可追溯、可复算、可审计的任务处理链路。

### 15. 架构复用：如果换一个政企客户，这套 Agent OS 能复用什么，哪些必须重新建设？

能复用的是通用运行底座和交付方法：OpenCode runtime、permission / hook 模式、trace 与审计结构、skill 文件格式、评测集构造方法、失败 case 回流机制。必须重建的是客户自己的 AGENTS.md、领域术语、数据 schema、工具连接器、业务流程、权限规则和核心 skills。

这个问题能体现项目的真正沉淀：交付的核心是一套把客户知识、流程、工具和风险边界装进 agent runtime 的方法。换客户时，runtime 和方法论复用，领域 harness 重新建设。
