最近一段时间Harness概念大热，上一代的Context Engineering已经快无人问津了。AI媒体圈就是这么后浪拍前浪。Agent Harness其实要说的话，跟2023年的Agent Framework其实仍然是较为类似的生态位（这里说的不是LangChain和Dify），不过现在是更多为了Long-Horizon Task和目前的模型能力所特化。

之前有个圈内的戏谑但已经成为现实：只要学得够慢，就可以不用学。

以上是目前的状态，但本文想讨论的接下来的未来。

# 1、模型在演变，上层建筑也需要适配

真正做过长时间Prompt/Workflow/Agent产品维护的人都知道，Prompt/workflow的设计随着模型的不断换代，是会过时的。有些的问题只是变得不是最佳方案了，但有些可能会导致新模型的能力不能发挥出来。

那么问题来了，Agent Harness（以及Skill、其他prompt、SOP等）呢？

答案是，也会，没有什么理由能保证不会。如果你需要一个知名品牌的背书才愿意相信，那么可以去看最近 拾象的文章 [深度讨论新一轮模型发布：当智能进入月更时代](https://mp.weixin.qq.com/s?__biz=Mzg2OTY0MDk0NQ==&mid=2247523769&idx=1&sn=30ad3042cd0523c0859c0c3dd466d5f9&scene=21#wechat_redirect)

最近的例子就是Opus 4.6升级到Opus 4.7，实际上Opus 4.7并不是一个全方位的提升。一种解释是，Opus 4.7的RL阶段更多使用了类似目前Claude Code的使用范式，也就是主Agent调用子Agent的方式来处理任务。以及从实际使用上来说，如果你仍然按照之前单Agent session的long context方式来使用的话，会发现Opus 4.7变懒了一些，在context较长时候表现很明显。

所以单单一个小版本的模型升级，就可能导致上层的Harness设计要进行调整适配才能保持原有的效果。

那么问题就变成，Harness这个层面，我们攒下的到底是技术资产，还是技术债？

# 2、可积累的方案

一个明显的答案是，如果考虑到模型的迭代进展，特别是在目前这个模型能力在具体方向不能保证不退步的时代，Harness这个层面并不适合作为一个长期积累的资产。它只是当前实现产品效果的手段，而且保质期还不长。

如何获得一个保质期更长的方案呢？一个答案是外包出去，你看中东的国防都可以外包。但很多读者想要自己解决方案。

**那么一个常用的思路就是：提升抽象程度，寻找一个更稳定的抽象层面，然后对它以下的内容进行自动适配/生成。**这在IT领域中不是什么新的想法，Java就是案例，当初的宣传就是“*一次*编写，到处运行”（Write once, run anywhere）。因为每个平台都有自己的特性和汇编语言，想要在一个更稳定的层面进行开发和积累业务逻辑，那么就构建一种稳定的高级编程语言抽象，然后把这之下的部分弄成按需适配，当时没有AI编译器，所以是给每个平台单独编写JIT runtime。

那么Harness之上还有什么更抽象的层面呢？一个答案是：生成Harness的方法论，或者说生成Harness的Harness。

当然这并非万灵药，因为你得能生成接近于原来方案的结果，才算得上是一个更可迁移的替代。否则它只是一个廉价的下位替代方案，当然读过《创新者的窘境》的读者会知道：这也很好了，只是等他成熟需要时间和耐心。

**从Harness变成从高层Harness生成Harness，缺了什么呢？缺的是解决当前问题的****最佳实践****的经验，**这被不少人笼统地称为know-how。这个信息并非不可获得的，如果是一个公开知识比较多的领域，这个know-how很可能已经被模型所知晓，那么就可以期待模型生成Harness时自动关联相关的知识。如果模型不能自主召回，但有公开的信息，也可以依赖于模型进行调研。

那么剩下的场景呢？如果模型的智力强大到能够根据当前场景推理出最佳实践，则也可以，这一般被称为第一性原理思维。

剩下的部分就只能指望用户进行反馈了，对于用户并非该领域专家的场景，产品效果就是退化了。

但所谓的产品效果退化是一个伪问题，大部分用户用不到专家为其定制开发的产品，大部分开发者也不能做到在大部分领域都专业。所以对于通用性产品来说，实际上只要我们比用户已经能使用明白的产品一般交付的效果明显更好就可以了。注意这里是普通用户的使用模式，而不是一些谙熟一些AI产品、Agent特性的专家才能挖掘出的效果。

实际上这个模式曾经出现过。Manus至于ChatGPT，就能对于一般用户交付更好的效果。熟练使用Claude Code的人不用Manus，但大部分人不是。

# 3、绝大多数方案都有窗口期

当然这种方式也不是永生的。

模型厂也可以把这种方式学进去，如果有人做出一个这方面的benchmark并流行，那么模型厂把它训进去的速度就会更快。

但目前来看，Claude Code和Codex都没有开始动这块。我们还有时间，至少是半年，有可能1年。

考虑到这类通用Agent产品已经成了各家模型厂收用户case的关键途径，只要模型厂对应的Agent产品没有实现这点，那么这个窗口期就会持续。

GenAI应用圈，每半年都会打开不同的窗口期，赶上了才能实现提升一个层次。

## 个人阅读笔记

### 文章结构拆解

Prompt/Workflow 会随模型换代而过时（已知事实）→ 类比推演：Harness 没有豁免理由，同样会过时（Opus 4.6→4.7 的 RL 范式变化为实证锚点）→ Harness 层不适合做长期资产积累 → 解法是提升抽象程度，在 Harness 之上构建“生成 Harness 的方法论”，类似 Java JVM 的“一次编写、到处运行”逻辑 → Know-how 来源拆为三层（模型已知 / 模型搜索 / 用户反馈），剩余场景的产品效果退化被定义为“伪问题” → 该方案自身也有窗口期，模型厂尚未跟进，估计半年到一年 → 文末转入创业合作招募。

核心论点：Harness 层面对模型迭代不具备长期积累价值，下一阶段的竞争力将从手写 Harness 上移到自动生成 Harness 的方法论，这个窗口期大约半年到一年。

### 值得带走的

**技术资产与技术债的区分不在于东西本身，而在于它对模型迭代的敏感度。** 文章把 Harness 热潮中的隐性成本拎了出来：不是所有攒下来的配置和流程都是资产，那些依赖模型具体行为的东西（特定的 Prompt 措辞、Workflow 编排）半衰期以模型版本为单位。这个区分比文章自己给出的“全盘否定 Harness 积累价值”更有解释力。结合交叉阅读可以进一步拆分：会过时的只是模型行为敏感的 Harness 上层配置，而验证体系、上下文架构、确定性工具链这些模型行为无关的基础设施会复利。

**“提升抽象层级”是 IT 领域的通用解题框架，但在 AI 时代有新的适用边界。** 文章用 Java JVM 类比来论证“生成 Harness 的 Harness”的合理性，这是一个精准的认知脚手架。但拿来类比的 Java 有一个关键前提：底层平台的差异性是有界的、可穷举的。LLM 的行为变化是否同样有界可穷举，文章没有论证，这决定了类比能走多远。

**窗口期的判断提供了一个实用视角：不是“这个方案永远有效”，而是“这个方案在下一个范式到来前有效”。** 文章承认自己的方案也有保质期，不自洽为永恒解。这种短周期思维在 GenAI 应用圈有其现实基础：每半年打开不同的窗口期，赶上才能上一个台阶。

### 行动指导

1. **把你写的 Harness 拆成两层来维护。** 模型行为敏感的上层（Prompt 措辞、具体 Workflow 链）当耗材，定期更新、不过度优化。模型行为无关的下层（验证标准、上下文分层架构、确定性工具链）当资产，持续积累。每次模型升级后先跑一遍下层验证，看哪些上层配置需要重做，而不是全线推倒。

2. **“怎么判断做对了”比“怎么做”更值得写进规则文件。** 给 AI 的导航信号不是更精巧的 Prompt，而是可执行的验证标准。测试、类型检查、lint、golden case 这些确定性验证，模型越强越需要。没有它们，你就是在做 AI 出错和 AI 修改之间的反馈搬运工。

3. **把你反复做的判断外化成机器可读的文档。** 你觉得某种写法不好、某条边界不能碰、某种抽象层级不对，这些判断如果只留在你脑子里，AI 每次新会话都会重蹈覆辙。写进 AGENTS.md、写进测试用例，写一次，未来所有会话继承。文档更新的动力来源会自然切换：不是因为“需要写文档”，而是因为“不写就会继续出错”。

4. **按场景选 Harness，不追求统一。** 长会话深度任务用擅长长上下文管理的，批量并行任务用擅长吞吐量的。这不是混乱，是承认运行时层的每项设计都在同时做能力和壁垒，没有通用标准。

5. **给“感觉快了”装一个测量。** 人的体感记住了生成的快，忽略了理解和修正的慢。至少要有一条硬指标（实际完成时间、返工轮次、回滚频率），不让体感偏差驱动工具选择。

### 存疑

“生成 Harness 的 Harness”停留在概念层，未给出任何架构颗粒度。它需要输入什么、输出什么、生成质量怎么 eval，全部留白。如果生成的结果不能接近手写 Harness 的效果，按作者自己的标准它就只是一个廉价下位替代。而文章没有论证这个跨越是可行的。

三层 Know-how 来源缺乏操作性判据。什么时候一个领域属于“公开知识多可以自动关联”，什么时候需要“第一性原理推理”，没有区分标准。这会导致设计“生成 Harness 的方法论”时无法判断一个具体场景该走哪条路径。

“产品效果退化是伪问题”的论证有偷换。作者把“退化是否客观存在”替换为“退化是否影响商业可行性”（多数用户用不到专家产品，所以不是问题），绕过了对退化程度本身的评估。如果退化幅度大到普通用户也能感知，这个论证就站不住。

窗口期估算缺少方法。半年到一年的判断基于“Claude Code 和 Codex 目前都没做”，但厂商同时在另一个方向用力：把 Harness 私有化（双面合同逻辑）。两条路线不是先后关系而是并行竞争，单纯用“还没做”作为窗口期依据不够。

文章没有面对一个结构性问题：如果“生成 Harness 的 Harness”跑在闭源商业模型上，Know-how 的获取和数据飞轮的闭环在架构层面被切断（Skill 作者拿不到使用数据，数据全部流向模型提供商）。这个第三方通吃结构会让“生成 Harness 的方法论”变成一个无法自迭代的系统，与它声称的“可积累”属性矛盾。
