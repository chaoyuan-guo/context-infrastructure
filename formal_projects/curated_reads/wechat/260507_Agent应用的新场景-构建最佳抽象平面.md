# 1、最佳抽象平面

要讨论的视角是如此的抽象，以至于用来打比方的例子我都得先解释一番。首先要介绍的，就是标题中最佳抽象平面该怎么理解。

这个比方其实源于线性回归，简单来说就是给一些数据点，然后寻找一条直线来最好的近似它们。说实话我觉得到这里大概就卡住了不少读者，但本文也不想展开太多关于线性回归的介绍，所以如果读者在此就感到困惑，请考虑放下本文用ChatGPT去了解一下线性回归。

如果我们考虑的不只是二维数据点的拟合，那么这个就扩展到找出一个超空间中的超平面来近似数据点。我认为相对比较容易想象且有足够直觉性的例子是3**维空间中用平面来拟合3维数据点**，这也就是为什么这里叫做平面。

接下来的问题是，这里的抽象平面是指什么。

在很多时候，无论是人还是Agent，都在处理一些足够复杂的问题，以至于目前已经数字化的材料和Context不完整，但也不是完全没有信息。这里的一条线是，试图强迫用户提供更多的Context、试图接入企业内更多的系统等等。这是一条路，但改变用户和组织的成本实际上很高，很多时候用户/客户就用脚投票了。我们是否还能做得更好呢？

想象你是一个刚入职的员工，你的领导给你了一些碎片的文档和材料。这时候人是怎么做的呢？其实首先是尝试从这些不完整的材料中构建自己对于这个问题/环境/工作的理解，在自己的认知体系中形成一个完整的认知。如果把它写出来就是一个整体认知的文档。而这就被称为/类比作抽象平面。

**这个抽象平面是你基于已有的碎片材料推断得出的，虽然并不是所有信息/判断等都直接由你获得的材料告诉你，但你能够通过这些碎片的材料来推测这个整体环境是什么样的、流程是什么样的、各个人的角色是什么样的等等。**当然这里有一部分是猜测，并不是有着十足的把握，但对于你理解当前环境和如何做行动则很重要。

当然**由于信息是不完备的、模糊的、甚至看似冲突的，**所以你未必能找到唯一一种看起来最可能的“抽象平面”，可能有多种可能的认知方式、或者说事实情况。然后你开始找你的领导和同事进行沟通，确认到底是什么样的情况，从原来少数的可能情况中选择/修正最后得到你心中的事实情况，也就是从多个可能的抽象平面中找出最符合事实的那个。

**我们为什么要做这样的事情呢？用GenAI应用层的话来说是：可以最小化索取Context的量。本质上是一种用****算力****换取降低索取Context量的方式。**

那么这里的最佳抽象平面的最佳该如何理解呢，特别是在确认信息之前？可以把这里的最佳理解为最可能，也就是说最符合你已有认知先验的认知。当然这个最可能并非数学上的最大值，更接近于极大值，可能有多个，只要它们的概率都不能被忽略就需要纳入考虑。

# 2、构建最佳抽象平面的成本较高

人在融入一个新环境中时，一大块的心智消耗就是熟悉过程，这里就包含了这个抽象平面的构建过程。

对于人类来说，构建抽象平面不光是一个重推理的过程，而且还是一个调整自己的习惯与直觉的过程，因为新的环境不是自己之前熟悉的方式，自己之前的直觉和认知方式可能都并不适合新环境、甚至与新环境有明显的冲突。

有确定目标且高心智成本的事情，更适合交给Agent来做。

构建最佳抽象平面虽然不算是完全有确定的目标，但目标答案还算相对稳定一些。所以它也比较适合Agent。**不过目前这对于Agent来说也并非一件容易的事情，不光难度大、需要反复推理的时间也长，而且过程中还要考虑到大量的不确定性，不是基于一个确定的Context来推理。**

# 3、应用场景：沟通

前面提到了，这种方式的价值就是降低Context索取量，以及让提问者看起来没有那么傻或者不懂。

所以这种方式可以用来降低与用户的沟通量，但对于过于复杂的问题，目前Agent进行抽象平面的构建时间还很长，交互延时无法接受。

但如果是帮用户对于甲方或领导的任务进行分析，这个时间就还尚可接受。而且让用户“看起来没有那么傻”是一个真需求。

# 4、应用场景：预测

沟通应该是这种方式最主要的使用场景，但它也有别的用途，这是场景就小了一些。

本质上这种方式实际上是基于已有材料构建了对于这个环境的概率模型，而且是白盒的模型，某种意义上有点像是概率图的那种感觉（但并不是）。

所以这种模型原本最主要的用途是用于预测，或者是对于已有不能完备观测的事物进行估计。所以在金融、旁观预测等场景也是适用的，或者说是强需求的。

## 个人阅读笔记

### 文章结构拆解

文章的论证链条是：真实任务中的 context 往往不完整 → 强迫用户或组织补齐 context 成本很高 → 人类在进入新环境时会先基于碎片材料构建整体认知 → Agent 也可以通过重推理构建这样的暂定认知结构 → 这种方式本质上是用算力换取更少的 context 索取 → 因为构建过程需要处理信息缺失、模糊和冲突，所以适合交给 Agent → 主要应用场景是降低沟通成本，其次是预测和不完备观测下的估计。核心论点：Agent 的一个新价值点，不是继续索取更多 context，而是在有限材料下构建可行动、可校正的最佳抽象平面。

### 值得带走的

**最佳抽象平面。** 这个概念最有解释力的地方，是把 context engineering 从信息供给问题推进到了认知补全问题。很多 AI 应用默认的解法是接更多系统、同步更多资料、让用户补充更多背景，但真实世界里的 context 永远不完整。组织惯性、隐含规则、人的偏好、历史包袱和真实流程常常没有被写下来。最佳抽象平面提醒我们，Agent 需要的不只是读到资料，还要能基于碎片资料推断背后的结构，并把这种推断用于下一步行动。

**用算力换 context。** 这是本文最值得记住的经济学判断。传统路径是用用户时间和组织改造成本换取更多上下文，本文提出的是用 Agent 的推理成本降低上下文索取量。这个转变很重要，因为改变用户行为和企业系统接入成本很高，而算力成本相对可下降。真正的问题变成：哪些背景必须向用户确认，哪些可以由 Agent 先形成候选假设，再通过少量关键问题校正。

**多候选世界模型。** 文章隐含但没有充分展开的一点是，最佳抽象平面不应该是单一结论，而应该是一组候选解释。信息不完备时，最合理的做法不是让 Agent 自信输出一个看似完整的判断，而是维护多个可能的认知模型，标注各自依据、置信度、冲突点和待验证问题。这样才能把推断和幻觉区分开。

**从 RAG 到结构推断。** 结合 RAG、Wide Research 和 Harness 相关文章看，本文的位置很清楚：RAG 解决已经被写下来的知识如何进入模型，Wide Research 解决大量碎片如何被横向处理，Harness 解决 Agent 在什么环境里执行，最佳抽象平面则解决碎片材料背后的结构如何被推断。它不是 RAG 的替代，而是 RAG 之后的一层认知建模。

**沟通质量的新标准。** 本文把沟通场景放在最前面，这一点很现实。好的 Agent 不应该只是少问问题，而是少问低价值问题。它应该先形成暂定理解，然后只问那些能最大幅度区分候选解释的问题。评价这类 Agent 的标准，不是它显得多懂，而是它能否让用户用更少反馈校正关键假设。

### 行动指导

1. **先建模，再追问。** 遇到上下文不完整的任务时，不要马上要求用户补齐所有背景。先让 Agent 基于已有材料输出当前理解、证据依据、候选解释、不确定点和关键追问。人的反馈应该集中在校正模型，而不是从零讲背景。

2. **把假设显式化。** 以后给 Agent 做任务分析时，要求它区分事实、推断和猜测。尤其是涉及组织流程、客户真实意图、权限边界和历史决策时，合理解释不等于事实。所有关键推断都应该带依据和置信度。

3. **用最小问题集确认关键变量。** 追问用户前先判断每个问题能排除哪些候选解释。不能减少不确定性的背景问题先不问。一个好的问题应该让后续行动方向发生明显变化，而不是只是让 Agent 的上下文更厚。

4. **把 Wide Research 和抽象平面分开做。** 做调研时先用分治方式收集和处理碎片，再集中构建整体解释。不要把多个 summary 拼接当成分析。真正的分析要回答这些碎片背后有什么结构、哪些变量在驱动结果、哪些解释仍然缺证据。

5. **把验证机制放进抽象平面。** 构建认知模型之后，要列出哪些后续反馈可以证实或推翻它。沟通场景可以看用户纠正了哪些假设，预测场景可以做后验校准，工作流场景可以记录哪些判断导致了错误行动。没有反馈更新，抽象平面会退化成高级幻觉。

6. **沉淀被验证过的抽象。** 临时任务中被用户确认过的组织规则、流程关系、人物偏好和风险边界，应该写回长期 context、AGENTS.md、skill 或项目文档。最佳抽象平面适合 cold start，但验证过的抽象应该沉淀为后续 Agent 可直接使用的机器可读上下文。

7. **给 Agent 设计停止条件。** 如果关键假设未验证、信息冲突无法消解、操作不可逆或权限边界不明，Agent 应该停下来确认，而不是带着错误抽象继续行动。会停是最佳抽象平面系统可靠性的组成部分。

### 存疑

文章对最佳的定义仍然偏松。文中把最佳解释为最可能或最符合已有认知先验，但实际产品里最可能、最有用、最符合事实、最节省沟通和最低风险并不总是一致。沟通场景可能优先降低追问成本，预测场景优先后验准确率，企业流程场景优先风险可控。没有场景化目标函数，最佳抽象平面容易变成一个难以评估的比喻。

作者没有充分处理幻觉风险。基于碎片材料补全整体环境，本质上就是在缺失处做推断。如果 Agent 没有证据登记、置信度标注、冲突识别和用户校正机制，这种能力会把幻觉包装成成熟理解。尤其在组织和业务场景中，一个看似合理但实际错误的抽象平面，可能比直接说不知道更危险。

文章提到多个可能的抽象平面，但没有展开如何在它们之间选择和更新。真实系统需要维护候选假设集，而不是只输出最可能解释。它还需要知道哪些问题能区分候选解释，哪些新证据会改变置信度，哪些假设一旦错误会导致高风险行动。这里缺少工程闭环。

沟通场景中的让用户看起来没有那么傻是一个真实需求，但也存在产品伦理边界。Agent 可以帮助用户更专业地提出问题，却不应该制造虚假的理解感。好的体验应该是让用户少暴露无效无知，同时清楚知道哪些地方仍需确认。

预测场景被处理得过于简略。作者说最佳抽象平面像白盒概率模型，可用于金融和旁观预测，但预测系统的关键不只是能构建解释，还要能做 backtesting、calibration、base rate 对照和错误归因。没有这些机制，白盒解释很容易变成事后合理化。

文章缺少一个具体案例，导致概念的边界仍不够清楚。最佳抽象平面到底适用于新员工 onboarding、售前需求理解、企业流程诊断、投资研究，还是个人助理场景，不同应用会需要不同输入、输出和评估方式。后续如果要产品化，最先需要补的不是更宏大的理论，而是一个可跑通的最小场景。
