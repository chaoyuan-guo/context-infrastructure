# 为什么所有人都在学名词，但真正拉开差距的是动词

我们在教 AI 的过程中，反复遇到一个让人沮丧的现象。

每次我们讲 Context Architecture、讲任务分解、讲人机分工的判断逻辑，台下的人都在点头。但课后收到最多的问题永远是：能不能多讲讲 LangChain？能不能教一下 RAG？能不能加一节 fine-tune 的课？

我们在企业培训中遇到过更直接的版本。一位资深制作人当面挑战我们："你们有没有做过超出 Demo 的复杂项目？"——言下之意，你们连复杂项目都没做过，凭什么教我们？

这两件事表面上不一样，但底层是同一个问题。

## 市场在买名词

LangChain 是一个名词。RAG 是一个名词。Fine-tune 是一个名词。Harness 是一个名词。

名词有几个特征让人天然觉得"这是值得学的东西"：

**名词有边界。** 它有 GitHub 仓库，有文档页面，有版本号。你要么会，要么不会，判断起来非常干脆。

**名词可以被考核。** 写在简历上、写在技能栏里、在面试中被问到。"你会 LangChain 吗？"这个问题有明确的对错。

**名词自带"硬技能"的暗示。** 人的大脑有一个很深的倾向——能命名的东西才是"真实"的东西。一个有名字的技术，听起来就比一个没名字的方法论更值钱。

所以当你告诉市场"我们教的是 AI 方法论"，市场把它自动归类到了"软技能"那个货架上——和"沟通技巧""领导力""思维框架"放在一起。那个货架上的东西，人们觉得有道理，但不觉得紧迫，不觉得是非学不可的。

而"LangChain""RAG""fine-tune"被放在了另一个货架上——"要学的技术"。那个货架上的东西，人们愿意付钱，觉得学了就有竞争力。

**这是一个分类错误，但它在认知上极其顽固。**

## 但真正决定成败的是动词

我们来看一个现实：2025 年，大量的人已经学会了 RAG 的原理，能搭一个 demo，能在技术面试中把流程讲清楚。但你问他们：在一个十万行代码的真实项目里，你的 RAG 管用吗？

大多数人沉默。

因为问题从来不是"你会不会 RAG"。问题是：

- 你的上下文管理做得好不好——该加载的信息加载了吗？不该加载的噪音过滤了吗？
- 你的任务分解做得对不对——一个大任务直接扔给 AI，它就会乱来，你怎么拆？
- 你的人机分工判断准不准——这个环节该让 AI 独立做，还是需要人介入？
- 你的产出一致性有没有保障——二十个 AI 会话同时改你项目的不同部分，怎么保证它们不打架？

这些全是动词。分解、判断、管理、路由、诊断、沉淀。没有一个有 GitHub 仓库，没有一个能 pip install，没有一个能写进简历的技能栏。

但它们才是决定你的项目成不成的东西。

**名词是零件。动词是组装能力。你买回来一堆最好的零件，不会组装，它就是一堆零件。**

## 为什么人看不到动词的价值

这不是智商问题，是认知结构的问题。具体来说，有三层原因：

**第一，人只能看见自己当前的瓶颈。**

一个还没有在复杂项目中被 AI 搞崩过的人，他的心理模型是线性的：我现在不会用 AI → 因为我不懂这些工具 → 学会这些工具 → 我就能用 AI 了。

在这个模型里，瓶颈是"工具知识的缺失"——几个他还不认识的名词。你告诉他"不对，你缺的是方法论"，他根本理解不了，因为他还没遇到过"工具全都会用但项目照样失控"的体验。

这和软件工程的历史一模一样。初级工程师觉得难的是学 React、学 Kubernetes，以为学会框架就能写好软件。只有在复杂系统中被架构问题反复毒打之后，才意识到框架从来不是瓶颈，设计才是。你无法在他被毒打之前让他相信这一点。

**第二，好的方法论在起作用时是隐形的。**

项目做成了，大家觉得"AI 真厉害"或"我们团队真强"。没有人会说"是因为我们的 Context Architecture 做得好"。

项目做崩了，大家的归因是"工具不好用""AI 还不成熟""我们的需求太复杂"。没有人会说"是因为我们没有做好上下文管理"。

工具的问题是可见的——报错、crash、出不来结果。方法论的缺失是不可见的——你不知道你不知道。所以**人们永远在为可见的问题买单，不为不可见的问题买单。**

**第三，名词制造了一种"学会了"的错觉。**

看完一篇 RAG 教程，你觉得自己会了。听完一场 LangChain 的分享，你觉得自己懂了。名词给人一个清晰的 checkpoint：学之前不会，学之后会了，进步是可感知的。

但方法论没有这种 checkpoint。你不会在某一天突然"学会了上下文管理"——它是一种在实践中逐渐生长的判断力。这种渐进感让人觉得"这不就是经验吗？我做多了自然就会了"。

"做多了自然就会"也许是对的。但有方法论指导着做和没有方法论盲目做，积累速度差十倍。这也是经验——但你没经历过这个对比，你就没法理解这个差距。

## 我们在教学中的真实困境

坦白说，这个问题一度让我们非常沮丧。

我们花了大量时间去打磨方法论体系——Context Architecture 怎么分层、任务分解的具体规范、人机分工的判断框架、Skill Files 怎么写才能让 AI 的产出稳定可复用。这些东西是我们在真实的企业培训、真实的产品开发、真实的学员项目中一轮一轮验证出来的。

但我们总会遇到这样的反馈："能不能多讲讲具体工具？""方法论我都懂，但我想学点硬的。"

你说方法论你都懂。那我问你：你的 Skill File 是什么结构？你的 Context Stack 分了几层？你的 Delegation Spectrum 画过没有？你在 AI 产出不好的时候，做过 Failure Trace 吗——是 context 不够，还是指令不清，还是任务该拆没拆？

这些问题大多数人答不上来。不是因为菜，是因为这些能力从来没有被当作"要学的技术"来对待。它们被归类到了"软性提升"里，和"工作经验""悟性""sense"放在一起，变成了一种你觉得自己早晚会有但永远不急着学的东西。

而这恰恰是最贵的错觉。

## Garry Tan 的 "Thin Harness, Fat Skills"

Y Combinator 的 Garry Tan 最近写了[一篇文章](https://x.com/garrytan/status/2042925773300908103)，核心观点是：用同样模型的人之间，效率差距可以达到 100 倍。差距不在模型智能，在架构。他把这个架构总结为五个概念：Skill Files、Harness、Resolvers、Latent vs. Deterministic、Diarization。

注意他做了什么——他把一套方法论里的每一个组件都变成了名词。

Skill File 不叫"把你的经验写成文档"。Resolver 不叫"根据任务类型加载不同的上下文"。Diarization 不叫"让 AI 读完所有材料写一份综合判断"。每一个都有一个专有名称，有清晰的定义，有具体的用法。

结果呢？工程师社区一读就觉得："这是我要学的东西。"

他做的事情，本质上就是**给动词穿上了名词的外套**。方法论还是那个方法论，但因为每个组件都有了名字，它就从"软性认知"那个货架跳到了"硬核技术"那个货架上。

这是很棒的认知接口设计，值得我们学习。

## 名词和动词不是对立的

我不是在说名词不重要。RAG 在某些情况下值得学（**#Why We Don’t Teach RAG: A Deeper Dive into Its Principles and Future** )。LangChain 在某些情况下有用（**#为什么学习Agentic AI的第一步是忘记所有框架？ ** ）。Harness 的架构设计当然是关键技术。

我说的是：**名词是地图上的地标，动词是你在地标之间走的路。你收集了所有的地标但不知道怎么走路，你哪儿也到不了。**

反过来也成立——你光会走路但不认识任何地标，也走不到目的地。

真正的能力是：知道这些名词（工具、框架、概念）各自解决什么问题，**并且**知道在真实项目中怎么把它们组装起来（分解、判断、路由、诊断、迭代）。

名词给你零件。动词给你组装能力。你两个都需要。但市场只给名词定价，不给动词定价——所以大多数人的名词远远多于动词，零件堆了一地，什么也没造出来。

## 对你意味着什么

如果你正在学 AI，问自己一个问题：

**上一次让你真正变强的，是学会了一个新工具，还是在一个真实项目里搞砸了然后想明白了为什么？**

大多数人的诚实回答是后者。

那个"想明白为什么"的过程，就是在练动词。问题是，大多数人把这个过程当作"交学费"，而不是"在学习一种技术"。它没有名字，没有课程，没有证书，所以它不被当作技术。

但它就是技术。只不过是一种还没有被充分命名的技术。

我没办法对抗人性，所以我能做的，就是给这些动词命名。Context Architecture、Context Stack、Context Resolver、Delegation Spectrum、Failure Trace、Skill Files、Agentic Loop——这些不是营销术语，是我们在大量真实教学和项目实践中提炼出来的、可以被学习、可以被练习、可以被检验的具体方法。

给它们命名，不是为了让它们听起来更唬人。是因为，没有名字的东西不会被认真对待。

一旦它有了名字，你就可以问自己："我的 Context Stack 搭了没有？""我的 Delegation Spectrum 画了没有？""上次 AI 产出不好，我做 Failure Trace 了吗？"——你就有了一个个具体的、可以打勾的检查点。

这就是名词的力量。不是因为名词本身有魔法，而是因为它让动词变得可见、可学、可考核。

这也是为什么，我们一直坚持教方法论，同时也在不断地给方法论里的每一个组件创造清晰的名字。

**因为最终，名词和动词不是两个对立的选择。最好的状态是：学名词来获取零件，练动词来获取组装能力，然后给动词也起个名词——这样它才不会被遗忘。**

### Jeremy Zheng
*2026-04-15*

认真读完之后，也在思考一个问题：技术一时一换，真正不变的到底是什么。

很喜欢你把技术名词和动作比作“地图上的坐标和道路”。不同的技术名词，就像分布在一张地图上的不同坐标，有些彼此接近，可以归在同一个问题集合里（更像是地图上的一个区域）；有些则相距很远，对应完全不同的问题。而这些坐标之间，并不是孤立存在的，它们通过“道路”连接起来——这些道路，本质上就是不同技术在解决同一个更大问题时形成的关系和路径。

在这个框架下，相比“这个坐标是什么”，更重要的是——如何到达这个坐标，以及为什么要到达它。因为新的技术（坐标）变化很快，但问题本身（区域）变化是相对慢的。

还联想到对于“问题”的定义是： 当前状态（坐标）和理想状态（坐标）的差距；“解决问题”是：如何从当前状态到达理想状态（路径）。

再往下想，“如何在这些道路上行走”，其实就是我们在解决问题的过程。
所以所谓的能力训练，不是去不断积累更多坐标点，而是逐渐具备一种能力——在这张问题地图中，能够识别区域、设定目标、规划路径，并在过程中根据实际情况不断调整路线的能力

这种能力，相对来说是更稳定的。
技术会变，坐标会换，但地图的结构和“走路的方式”不会轻易变化。

## 个人阅读笔记

### 文章结构拆解

教学反馈的悖论（讲方法论听众点头但只为名词买单）→ 现象命名（市场只买名词，因为名词有边界、可考核、自带"硬"信号）→ 反命题（决定 AI 项目成败的其实是一组动词：context 管理、任务分解、人机分工、产出一致性）→ 三层成因（人只看见当前瓶颈、好方法论起作用时隐形、名词制造"学会了"的错觉）→ 教学困境（"我都懂方法论"是最贵的错觉，可用一组诊断问题证伪）→ 借势例证（Garry Tan 把方法论组件全部命名，让动词穿上名词外套）→ 辩证收口（名词与动词不是对立，是地标与道路、零件与组装）→ 行动方案（给自己的方法论批量造词）。

核心论点：市场只为有名字的东西定价，但真正拉开差距的能力大多还没有名字；最优策略不是在学名词和练动词中二选一，而是练动词并主动给动词命名。

### 值得带走的

**货架错配**。文章把"方法论卖不动"这件事从"我们没讲好"提升到了"市场分类系统的结构性偏差"。同一个东西放在硬技能货架上有人愿意付钱，放在软技能货架上就被归类成"早晚会有但不急"的东西。这个概念的解释力在于，它把一个看似教育者能力问题的事，重新定义成了认知接口设计问题。值得记住是因为，它适用范围远超 AI 教育，任何"东西本身有价值但卖不动"的场景都可以先问一句：是不是放错货架了。

**方法论的隐形性**。好的方法论起作用时是不可见的，项目做成被归因到团队和 AI，做崩被归因到工具不好用。这个不对称导致动词永远拿不到信用。这一点的可怕之处在于不可证伪：你没法证明"如果没有这套方法论项目就会崩"，所以方法论永远在为可见的问题让路。

**名词制造的"学会了"错觉**。看完一篇 RAG 教程觉得自己会了，但项目里 RAG 不管用时不会觉得自己"还没学会"，会觉得"工具有问题"。名词给学习闭环提供了清晰的 checkpoint，动词没有这个 checkpoint，所以学习者会无限留在名词上而不察觉。这解释了为什么知识焦虑的人持续学新框架但能力不增长。

**给动词命名 = 铸造可结算单位**。把这一点和 260420 Harness Engineering 一文对照：harness engineering 起飞不是因为内容更新，而是因为这两个词的组合给一组散落的动词提供了可以装进招聘 JD 和服务合同的最小单元。命名的本质是让能力可以被定价、被招聘、被追责。这个视角让"造词"从一个市场营销动作变成了认知工程动作。

### 行动指导

1. **换掉自我评估的问题**。不要再用"我会哪些工具"来判断自己在 AI 上的进展，换成一组动词性的诊断问题。比如：上次 AI 产出不好，我能不能定位到是 context 不够、指令不清，还是任务该拆没拆。能不能说清自己的 Context Stack 分了几层、Skill File 是什么结构、Delegation 边界画在哪里。如果这些问题答不上来，就说明动词层面的能力没有真正建立，无论学过多少框架都不算。

2. **给学新工具配置硬约束**。每学一个新名词都要配套一次真实使用，并且在使用之后写一份复盘，记录它解决了什么问题、在哪里失灵、跟已有工具怎么组装。没有这个配套动作就不算学过，只算听说过。这一条的意义在于强制把名词和动词绑定，避免零件越堆越多但永远造不出东西。

3. **给自己的隐性能力造词**。每当意识到自己做某件事比同事顺、但说不清具体做了什么，就停下来给这个动作命名。命名不是为了听起来唬人，是为了让这件事变成可以被自己反复调用、被别人传授、被简历承载的最小单元。没有名字的能力会被自己遗忘，也无法被市场识别。

4. **在记录中区分名词笔记和动词笔记**。名词笔记记的是"这个工具是什么、怎么用"，动词笔记记的是"在 X 场景下我做了什么判断、为什么这么判断、结果怎样"。两类笔记都要留，但要清楚动词笔记才是个人复利的真正来源，名词笔记的半衰期会越来越短。

5. **警惕"做多了自然就会"**。这句话部分正确，但有方法论指导地做和盲目做，积累速度差很多。具体做法是每个项目结束后强制做一次 Failure Trace 或 Success Trace，把判断显性化，否则经验只是在身体里滑过去，不会沉淀成可复用资产。

### 存疑

文章主张"给动词命名"是解药，但没有讨论命名的副作用。260420 Harness Engineering 一文已经观察到 prompt engineering、context engineering 这类后缀正在贬值。命名一旦进入市场就会被简化、被滥用、被稀释，所以命名是消耗品而不是一次性解决方案。本文对这个腐烂周期没有展开，留下了"造完词之后怎么办"的空白。

更深的张力是和 260415《良质与 AI》的对比。后者主张动态良质一旦被命名就坍缩为静态规则，失去原本的"活"。如果这个观点成立，那么本文的"给动词命名"对于真正高阶的判断性能力来说可能是降维操作。两者并不矛盾但侧重相反，本文对"哪些动词适合命名、哪些应该保持示范态"没有区分。

文章把市场偏好归因到"认知偏差"，但其实还有制度性原因：名词便于追责（学了 X 还做不出来怪你），动词不便追责。HR 和企业培训买家结构性需要可考核的标签不只是因为认知懒惰，而是因为他们的 KPI 和组织流程要求这种形态。这一层政治经济学的解释没有展开，导致"换个市场就行了"成了一个潜在但未被回应的反驳。

最后一个隐藏假设是"硬货架就是好货架"。文章想让方法论从软技能货架搬到硬技能货架，但硬货架的评估机制（可考核、可证书化、可面试）本身就和动词的本性冲突。把动词搬上硬货架可能让它进入流通，但也可能让它被错误的评估方式扭曲。这一层张力作者没有正面处理。

Garry Tan 模式的可复制性也存疑。Tan 能让一组名词流通，部分依赖他在 YC 生态的分发权力。一个普通教育者或者个人，即使造了好名字，也未必能让市场接收。文章把"造词"作为可行解给出来，但低估了分发渠道这个变量。
