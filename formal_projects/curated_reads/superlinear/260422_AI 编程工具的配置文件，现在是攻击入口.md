# AI 编程工具的配置文件，现在是攻击入口

> 来源：<https://www.superlinear.academy/c/news/ai-8613e5>
> 作者：Superlinear Academy
> 发布日期：2026-04-22
> 平台：Superlinear Academy

---

过去 12 个月，安全研究者在 GitHub Copilot、Claude Code、Cursor、Amazon Q 和 OpenAI Codex 上各自独立发现了一批 prompt injection 漏洞，至少 8 个 CVE，CVSS 最高 8.8。攻击方式高度一致：在项目的配置文件或代码注释中嵌入自然语言指令，AI agent 读取后将这些数据当作指令执行。`.cursorrules`、`.claude/settings.json`、`.github/copilot-instructions.md`、`AGENTS.md`，这些开发者日常接触的文件，现在可以控制 AI agent 在你的机器上运行什么命令。

所有已知漏洞均已修补。但同类漏洞在所有主流产品上反复出现，修一个来一个。原因是 LLM 处理输入时，system prompt、用户指令、代码注释、配置文件全部是 token 序列，模型内部没有任何机制区分哪些是指令、哪些是数据。这和计算机安全史上反复出现的冯诺伊曼问题是同一件事：指令和数据共享同一个通道，攻击者找到让数据被当作指令执行的方法。只是这一次，分离机制还没有找到。

## 三种攻击模式

这些漏洞的攻击面可以归纳为三种模式。

### 数据变成指令

`.vscode/settings.json`、`.cursorrules`、`.claude/settings.json`、`.github/copilot-instructions.md`、`AGENTS.md`，这些文件在 AI 编程工具出现之前就存在于项目中。开发者对它们的认知是编辑器配置或项目说明，安全级别和 `.editorconfig` 差不多。

AI 编程工具改变了这些文件的实际语义。Agent 读取它们之后，不只是调整代码风格或补全偏好，而是据此决定执行什么操作、调用什么工具、以什么权限运行命令。一个 `.claude/settings.json` 里的 hook 定义会在 Claude Code 启动时以 host 权限运行。一个 `.cursorrules` 能决定 Cursor 在你机器上执行的 shell 命令内容。文件的格式没变（还是 JSON 或 Markdown），在 repo 中的位置没变，但它在系统中的角色从数据变成了指令。这正是冯诺伊曼问题在应用层的具体表现：原来只是被读取的内容，现在可以控制执行流。

8 个公开事件中有 6 个利用的就是这个语义升级。CVE-2025-53773（[GitHub Copilot](https://www.persistent-security.net/post/part-iii-vscode-copilot-wormable-command-execution-via-prompt-injection)，CVSS 7.8）通过 README 中的 prompt injection 让 Copilot 修改 `.vscode/settings.json` 开启自动批准，此后执行任意命令不需要确认，研究者还论证了蠕虫传播性。CVE-2025-59536（[Claude Code](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)，CVSS 8.8）中恶意 settings.json 的 hook 在 trust dialog 弹出之前就已执行。CVE-2026-25725（[Claude Code Linux](https://github.com/anthropics/claude-code/security/advisories/GHSA-ff64-7w26-62rf)，CVSS 7.7）利用了沙箱只对已存在的配置文件设置只读保护、新项目中该文件不存在的条件。Pillar Security 的 [Rules File Backdoor](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents) 用不可见 Unicode 字符在 `.cursorrules` 里藏 injection，编辑器和 diff 中看不到，AI 正常读取。NVIDIA AI Red Team 的 [AGENTS.md 注入](https://developer.nvidia.com/blog/mitigating-indirect-agents-md-injection-attacks-in-agentic-environments/)通过恶意 Go 依赖在 build 阶段覆写 Codex 的配置文件，把供应链攻击转化为 agent 行为劫持。

### 审批通过后的替换

有些工具对安全审批采用"批准一次，永久信任"的设计：用户首次批准某个配置后，即使配置内容被替换也不再重新验证。CVE-2025-54136（[Cursor MCPoison](https://www.tenable.com/blog/faq-cve-2025-54135-cve-2025-54136-vulnerabilities-in-cursor-curxecute-mcpoison)，CVSS 7.2）利用了这个机制：攻击者先在 repo 中提交一个无害的 MCP 配置等用户批准，然后替换为恶意 payload，Cursor 不再验证底层 command 是否变了。审查发生在批准的时间点，攻击发生在批准之后，payload 在审查时是无害的，执行时已经变了。Cursor v1.3 修复后，配置变更会触发重新审批。

### 跨 agent 传播

EmbraceTheRed 展示了[跨 agent 提权](https://embracethered.com/blog/posts/2025/cross-agent-privilege-escalation-agents-that-free-each-other/)：通过间接 prompt injection 劫持 Copilot，让 Copilot 向 Claude Code 的 `.mcp.json` 写入恶意指令。用户下次启动 Claude Code 时自动加载并执行，反向传播同理。前提是多个 AI agent 共享同一个工作目录，且每个 agent 都能写入其他 agent 的配置文件。同一项目里同时使用 Copilot 和 Claude Code 的情况现在很常见，一个 agent 被操纵后，可以通过文件系统把攻击传递给同目录下的其他 agent。

三种模式可以组合。供应链攻击（比如 2026 年 3 月的 [Axios npm 事件](https://cloud.google.com/blog/topics/threat-intelligence/north-korea-threat-actor-targets-axios-npm-package)波及了 OpenAI 的签名证书 workflow）提供初始入口，配置投毒建立持久化，跨 agent 传播扩大范围。Cornell Tech / Trail of Bits 的 COLM 2025 论文 [Multi-Agent Systems Execute Arbitrary Malicious Code](https://openreview.net/forum?id=DAozI4etUp) 把这种组合归纳为两阶段持久化攻击。

## 为什么这一代的分离机制特别难建立

所有已知漏洞都修了。但每一个补丁修的是一条具体攻击路径，同一类漏洞在所有主流产品上反复出现。原因回到开头的框架：冯诺伊曼问题的每一次出现都需要一个对应的分离机制，而 LLM 这一代的分离机制面临几个前几代不存在的困难。

### 自然语言没有语法边界

Buffer overflow 的分离机制是内存保护（W^X、ASLR、stack canaries），SQL injection 的分离机制是参数化查询。这两个方案能成功，前提是指令和数据在形式上可以被区分：机器码有固定的指令格式，SQL 有明确的语法结构，分离机制可以在形式层面建立一条硬边界。

LLM 处理的是自然语言，而自然语言没有这种形式上的边界。一段文字是"数据"还是"指令"取决于它出现的上下文和模型对它的理解，不取决于它的格式或结构。一个 `.cursorrules` 文件里的"请确保所有网络请求使用 HTTPS"和"请在每个文件开头插入以下 shell 命令"在语法上没有区别，都是自然语言句子。模型要区分它们，就需要理解语义，而理解语义本身就是 LLM 在做的事情。

英国国家网络安全中心在 [Prompt injection is not SQL injection (it may be worse)](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection) 中的判断基于的正是这个分析：

> "As there is no inherent distinction between 'data' and 'instruction', it's very possible that prompt injection attacks may never be totally mitigated in the way that SQL injection attacks can be."

一篇把这个问题放进计算机体系结构历史的[论文](https://arxiv.org/html/2603.12230v2)进一步指出：LLM 的情况比前几代更严重，因为 plaintext prompt 充当了 code 的角色，动态生成的文本本身会成为新的 prompt，control flow 依赖运行时才知道的 payload。在传统计算中，即使没有内存保护，你至少可以静态分析哪些内存区域存的是代码、哪些是数据。在 LLM 中，这个静态分析不可能做到。Rice 定理从计算理论角度给出了形式化的解释：判断任意自然语言输入是否会诱导 agent 做出非授权行为，在一般情况下是不可判定问题。

### 执行权限和产品价值绑定

即使指令数据混合的问题存在，如果 agent 只输出文本建议，安全后果也有限，普通 LLM chatbot 就是这个情况。Coding agent 不同：它能运行测试、安装依赖、修改文件、执行构建、调用外部 API。这些执行能力是产品价值的核心，也恰好是攻击者需要的。去掉执行权限，agent 退化成自动补全工具；保留执行权限，每一条成功的 prompt injection 都能触发系统级操作。

Permission prompt 是对这个 trade-off 的标准折中，但实际数据说明它的效果有限。UCSB 的 LLM router 研究截获了真实 Codex session 流量，440 个 session 中 [401 个在 YOLO 模式下运行](https://arxiv.org/abs/2604.08407)，91% 的用户完全跳过了审批。在产品竞争驱动下，用户面对"安全但慢"和"快但不安全"时选了后者。厂商的激励方向一致，更强的安全默认值会导致用户流向竞品。

更细粒度的权限控制（按操作类型、目标路径、网络出口分别授权）是一个改善方向，Claude Code 的 hooks 系统和 Codex 的三级沙箱都在往这里走。但历史上，细粒度权限系统（Android 权限模型、浏览器 CSP）的实际效果一直低于设计预期，原因是用户倾向于选择最宽松的配置。

### 攻击面随 agent 能力自动扩大

前两个困难是静态的：指令数据混合是 LLM 的固有属性，执行权限的 trade-off 是产品设计的约束。第三个困难是动态的：agent 能读取并赋予执行语义的文件范围在不断增长，攻击面随之扩大。

今天的配置文件投毒局限在 IDE 配置和 MCP 定义。MCP 生态是最近的扩展方向：[第一个被发现的恶意 MCP 服务器](https://www.penligent.ai/hackinglabs/ai-agent-security-after-the-goalposts-moved-2/) postmark-mcp 伪装成 Postmark 邮件服务，正常发邮件但每封密送给攻击者，约 300 个组织在发现前已集成到工作流中。OWASP 已发布 [MCP Top 10](https://genai.owasp.org/) beta 版。明天，当 agent 被赋予读取 Slack 消息、处理邮件附件、访问内部 wiki 的能力时，这些内容都可能成为 prompt injection 的载体。冯诺伊曼问题在每一代计算平台上的攻击面都比上一代更大，LLM 也不例外。

GitHub 在设计 Agentic Workflows 安全架构时选了一种顺应这个趋势的思路：[直接假设 agent 已经被入侵](https://blog.bytebytego.com/p/the-security-architecture-of-github)，不试图阻止 prompt injection，而是限制 injection 成功后能造成的损害。Google DeepMind 的一项联合研究得出了类似结论：依赖当前 LLM 架构的 agent [不太可能提供可靠的安全保证](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)，可行的策略是限制 agent 的通用性来换取安全性。这意味着解决这个问题的路径大概率不是"让 agent 更抗 injection"，而是在 agent 的执行权限和可访问范围上做更严格的工程约束，就像内存保护不是让 CPU 更聪明地判断哪些字节是代码，而是直接禁止数据区域被执行。

## 可以做的事

关闭 auto-approve / YOLO mode 是目前性价比最高的单一措施。91% 的 YOLO session 数据说明绝大多数用户在自动批准模式下使用 agent，而多数攻击链的前提条件就是自动批准。

开启沙箱（Claude Code 的 bubblewrap/Seatbelt，Codex 的 Landlock/Seatbelt）可以限制被操纵后命令的损害范围。如果你用的工具支持沙箱但默认没开，手动开。

对 `.cursorrules`、`.claude/settings.json`、`.github/copilot-instructions.md`、`AGENTS.md` 这些文件的 PR 修改，给予和 `.github/workflows/` 同等的审查级别。它们能控制 agent 在你机器上执行什么。

把 `.zshrc`、`.npmrc`、`.env` 里的凭证迁移到 secrets manager。AI 编程工具的 session log 会记录读到的所有文件内容。

CI/CD 中使用 AI agent 时，对所有依赖使用 pinned commit hash 并配置 `minimumReleaseAge`。OpenAI 的 [Axios 事件](https://openai.com/index/axios-developer-tool-compromise/)根本原因就是 floating tag 加上没有冷却期。

## 个人阅读笔记

### 文章结构拆解

AI 编程工具开始读取项目配置、代码注释和规则文件 → 这些文本原本只是数据或说明，现在会影响 agent 的工具调用、命令执行和权限边界 → 攻击者可以把自然语言指令藏进 `.cursorrules`、`.claude/settings.json`、`.github/copilot-instructions.md`、`AGENTS.md`、MCP 配置或代码注释中 → 一旦 agent 把这些数据当作指令执行，就会出现配置投毒、审批绕过、跨 agent 传播和供应链持久化 → 根因不是某个厂商的单点实现，而是 LLM 把 system prompt、用户指令、项目文档和配置文件统一处理成 token 序列，自然语言缺少可靠的指令和数据边界 → 因此防御重点不能只放在让模型识别 prompt injection，而要放在沙箱、最小权限、配置审查、凭证隔离和执行审计上。

核心论点：AI agent 时代的安全边界正在从代码和 API 扩展到 context 与配置文件，凡是能被 agent 读取并影响行为的内容，都应被视为潜在控制面。

### 值得带走的

**配置文件的语义升级**。文章最有解释力的地方，是指出 `.cursorrules`、`.claude/settings.json`、`.github/copilot-instructions.md`、`AGENTS.md` 这类文件的格式没有变，但系统角色变了。过去它们接近编辑器配置或项目说明，现在它们会影响 agent 怎么调用工具、是否执行命令、以什么权限行动。这个概念解释了为什么开发者的旧安全直觉会失效：你以为自己在审 Markdown 或 JSON，实际上是在审 agent 的行为控制面。

**指令和数据共通道**。文章用冯诺伊曼问题解释 prompt injection，比单纯说模型容易被骗更有穿透力。LLM 输入里的 system prompt、用户要求、README、代码注释、配置文件都是 token 序列，模型没有形式化机制保证哪些是指令、哪些是数据。传统 SQL injection 可以靠参数化查询建立边界，LLM 面对自然语言时很难建立同等强度的边界。这个区分值得记住，因为它把防御方向从模型更聪明转向环境更受限。

**执行权限和产品价值绑定**。普通 chatbot 被注入后通常只是输出错误文本，coding agent 被注入后可以读文件、改配置、跑命令、装依赖、调用外部 API。危险并不是 prompt injection 本身突然变新，而是 agent 的价值正好来自攻击者想利用的执行能力。关闭执行权限能显著降低风险，但也会让 agent 退化成补全工具，所以真正的工程问题是如何保留执行价值，同时缩小可造成的损害范围。

**工作目录成为传播介质**。跨 agent 传播这个模式很值得警惕。同一个 repo 里同时使用 Cursor、Codex、Claude Code、Copilot 时，它们共享文件系统，也可能读写彼此的配置文件。一个 agent 被 README、issue 或代码注释注入后，可以修改另一个 agent 会信任的 `AGENTS.md`、`.mcp.json` 或 settings 文件。这里的安全边界不再是单个工具，而是整个 workspace。

**Context infrastructure 的双重属性**。同目录里关于 harness、skills、AGENTS.md 的文章都强调把知识写进 repo 能让 agent 更强。这篇文章补上了另一面：能让 agent 更强的 context，也会成为攻击面。`AGENTS.md` 是协作契约，也是注入入口；skill 是能力积累，也是供应链载体；MCP 和 CLI 是能力接口，也是权限扩散通道。以后评价 context infrastructure 时，必须同时看生产力收益和控制面风险。

### 行动指导

1. **把 AGENTS.md 当控制面审查**。个人使用 Codex 打开陌生 repo 时，先看 `AGENTS.md`、`.cursor/rules`、`.github/copilot-instructions.md`、`.mcp.json` 和 `.claude/settings.json`。重点检查是否要求读取 `.env`、`.npmrc`、SSH key、credentials，是否要求运行不透明脚本，是否要求关闭确认或修改 agent 配置。这个动作应该像看 `.github/workflows/` 一样自然。

2. **不要把 YOLO mode 当默认工作方式**。自动批准适合自己熟悉、权限边界清楚、没有敏感凭证的目录。只要是外部 repo、外部 PR、供应链依赖、包含真实凭证的项目，就回到人工确认模式。效率提升不能建立在完全放弃执行边界上。

3. **区分素材层、规则层和执行层**。文章、笔记、案例可以宽进，因为它们主要提供素材。`AGENTS.md`、skills、workflow 属于规则层，会改变 agent 怎么判断和行动，需要筛选。hook、MCP server、CLI、shell script、auto-approve 配置属于执行层，需要更高审查。把三层内容都当普通文本，是个人工作流里的主要风险来源。

4. **外部 skill 和配置只吸收，不整段信任**。网上复制来的 `AGENTS.md`、`.cursorrules`、MCP 配置和 skill 文件，不应该直接粘进自己的项目。更稳妥的做法是先读懂它改变了什么行为，再拆成小块，只吸收自己明确认可的规则。skill 的价值在于把隐性知识显性化，但显性化之后也变成了可复制的供应链对象。

5. **给自己的 workspace 做 agent control checklist**。每次新增或修改 `AGENTS.md`、skill、MCP server、hook、自动化脚本时，问三个问题：它会让 agent 读什么，它会让 agent 做什么，它出错或被注入后最坏会影响什么。这个 checklist 比记住具体 CVE 更稳定，因为新的漏洞会变，但控制面的位置相对稳定。

6. **把凭证从默认上下文里移走**。`.env`、`.npmrc`、`.zshrc`、本地配置和 session log 都可能被 agent 读到或写入上下文。长期凭证应迁移到 secrets manager，项目目录里尽量只保留短期、最小权限、可撤销的凭证。agent 的 session log 也应被视为可能含敏感信息的材料。

7. **按 agent 隔离工作环境**。如果同一个项目里同时使用 Codex、Cursor、Claude Code，不要默认它们可以互相写配置。至少要意识到 `.mcp.json`、`AGENTS.md`、`.cursor/`、`.claude/` 这些文件一旦被某个 agent 修改，会影响另一个 agent 的后续行为。重要项目中，跨 agent 共享配置应走显式 review。

8. **评估 AI 工具时看安全工程，不只看模型能力**。一个 coding agent 是否适合长期使用，不能只看 SWE-bench 或代码生成能力，还要看沙箱、网络限制、文件权限、命令审批、session log、配置加载规则和审计能力。benchmark 决定它能不能做事，执行边界决定它能不能安全地长期进入工作流。

### 存疑

文章把所有问题统一放进冯诺伊曼问题框架，这个解释很强，但也可能过度压平了不同攻击面的差异。配置文件投毒、审批后替换、跨 agent 传播、恶意 MCP server、供应链依赖投毒，虽然都可以归入指令和数据混合，但具体防御手段分别落在内容审查、变更检测、权限隔离、server trust、依赖治理上。统一框架有助于理解根因，但落到工程实践时还需要更细的分类矩阵。

文章强调自然语言没有语法边界，因此 prompt injection 可能无法彻底解决。这个判断大体成立，但它没有充分区分不同类型的 agent 输入。有些输入确实是自然语言，比如 README、issue、Slack 消息；有些输入可以被结构化和类型化，比如 tool schema、MCP 配置、permission policy、hook 定义。未来一部分边界可能不是在自然语言内部建立，而是通过把高风险指令从自然语言迁移到类型化配置中建立。文章对这个中间路径讨论不足。

文章对 permission prompt 的悲观判断基于 91% Codex session 使用 YOLO mode，这个数据很有冲击力，但还需要拆分场景。个人本地实验、熟悉 repo、CI 环境、企业受管设备的风险分布不同。YOLO mode 的高占比能说明用户偏好效率，但不能直接推出所有场景下 permission prompt 都无效。更精确的问题应该是：哪些场景适合默认拒绝，哪些场景适合批量授权，哪些场景必须使用内容级 approval。

文章给出的行动建议偏向个人开发者和单 repo 维护者，对团队级治理还不够完整。比如团队是否应建立 agent config CODEOWNERS，如何 pin 外部 skill 版本，如何审查子目录 `AGENTS.md`，如何隔离多个 agent 的配置目录，如何对 session log 做 retention 和脱敏，这些都是把文章落到组织实践时必须回答的问题。

文章隐含了一个前提：agent 读取到的控制文件越多，攻击面越大。这个前提是对的，但它也需要和 context infrastructure 的收益放在一起权衡。`AGENTS.md`、skills、rules 文件确实增加攻击面，同时也是让 agent 从 generic assistant 变成 informed practitioner 的关键机制。真正的问题不是少写规则，而是给规则分层、定级、审查和版本化。文章指出了风险，但没有充分展开这种分层治理方案。
